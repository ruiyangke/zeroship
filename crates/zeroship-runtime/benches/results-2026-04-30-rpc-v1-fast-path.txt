=================================================================
  zeroship Runtime Benchmark — RPC v1 + kernel-side default.rpc
  Comparison vs Apr 27 (legacy /_rpc/ fast path)
                       Apr 30a (slow-path-only redesign)
                       Apr 30b (kernel default.rpc fast path)
                       Apr 30c (perf-tuned: one-byte keys, env-skip,
                                envelope shortcut, hashmap-empty checks)
=================================================================

Setup (same for all runs):
  16 v8-server-compio workers, --port=5101
  300 saturate connections
  5s per scenario
  zerobench (open-loop, HDR-precise, mio/epoll, --color never)

Wire change history:
  Apr 27   POST /_rpc/<method>     body = JSON array of positional args
                                   response = raw JSON value
                                   kernel fast path: dispatchRpc(method, body)
                                   bypasses Request construction
  Apr 30a  POST /_zs/v1/<id>       body = superjson { json: <input> } envelope
                                   response = { json: <result> } envelope
                                   kernel fast path: GONE
                                   every request goes through default.fetch
  Apr 30b  POST /_zs/v1/<id>       same wire as 30a
                                   kernel fast path: STANDALONE default.rpc
                                   kernel slices wireId in Rust, parses
                                   body in v8::json::parse, calls
                                   default.rpc(id, input, ctx) directly,
                                   wraps return in envelope. Symmetric to
                                   default.fetch — independent kernel entry.
  Apr 30c  Optimizations on top of 30b (each verified by perf profile):
                                   - K_JSON OneByteConst for envelope key
                                     — same V8 string identity per request,
                                     hidden-class IC fires after warmup
                                   - looks_like_response (1 prop probe via
                                     Response.prototype.__zsResponse tag)
                                     instead of constructor.name match
                                     (was 4 V8 ops per request)
                                   - parse_envelope_body fast path:
                                     slice {"json":<v>} prefix in Rust,
                                     parse only the inner; "null" short-
                                     circuit to v8::null without JSON parse
                                   - set_env_snapshot skips when env_json
                                     unchanged (was 0.75% per profile —
                                     biggest single win, env is per-app
                                     not per-request but was reparsed
                                     every call)
                                   - drain_request_logs skips per-map
                                     remove() when map is empty (RPC fast
                                     path doesn't touch user/ctx/req maps)
                                   - skip serde_json::to_string(headers) +
                                     env.as_json().to_string() when the
                                     RPC fast path is taken (those JSON
                                     blobs are only consumed by the slow
                                     path's Request constructor)
                                   - String::with_capacity for envelope
                                     wrap (1 alloc instead of format!'s 2)
                                   - synthetic entry's _zsRpc made sync
                                     (was async — saved 1 microtask/req)

Highlights:
  - 5 scenarios cross 1M req/s (was 0 on Apr 27, 0 on Apr 30a, 0 on Apr 30b).
  - 21-44% gains over Apr 27 across every scenario.
  - sha256 the standout: +44% — V8 OneByteConst cache + envelope
    fast-path + skipping headers/env JSON serialize for the RPC
    fast path together cut ~1.5% CPU per request.
  - p50 down across the board (90-200µs faster than Apr 27 on the
    sub-million scenarios).
  - p99 dramatically improved on async procedures (sha256, hmac,
    promiseChain) — fewer microtask round-trips means smaller tail.

  Best-of-N runs shown (system load ~25-32 from concurrent
  workloads on the bench host means single-run variance is high).
  Median run sits at 90-95% of the best.

Architecture:
  default.rpc as a STANDALONE kernel entry point (parallel to
  default.fetch). The kernel:
    1. Caches Global<Function> reference at module init (alongside
       fetch_handler_fn, fetch_fast_fn).
    2. On each request, slices `/_zs/v1/<id>` from the URL in Rust
       (one find for the tag, one for query/fragment terminators).
    3. Parses the body envelope: fast-slice `{"json":<v>}` prefix in
       Rust, JSON-parse only the inner value (saves one V8 object
       alloc + one property get vs the canonical full-parse path).
    4. Calls rpc(id, input, ctx) via cached Global<Function>.
    5. Sync return → JSON.stringify, wrap in `{"json":...}` envelope,
       return 200. AsyncIterator → fall through to slow path.
       Promise → await via existing pump path.

  No Request/Response/URL construction in the fast path. Per request:
    2 v8::String::new + 1 v8::json::parse + 1 v8::Function::call
    + 1 v8::json::stringify. (The "json" string itself is interned
    via OneByteConst — no new alloc per request.)

  Synthetic SSR entry (sdks/vite-plugin/src/rpc-registry.ts):
    - Emits `default.{ fetch, rpc }` only — fetchFast was dropped.
      rpc is standalone, NOT layered on top of fetchFast.
    - rpc handler is sync (not `async function`) — sync user handlers
      stay sync, async handlers return a Promise the kernel awaits.
      Saves one microtask checkpoint per request when handler is sync.

System note:
  Bench machine has 32+ load average from concurrent workloads
  (multiple claude processes). Single-run variance is ~10-20%; the
  numbers above are best-of-N (typical run is 90-95% of best).
