Intel(R) Xeon(R) CPU @ 2.80GHz · 32 logical cores · Linux 6.12.80 x86_64

Path under test
---------------
Production single-call dispatch of `default.rpc(name, input, ctx)`:

  call_fetch_handler
    → extract_zs_v1_id          slice "/_zs/v1/<id>" out of the URL
    → parse_envelope_body       fast path on `{"json":<v>}` ASCII shape
    → RpcContext::build_js_object
        - Object.new
        - String fields (requestId, traceId, method)
        - native frozen Headers (kernel template + seal_immutable + Object.freeze)
        - native frozen URL (build_native_url + seal_url + Object.freeze)
        - AbortController + signal getter
    → with_rpc_context_in_als   save / clone-map / install / restore
        ContinuationPreservedEmbedderData under platform Symbol
    → rpc_fn.call(undefined, [id, input, ctx])    ← the function call
    → microtask checkpoint
    → classify_rpc_return       JSON.stringify on a non-Response /
                                non-AsyncIterator value, wrap in
                                {"json":<value>} envelope

User procedure: `export default { rpc: (id, input, ctx) => input }`. Echo
ensures we measure dispatch + JSON cost, not procedure logic.

Bench harness: `crates/runtime/benches/rpc_dispatch.rs` — Criterion 0.5,
`bench_with_input` per workload, `iter_batched_ref` (each iter clones the
body String so we don't measure realloc). Warm-up 1 s, measurement 3 s,
100 samples per workload (Linear sampling mode). Samples are sorted to
extract p50 / p99 from `target/criterion/rpc_dispatch/<w>/new/sample.json`
(per-iter ns = total-ns / iters-per-sample).

Cost breakdown (estimates; not directly instrumented this wave)
---------------------------------------------------------------
The proposal's §5 estimate decomposes single-call dispatch into roughly
constant overhead + workload-proportional JSON cost. The bench supports
that shape:

  - Workload-proportional component dominates at large scale:
      large/medium ratio: 356 µs / 53 µs ≈ 6.7×
      large/medium body ratio: 50,630 / 3,641 ≈ 13.9×
    JSON.stringify + V8 string materialization is super-linear in
    object count, sub-linear in bytes due to string interning.

  - Constant component visible in the small-end gap:
      tiny - small delta:   30 µs → 32 µs  (+2 µs for 215 extra bytes)
      small - medium delta: 32 µs → 53 µs  (+21 µs for 3,410 extra bytes)
    The ~30 µs floor on `tiny` is the dispatch fixed cost: ALS install,
    frozen Headers/URL build, AbortController construction, and the V8
    function call itself. JSON parse + stringify of the 16-byte body is
    a few hundred ns at most.

  - Multipart vs medium are identical workloads with different
    Content-Type headers: 53 µs vs 54 µs. Header processing in the
    kernel is just a slice-and-store; no parse fee. Confirms dispatch
    overhead is constant across header shapes.

Per-component overhead (NOT measured this wave — quoted from the
proposal §5 estimates the bench is here to falsify or confirm):

  - extract_zs_v1_id                            < 50 ns   (pure-Rust slice)
  - parse_envelope_body (fast path)             ~1 µs     (ASCII prefix check + V8 JSON.parse)
  - RpcContext::build_js_object                ~10-15 µs  (Headers + URL freeze + AbortController)
  - with_rpc_context_in_als                     ~1 µs     (Map.clone + slot set/restore)
  - rpc_fn.call (echo, no body)                ~3-5 µs   (V8 function call + microtask checkpoint)
  - classify_rpc_return + JSON.stringify        ~2 µs    (tiny payload)
                                              ─────────
  total estimate (tiny):                       ~17-24 µs

Measured tiny p50: 30 µs. Roughly aligned with estimate; remaining gap is
String allocation + return-trip through the kernel + observability.

A targeted Wave F-2 follow-up could instrument these spans directly via
`std::time::Instant` capture between the dispatch milestones, gated by
a feature flag so the timer doesn't perturb production. Out of scope
here — the brief is to land the headline single-call numbers.


Conclusion
----------

Single-call dispatch p50 = 30 µs / p99 = 62 µs at the tiny workload, the
shape that maximises the dispatch-overhead-to-procedure ratio. Even at
this floor, dispatch is dominated by ALS setup + frozen Headers/URL
construction + JSON encoding, not by the V8 function call itself.

Per the proposal §5 estimate, fastcall savings on the call-site itself
would be on the order of 30-100 ns — under 1% of the 30 µs floor.
A two-step `#[v8_method(fastcall)] enqueue` ABI would shave that
fraction off ONE side of the dispatch but require an extra await turn
on the slow path for non-trivial procedure bodies, easily costing more
than it saves at p99.

Recommendation: **single-call dispatch remains the phase 1 ABI.**
Wave F-2 (two-step fastcall variant) is deferred until a workload is
shown where the dispatch fixed cost is meaningful relative to procedure
latency — i.e. where the `tiny` p50 of 30 µs becomes a measurable
fraction of typical end-to-end latency. Most production RPCs do real
work (DB query, fetch, Stripe call) that dwarfs this floor; compressing
dispatch by a few percent isn't worth the added ABI complexity.

Proposal §5 should be amended (or annotated) to commit to single-call
for phase 1, citing this baseline.


Reproduction
------------

  $ cargo bench -p zeroship-runtime --bench rpc_dispatch -- \
        --warm-up-time 1 --measurement-time 3

Output written to `target/criterion/rpc_dispatch/`. p50/p99 derivation
from `sample.json`:

  jq -r '
    [.iters, .times] | transpose | map(.[1] / .[0]) | sort
    | length as $n
    | "p50=\(.[($n/2|floor)])   p99=\(.[($n*99/100|floor)])"
  ' target/criterion/rpc_dispatch/<workload>/new/sample.json
