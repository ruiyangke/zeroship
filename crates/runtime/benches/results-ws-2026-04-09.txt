==========================================================
Optimizations applied
==========================================================

1. Cached V8 handles: resolve __wsRegistry[id]._onMessage/_onClose once at
   ws.accept() time, store as v8::Global. Eliminates 3 property lookups per
   message (-6.8% V8_ENGINE). call_ws_method is now fallback-only.

2. Event-driven pump: replaced 10ms sleep()+select! polling with WsPollBoth
   custom future (Rc<Cell<bool>> flag + Waker). Fixed 200-client stall.

3. Removed Fuse/select! overhead: hand-rolled WsPollBoth polls TCP read and
   outgoing notification without Fuse wrappers (-1% async overhead).

4. Eliminated from_utf8_lossy: use String::from_utf8 (fast path, no scan).
   Removed redundant incoming buffer push (message delivered directly via V8).

==========================================================
Remaining bottleneck
==========================================================

io_uring syscall + compio runtime = 42.5% of CPU. This is the I/O floor.
V8 Function::Call + JS execution = ~16%. This is the JS floor.
Together = ~59%. Remaining 41% is framework overhead (task scheduling,
buffer management, waker machinery).

Node.js advantage: ws library echoes in C++ without entering V8. Our
architecture requires V8 enter/exit per message because the handler is JS.
This is by design (user code flexibility > raw echo perf).
