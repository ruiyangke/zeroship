# PLATFORM_RESERVED_COLLECTION_PREFIXES: keep it, and the rule for the rest

Read at `7dd6ad9b5`. Nothing was built; every claim is marked.

## 1. The answer

**KEEP it, hard-coded, in all three copies. Do not delete it and do not inject it.** The single fact that decides it: this is a *refusal* over creator-supplied input, and the only party positioned to supply an injected list is the worker, which executes creator code - so an injectable fence here is a fence the constrained party can pass `&[]` to, which is the platform invariant in AGENTS.md ("privilege follows the PROCESS"), not a style preference. Deletion is separately refuted by one line: `IdentRole::reservations()` returns `Self::Collection => &[]`, so this constant is not one refusal among several - it is the *entire* platform collection fence in that crate, and the whole `if role == IdentRole::Collection` block in `Ident::parse_as` is it (CONFIRMED, read at `crates/zeroship-data-query-builder/src/ident.rs`). Two honest qualifications you should state out loud rather than let a reader infer: (a) the crate has **zero non-dev dependents** - `zeroship-schema` and `zeroship-plugin-db` are both `kind=dev`, `optional=false`, verified by `cargo metadata --no-deps`, and they are the only two reverse edges - so deleting it today is a *latent* regression, armed the day the write family is wired, not a live one; (b) **the commit that becomes necessary when the IR is wired is not on this constant at all** - it is the audit-table exception, because `__zeroship_audit_unmask` is a relation the worker holds `GRANT INSERT` on by explicit exemption (`WORKER_WRITABLE_RESERVED_TABLE` in `crates/zeroship-data-engine/src/auth/bootstrap.rs`) and which `Ident::parse_as(_, IdentRole::Collection)` refuses, with no exception mechanism. Design that exception in the shape `bootstrap.rs` already chose - blanket prefix minus an enumerated allowlist - **before** the write family ports, or the port dies on the one INSERT that records who read plaintext.

## 2. Why it differs from `PLATFORM_FIELD_NAMES`

Your framing is right and the difference is one axis, not two. `PLATFORM_FIELD_NAMES` **widened** what the plan emitted: it unioned seven platform names into every row projection, so the caller could not say what a row was. Deleting it narrowed the plan to what the caller asked for, and the invariant that was riding on it had to be restated explicitly - `7dd6ad9b5` added `ProjectionError::Empty` in the same commit precisely because "non-empty" had been a side effect of the union. `PLATFORM_RESERVED_COLLECTION_PREFIXES` **narrows** what the plan will represent. Delete it and nothing fails; the plan silently accepts more.
One correction to your point 3, and it matters because you will cite it again: **`__zero_migrate` prefixes nothing live in this tree** (CONFIRMED). Every remaining occurrence is a *suffix* (`format!("{table}__zero_migrate_rebuild")` in `zeroship-migrate-backend/src/table_rebuild.rs`, which a prefix fence cannot cover), a MySQL session variable, a comment about a sidecar `__zero_migrate_schema_meta` that three files say "does not exist", or a test corpus. `__zeroship_` *is* live, over a dozen relations. Pass C's census counted spellings and read them as objects; Pass A and the refuter both enumerated properly and I re-ran it. Side with them.

## 3. The rule for the next one

> **If the item decides what the plan EMITS, the name belongs to the caller. If it decides what the plan REFUSES, the list stays hard-coded.** An emitted name is knowable only by the caller, which is why `7dd6ad9b5` and `49e743269` were right; a refusal fences creator-supplied input and the only available injection site is the worker, which executes creator code, so an injected refusal is one the constrained party can empty. Corollary you will need twice: **"it no longer guards a live object" is not a reason to delete a refusal** - a reserved name becoming creator-nameable is a one-way door, and holding a squat is free. Items that are neither (identifier-*form* rules, protocol limits) are not platform vocabulary and are out of scope.

Applied to Pass C's census. `generate` = the item puts a name or a value into emitted SQL. `refuse` = the item rejects an input. `shape` = neither; a rule about identifier form or a wire/protocol limit.

## 4. What is actually broken

**(a) `__zs_` is a live platform relation prefix that no collection validator refuses. This is the only live bug in the census - CONFIRMED, four independent readings.** `zeroship-core/src/replication_names.rs` declares `OBJECT_PREFIX = "__zs_"` for publications and slots; `zeroship-data-sqlite/src/cdc.rs::is_filtered_relation` drops every `__zs_`-prefixed relation from CDC; and `zeroship-data-sqlite/src/lib.rs::introspect_schema` skips them, with the doc comment right above it saying "surfacing system tables would trigger spurious 'drop table' classifications". Meanwhile `__zs_` is reserved for `Namespace`, `Column` and `Alias` and **not** for `Collection`, and `"__zs_internal"` is a deliberate *acceptance* witness in both `the_table_fence_holds` and the Collection parity corpus. So a creator collection named `__zs_orders` is created by all three validators, then vanishes from schema introspection - the diff classifier sees an existing creator table as absent - and its CDC events are dropped in silence. That is a schema-authority bug, worse than the dropped subscription Pass B stopped at. NEEDS-BUILD to settle end to end.

**(b) Both role-enumeration guards are blind to `StoredColumn`, the one role added to loosen a fence - CONFIRMED.** `IdentRole` has seven variants. `every_role_has_deliberate_reservation_behavior` builds a six-element `cases` array and then asserts `cases.len() == 6` - the array measured against itself, never the enum against the array - under the message "a new role must be given reservation behavior deliberately". `tests/ident_refusals.rs` declares `const ALL_ROLES: [IdentRole; 6]` without `StoredColumn`, so the injection sweep (`users"; DROP TABLE users; --`, NUL, non-ASCII) never runs against it. Both stayed green through `49e743269`. This is the "gate that prints green while checking nothing" family, live, in a commit from this week.

**(c) The equality pin is a downward ratchet - CONFIRMED by reading, NEEDS-BUILD to demonstrate.** `reserved_collection_prefixes_match_migration_engine` is two `assert_eq!`s on exact slices, so **no copy can be made stricter alone**. Adding `"__zs_"` to one list turns three tests red in two crates: the slice pin, `reserved_collection_behavior_matches_migration_engine` (because `__zs_internal` is an agreed-acceptance witness), and `the_table_fence_holds` - which additionally has `assert_eq!(ruled_on, 14)` as exact equality, so the count is hand-edited. Consequence for you: **fix (a) as one commit touching all three crates, or the tree does not build green.** Do *not* invert the pin to implication (`plan_accepts => engine && schema`) to avoid that. It sounds better and it is worse: equality is what makes the audit-table blockage in section 1 a hard stop that forces the design conversation, and an implication pin licenses "the IR is allowed to be stricter, route around it", whose two cheapest routes are leaving `append_unmask_audit` on the `format!` path forever or adding a permissive `StoredCollection` role in exactly the shape that just slipped past both guards in (b). An equality pin also cannot go vacuous; a behavioural implication corpus can.

**(d) The IR's manifest refuses a `zeroship-schema` dependency for a reason that is false - CONFIRMED.** `crates/zeroship-data-query-builder/Cargo.toml` says depending on it "would drag a live PostgreSQL driver into a crate whose whole claim is that it can be built and tested without a database", citing `compio-postgres`, `zeroship-core` and `tracing`. `zeroship-schema`'s `[dependencies]` today are `serde_json`, `zeroship-core`, `sha2`. Two of the three names are gone. The *conclusion* survives on a different and narrower ground the manifest does not state: `serialize_derive_is_structurally_impossible` in `tests/no_sql_text_escape_hatch.rs` asserts the dependency tables are empty, and `zeroship-schema` transitively supplies `serde`, which would make `#[derive(Serialize)]` on `DbPlan` compile and kill SC-3 decision 3 as a structural fact. The next auditor inherits a false premise.

**(e) `tests/sync_claim_gate.sh` cannot see this obligation - CONFIRMED, and the miss is one word.** `crates/zeroship-data-query-builder/src` is in `ROOTS` and the crate has claim-phrase hits elsewhere (`projection.rs`, `render/mod.rs`, `write.rs`, `search.rs`, `predicate.rs`), but `ident.rs` produces **zero**, and there is no LEDGER row for the three-way claim under any file. `zeroship-schema` and `zeroship-migrate-core` both write "Platform-owned collection prefixes **mirrored by**..."; `CLAIM_PHRASES` contains `mirror of`. `zeroship-migrate-core`'s comment even names `zeroship-schema`, satisfying the crate-token half and failing only on the phrase. One genuine cross-crate obligation, invisible to the gate built to enumerate them.

**(f) Your dev-dependency candidate is NOT broken. Kill it.** The direction is forced: the IR's `[dependencies]` table is literally empty and a test asserts it stays empty, so the crate cannot pin anything upward, and the pin must live in the only crate that dev-depends on all three. Pass B priced the wrong arrow - `zeroship-schema -> IR` as a normal edge would mean schema *links* the IR, which is not the edge anyone wants; the useful arrow is `IR -> schema`, and it costs exactly the structural-Serialize fact above. The real residue is discoverability: `cargo test -p zeroship-data-query-builder` and `-p zeroship-migrate-core` never compile the pin. CI runs `cargo test --workspace --no-fail-fast`, so it is a local-loop hazard, not a hole. Not worth a commit.

**Two claims from the passes I am overruling.** Pass A reports that a DB-3 exploit attempt is "indistinguishable from routine anonymous traffic" because the rejected actor is not audited. That is a stale AGENTS.md sentence, not the tree: `claimed_actor` exists and is populated - declared in `crates/zeroship-data-core/src/capability.rs`, built in `crud/unmask.rs`, listed in both INSERT arms in `backend_handle.rs`, and declared in the DDL in `zeroship-migrate-server/src/provisioning.rs` (CONFIRMED, I grepped all five). Side with the refuter. And "defence in depth across three enforcement points" is the wrong phrase for the fence itself: `zeroship-migrate-core`'s copy fences DDL declaration, `zeroship-schema`'s fences runtime CRUD, and they never see the same input - that is **coverage of two disjoint flows plus one pre-positioned fence**, which is a *better* argument for keeping all three (deleting either live one opens a door the other does not watch) but is not depth. `AGENTS.md` and `crates/zeroship-data-engine/src/auth/mod.rs` both say "three crates pin against each other" in a list of protections; that reads as triple-fenced at runtime, and it is single-fenced.
