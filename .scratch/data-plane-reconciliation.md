# Data plane vs its proposal corpus: a reconciliation

Scope: the data-crate split (`docs/proposals/2026-08-31-data-crate-shape.md`) and the corpus that constrains it. Every claim is marked CONFIRMED or PLAUSIBLE. CONFIRMED means either a dossier verifier ruled it confirmed, or I re-derived it in this pass with a command I state. PLAUSIBLE means it survived one investigator and was not independently re-derived, or it needs a build. Nothing the verification passes refuted appears here. No line numbers are cited; where a citation is load-bearing I name the function and quote the code.

---

## 1. Where the split actually stands

The cut that mattered landed: the engine tier is out of the adapter, both vendor tiers are their own crates, and `zeroship-data-engine/src/backend/mod.rs` is a re-export ladder plus the `Backend` conformance marker. What did not land is the *verification* boundary. None of `zeroship-data-{core,engine,postgres,sqlite,cdc-server}` declares a `tests/` target, so the code moved and its oracle stayed in `zeroship-plugin-db` - which links V8, `zeroship-runtime` and both drivers - and no extracted crate can be exercised without building the thing the extraction existed to get away from (CONFIRMED: `find crates/<c>/tests -name '*.rs'` returns nothing for all five; `zeroship-data-query-builder` has ten and `zeroship-plugin-db` eighteen). The manifest fence the proposal calls the enforcement mechanism is real for `zeroship-data-core` and `zeroship-data-query-builder` and does not exist for the adapter, which declares nine dependencies it never names, `rusqlite` among them, while the vendor gate exempts four shipped adapter files by name. And the largest non-adapter block still inside `zeroship-plugin-db` is the CDC consumption path, which is genuinely blocked rather than deferred - so "six of six crates" is a true statement about the crate graph and a misleading one about the work, which the shape proposal's own status block already says.

## 3. What is unfinished, in dependency order

### 3.1 The three instruments that police the boundary are blind

Blocks everything below it: you cannot move code across a tier and know you did not carry vendor knowledge with it.

- **`tests/lib/vendor_value_flow_census.sh` measures nothing.** CONFIRMED - I ran it. It prints one source (`as_runtime_role`) and zero holders. Its `SRC_ROOTS` are `zeroship-plugin-db/src` and `zeroship-data-engine/src`; the dominant vendor-returning accessor is `pub fn pool(&self) -> &Rc<compio_postgres::Pool>` in `zeroship-data-postgres/src/postgres.rs`, outside both roots, so it is never collected as a source and its callers can never be reported. Worse, the one source it does find is inside `#[cfg(all(test, feature = "live-db-tests"))]`, because the source collector applies only the comment filter while the caller matcher applies the production filter. Both halves are vacuous.
  **First commit:** extend `tier_of_file` with `PG`/`SQLITE` arms keyed on the new roots and prove a known holder in `zeroship-data-postgres` is tiered and skipped for the right reason, THEN widen `SRC_ROOTS`, THEN give the source collector a floor. Widening the roots first converts a loud zero into a quiet wrong number, because every file under the new roots falls through to `CONTESTED` and is skipped as a caller.

- **`tests/vendor_embedding_gate.sh` carries three arms naming a deleted directory.** CONFIRMED - `is_vendor_tier` has arms for `zeroship-plugin-db/backend/postgres.rs`, `zeroship-plugin-db/backend/pg_*.rs` and `zeroship-plugin-db/backend/sqlite/*`, and `ls crates/zeroship-plugin-db/src/backend` is "No such file or directory". This is the exact defect the gate's own arm 2 refuses for baseline entries, applied to a skip list nothing audits - and a dead skip is strictly worse than a dead baseline, because a baseline is printed every run and a skip is silent.
  **First commit:** delete the three dead arms. Leave the predicate vendor-blind; making it per-vendor doubles `n_ruled` against an unchanged floor, dropping the collapse-detection ratio at the moment the gate is advertised as stronger.

- **The same gate rules on a fraction of `lib.rs`.** CONFIRMED. Its boundary is the first `#[cfg(test)]` immediately preceding a `mod`, and in `zeroship-plugin-db/src/lib.rs` large production blocks follow it - `BackendUrl`, `backend_for_url`, `backend_init_inputs`, `BackendInitGuard`, `init_pool_async`, plus a `#[doc(hidden)] pub use backend::pg_row_json::{first_row_or_null_for_bench, row_to_json_for_bench}` that two-hops into `zeroship-data-postgres` and is not cfg-gated. Nothing is currently falling through the hole.
  **First commit:** take the last `#[cfg(test)] mod` rather than the first, or exclude each test module's brace span. `tier_direction_census.sh` already carries a brace-depth tracker.

- **`tests/data_crate_closure_gate.sh` guards two of seven crates against four names, on the resolved graph.** PLAUSIBLE. It cannot see a declared-but-unused dependency by construction, and its own header says so honestly - it scopes itself to linkage. `zeroship-data-engine`, `zeroship-plugin-db` and the relay are unguarded. Its arm 1 floor equals the exact product of its two lists while its comment claims the floor is deliberately one below.

### 3.2 The adapter's manifest fence does not exist

The proposal's enforcement argument is "you cannot name `compio_postgres::Error` in a crate that does not depend on it - that is E0433, at compile time, for everyone, forever." For the adapter there is no E0433.

CONFIRMED, and the count is the finding. Reproduce in `crates/zeroship-plugin-db`:

```
for d in rusqlite sqlite_vec aes_gcm hkdf hmac base64 zeroize zeroship_data_postgres zeroship_data_sqlite; do
  printf '%-24s src=%s tests+benches=%s\n' "$d" \
    "$(command grep -rn -P "(?<![A-Za-z0-9_])$d\b" --include='*.rs' src/ | command grep -vE ':[0-9]+: *(//|///|//!|\*)' | wc -l)" \
    "$(command grep -rn -P "(?<![A-Za-z0-9_])$d\b" --include='*.rs' tests/ benches/ | command grep -vE ':[0-9]+: *(//|///|//!|\*)' | wc -l)"
done
```

All nine report `src=0`. Only `rusqlite` and `base64` appear in tests, so those two demote rather than delete. The three manifest comments justifying the crypto group, the `sqlite-vec` registration and `with-uuid-1` all describe modules and files that left: there is no `crate::encryption` (it is `pub use zeroship_data_core::encryption`), the `sqlite3_auto_extension` registration is in `zeroship-data-sqlite/src/session.rs`, and `pg_row_json.rs` is in `zeroship-data-postgres`.

**Why it blocks:** while `rusqlite` is a live manifest dep of the adapter AND `is_vendor_tier` exempts four shipped files by name, a `rusqlite::Connection` written into `wal_consumer.rs` compiles, passes the vendor gate and passes the closure gate.

**First commit, and the order is not optional:** collapse `[features] test-helpers` onto `["zeroship-data-engine/test-helpers"]` first - the engine's own `test-helpers` already forwards to core, postgres and sqlite - THEN drop the declarations. Whether a `dep/feat` entry resolves through a `[dev-dependencies]` entry alone is a build question (section 6), and getting it wrong fails the whole live-Postgres suite for an edit justified by a grep.

### 3.3 No extracted crate can be verified alone

CONFIRMED. `cargo metadata` reports zero `test` targets for `zeroship-data-{core,engine,postgres,sqlite,cdc-server}`. Their in-crate `#[cfg(test)]` coverage is substantial and includes live-PostgreSQL modules in the engine's `auth/bootstrap.rs` and `exec.rs` and a real-SQLite suite in `zeroship-data-sqlite` - so "zero coverage" would be wrong. What IS concentrated in the adapter is the bulk of the live-database coverage: eight of `zeroship-plugin-db`'s test targets name neither `v8::` nor `zeroship_runtime` and reach the engine and vendor tiers purely through the `lib.rs` re-export ladder.

**Why it blocks:** it inverts the proposal's own verification recipe, and it is what holds the ladder up. You cannot delete the `pub use` half of the ladder until those tests have somewhere to live.

**First commit:** declare one `[[test]]` target in `zeroship-data-engine` with `required-features = ["test-helpers"]` and move a single arm whose subject is engine behaviour. The `required-features` declaration is load-bearing and must land in the same commit: without it a bare `cargo test -p zeroship-data-engine` compiles a smaller set and prints a clean green with no skip line - the failure mode AGENTS.md already records for `cargo test -p compio-postgres`. Add an arm counting declared cases against cases that ran, because `--all-targets` silently skips a target whose `required-features` are unmet.

**Do not move by file.** The `cold_*_open_comes_from_ensure_backend_not_the_fixture` family in `crates/zeroship-plugin-db/tests/sqlite_integration.rs` asserts an ADAPTER behaviour (that the backend was opened by `tx_scope::ensure_backend`'s cold arm) observed through ENGINE calls. Moved down, the assertion becomes unbuildable, and the three ways out are all worse than the ladder: a second composition root (which is exactly the divergence `audit_table_parity.rs` and `mask_flip.rs` exist to detect), reversing the 2026-09-03 cut, or losing the only live-database coverage the data plane has. The split is per-test, and nobody has measured it.

### 3.5 The CDC extraction

CONFIRMED blocked, and one of the two recorded blockers is not what it says.

- `DatastoreId` exists only in `zeroship-cdc-wire` plus one rustdoc line in the relay. No table, column or control-plane record mints one. That blocker is real and code-verified.
- The "PostgreSQL 18.4 move" is a **design specification recited as a measured constraint**. CONFIRMED: `grep -rn "180000\|190000\|server_version" --include='*.rs' crates/zeroship-data-cdc-server/src/` returns nothing; the crate is three files; the only 18.4 in it is a comment in `lib.rs` reading "pins `postgres:16`; the relay's design assumes the 18.4 move." **First commit that moves it:** none inside the relay crate. Resolve that before anything encodes a frame.

### 3.6 `zeroship-data-query-builder`: built, tested, wired to nothing

CONFIRMED. It is a `[dev-dependencies]` entry in `zeroship-plugin-db` and `zeroship-schema` and nowhere else; `grep -rn "zeroship_data_query_builder" --include='*.rs' crates/*/src/` returns hits only inside the crate itself and inside `zeroship-schema/src/query.rs`'s `#[cfg(test)]` parity modules. Production query building still goes through `zeroship_schema::query`'s `BuiltQuery`. There is one renderer (`render/postgres.rs`), so the parity property the `ValueFormat` trait exists to enforce has never been exercised, and SC-3's parity acceptance arm cannot pass. Three of six plan families, the `FieldPath` qualifier and the SQLite refusal set do not exist.

**First commit:** delete `ProjectionSource::MaskedSibling`, `ProjectedField::masked` and `Ident::masked_sibling_of`. They are constructible today and render against `<field>_masked`, a column the storage flip stopped creating - so a plan built through them renders SQL against a column no migration produces. Self-contained, no external callers, removes a footgun the wiring work would otherwise carry into a shipped path. SC-3 already names this.

## 5. Defects and posture gaps worth acting on

Ranked.

**1. CDC slot lifecycle sits in the process that runs creator code.** CONFIRMED, and it is the invariant, not an approximation of it. `ALTER ROLE zeroship_worker WITH ... REPLICATION BYPASSRLS` in `db/migrations-ts/20260818000200_worker_database_authority.ts`; the worker refuses to boot without both (`crates/zeroship-worker/src/db_posture.rs`). Creator JS reaches `pg_create_logical_replication_slot` through `collection.openSubscription()` -> `Subscription.ready()` -> `cdc_lifecycle::ensure_ready` -> `PgChangeStream::spawn_consumer` -> `replication::ensure_worker_slot` - the chain `tests/worker_replication_privilege_gate.sh` states in its own header and `change_stream_pg.rs` closes at the call site. `START_REPLICATION`, `pg_drop_replication_slot` and `pg_terminate_backend` follow on the same login role. This is not a `SECURITY DEFINER` wrapper; it is the worker holding the cluster attribute directly, which is the exact shape "privilege follows the PROCESS" forbids. **Correct AGENTS.md's clause to name slot ownership only** - publication ownership already moved to `zeroship-migrate-server`, and briefing an implementer on "slot and publication" sends them to move something correctly placed. The four coordinated edits are specified in `2026-08-28-cdc-service.md`; the gate blocks them going piecemeal in both directions.

**2. `wal_consumer::is_fatal` cannot match any real PostgreSQL error.** CONFIRMED end to end. It substring-matches `ConsumerError::Io(e.to_string())`, and `compio_postgres::Error`'s `Display` renders `Kind::Db` as the literal `"db error"` - pinned by the driver's own `a_server_refusal_reaches_the_reader_with_its_sqlstate`. No SQLSTATE, no message, no server text survives; `as_db_error` is never called in that file. So on a reconnect after a slot is dropped or invalidated, the supervisor classifies the failure as transient and retries forever at the backoff cap while holding `SuppressGuard` - the subscriber receives nothing and local emit stays suppressed. The three unit tests that look like coverage feed hand-built strings production never produces, and one is named `is_fatal_slot_invalidated_is_fatal` while asserting only the slot-DELETED spellings. Slot invalidation is a reachable steady state in every deployment, because the worker refuses to boot on an unbounded `max_slot_wal_keep_size`.
**The fix is not shippable alone.** Making it return true drops `SuppressGuard`, which resumes `emit_local` - a second producer with a different `changed_columns` meaning that only sees writes from isolates in its own process. In the multi-container shape that converts a detectably dead feed into an undetectably partial one. Fix the classification and the disposition together, or neither.

**3. `tests/lib/vendor_value_flow_census.sh` reports zero and cannot report anything else.** CONFIRMED (section 3.1). This is the instrument built specifically to catch the failure the token gate names in its own header - possession of a vendor value arriving by public field or inference, with no token at the call site. It currently reports a clean tree over a population it does not scan. The live instance it should be reporting: `v8_classes/replication.rs`'s watchdog dispatch, whose `async move` does `crate::backend::BackendHandle::Postgres(pg) => crate::replication::watchdog_query(pg.pool(), &app_id)` - a V8 class body handing a raw driver pool into a CDC function, with zero vendor tokens in the file, invisible to all three instruments at once. CONFIRMED, and the gate prints green over it.

**4. The unmask ceiling is built and unwired, in the same struct literal as the schema epoch.** CONFIRMED, re-derived here. `check_unmask_authorization(app_id, actor, classification)` takes no ceiling parameter. `observation_for` in `transaction/driver.rs` mints **three** unproduced constants, not one:

```rust
epoch: expected.epoch,
lifecycle: LifecycleState::Stable,
// No ceiling is published yet, so the fold starts from the empty
// ceiling. `meet` can only tighten it, which is invariant 8.
ceiling: MaskCeiling::default(),
```

`MaskCeiling`'s only consumers outside `identity.rs` are `reducer/mod.rs`'s private `begin_ceiling` / `effective_ceiling` fields and the reducer tests. `LifecycleState::Stable` is why `APP_DEPROVISIONED` and `STALE_APP_INCARNATION` are unreachable. Three lenses reported three findings against this one literal and none saw the join, and `docs/proposals/2026-08-26-sc6-ceiling-read-contract.md` names both missing halves in its own status block. **The producer question is owned**, not orphaned: `docs/proposals/2026-08-26-sc5-service-ownership.md` designs the durable app incarnation as an append-only ledger plus a worker-read-only projection - AGENTS.md's `__zeroship_admin` shape - and its own Open 1 says the blocker is "It has no home". That is a decision, not a coding task. Separately, AGENTS.md's "the epoch again needs only its producer" is true about the comparison plumbing and silent about where observations enter: there is one non-test `AuthorityObserved` publisher, in `begin_top_level`, and `Action` has no authority-read variant, so the epoch would be checked once per transaction rather than once per statement. SC-1 invariant 7 asks for the latter.

**5. Ten numbered defects live only in code comments.** CONFIRMED, and the count is the finding:

```
command grep -rhoP '\bDB-\d+\b' --include='*.rs' crates/ libs/ | sort -u -V
command grep -c 'DB-[0-9]' docs/proposals/2026-08-26-runtime-db-binding-defect-register.md
```

Twelve identifiers in code; the register returns zero matches and carries `DB-2` in prose only. The entire review apparatus is organised around the `### L` headings, so DB-7, DB-11, DB-12, DB-14 and DB-15 are unreviewed by anything. **DB-13 is the reason this matters more than bookkeeping.** `crates/zeroship-data-core/src/encryption/aad.rs` documents it as an *accepted residual risk*: deterministic columns omit `row_pk`, so an actor with UPDATE access can copy row A's deterministic ciphertext into row B and read A's secret through B. The block states the tension, names the alternative (randomised mode) and draws the opt-in boundary. The obvious remediation - bind `row_pk` into deterministic AAD - destroys the B-tree-on-ciphertext equality lookup that is the entire reason deterministic mode exists (equality silently returns zero rows, not an error) and makes every column already written undecryptable, with no migration path because the plaintext is behind the decrypt that now fails. Any pass that traces reachability must read each DB-N block's disposition first and treat "the code documents why this is accepted" as terminal.

**6. The CDC tenant fence is a raw string equality on the schema name.** CONFIRMED: `emit_for_tuple` in `wal_consumer.rs` carries `if rel.namespace != self.app_id { return; }` - the only cross-tenant guard on the decode path - and it does not go through `zeroship_core::app_derivation::schema_name`, the one function the decoupling proposal names as where the new derivation lands. The day a Database id names the schema, that predicate matches nothing and every subscription on every app goes silently dead. Fail-closed, so not a leak; a total loss of live queries with no error. This sits exactly at the junction of the relay's blocker and the worker's decode loop.

**7. `changed_columns` names every column in the relation.** CONFIRMED: `let changed_columns: Vec<String> = rel.columns.iter().map(|c| c.name.clone()).collect();` - unconditional, for insert, update and delete alike. The field's name is a claim about which columns a write touched, it feeds the broker's subscriber-narrowing, and nothing binds it. Note this refutes the premise of the CDC lens's own recommendation-hazard argument (that the WAL path has a narrower publication-derived set than local emit) - the hazard in item 2 stands on the emit-locality difference, not on projection width.

**8. The adapter's manifest fence does not exist** (section 3.2). CONFIRMED. Ranked here rather than higher because nothing has walked through the hole yet; it is paper widening what *could* be written, and it intersects a gate exemption.

**9. `vendor_embedding_gate.sh` rules on the region of `lib.rs` before its first test module** (section 3.1). CONFIRMED. Production items follow the boundary; none currently names a vendor.

**10. `protection_floor` fails open on any collection the live schema does not enumerate.** PLAUSIBLE, and the reachability half is explicitly unestablished. `read_live_schema` in `zeroship-data-postgres/src/pg_introspect.rs` filters `relkind = 'r'`, so a partitioned parent (`relkind = 'p'`) is invisible; `refuse_offences` opens `let Some(stored_columns) = floor.get(collection) else { return Ok(()); }`. `SchemaIntrospect for PostgresBackend` is unconditional now, so the blind spot has moved from a decrypt decision into a security fence on the shipped write path - and the register's L17 note says the impl is still cfg-gated, which is no longer true. **Whether a creator can create a partitioned table is a live-database question**, not a reading one: `policies/confined-system-shape.inject.toml` injects `primary_key = ["id"]` with `author_primary_key = "forbid"`, and PostgreSQL requires every unique constraint on a partitioned table to include the partition key, so only `id`-keyed partitioning could exist. **Do not widen the shared predicate.** `read_live_schema` also feeds the migration diff, which treats a missing table as `table_missing` and plans a CREATE; `relkind IN ('r','p') AND NOT relispartition` makes the parent appear and every existing partition disappear, rendering CREATE TABLE against live data. A second, floor-specific catalog query is the safe shape.

**11. `BoundedLockAcquire` (the bounded-retry fix) has no shipped caller, while the unbounded shape it replaces does.** PLAUSIBLE. Its three `use` sites are a `#[cfg(test)]` module, a `#[cfg(any(test, feature = "test-helpers"))]` module and an adapter integration test; the SQLite vendor never names it - so the manifest's justification, "both of them call it", is false on one half and unreachable on the other, and `compio` plus `tracing` were admitted into `zeroship-data-core` to host it. Meanwhile `crates/zeroship-auth/src/advisory_lock.rs`'s `with_advisory_lock` runs `SELECT pg_advisory_lock($1)` - the wait-with-no-timeout the policy's own rustdoc calls a DoS lever - with shipped callers in `ui/consent.rs`, `identity/password_reset.rs`, `oidc/device_token.rs` and `store/users.rs`. **The action is to give it the caller, not to delete it.** Deleting removes the only written-down bounded schedule at the moment a shipped caller needs it.

**12. The masking and encryption transforms have never been audited.** Not a defect claim - a coverage claim, CONFIRMED. `crates/zeroship-data-engine/src/crud/mask_pass.rs` computes the mask and physically places it, and its production callers are `crud/write_pipeline.rs` (six sites), `crud/read_pipeline::wrap_row_on_read`, `crud/encryption_pass.rs` and `crud/mod.rs` - reproduce with `grep -rn "mask_pass::" --include='*.rs' crates/`. `MaskPlaintextSidechannel`, a structure that carries plaintext between passes, is constructed at three `write_pipeline` sites and one in `encryption_pass`. Seven lenses ruled on the fence *around* masking - the five DB-3 sites, the `protection_floor` fail-open, the storage flip, `MaskedSibling`, the policy registry, the SQLite sidecar, the `_masked` reservation - and none opened the module that does the work, nor `encryption/{aad,aead,wire}.rs`. That is a selection failure, not a coverage one: every lens was defined by a container (a crate, a service, a document set), and a defect whose two ends are in different containers is invisible to all of them.

## 6. Contradictions and open questions

### Contradictions in the corpus

- **Where `TxConnection` and `PostgresCanceller` belong.** `2026-09-02-sc1-vendor-lane.md`: "The split question is not 'enum or trait', it is **which crate the enum is compiled into**, and the answer is the vendor tier." `2026-08-31-data-crate-shape.md` decision 4 budgets `TxConnection` as one of the engine's three dispatch enums beside `BackendHandle` and `TxCanceller`, dated earlier. The tree implements the shape proposal, and `tx_lanes.rs`'s header cites it by name. Two lenses deferred to the shape proposal as the placement authority; a third proved that document wrong in four places. **Needs an operator ruling** before either can move, and the ruling has to say what distinguishes the sanctioned `BackendHandle` edge from the contested `TxConnection` one - nothing in writing does.
- **`gateway_sessions` and `app_session_anchors`.** `2026-09-05-gateway-central-database-decoupling.md` moves the first to auth and keeps the second, and asks the operator whether the first should exist at all - offering the second as the alternative. `2026-09-05-auth-foundation-redesign.md` deletes both into one `zeroship.sessions` row. The auth redesign cites the gateway document; the gateway document does not cite the auth redesign. Outside the split, but it is the highest-value thing the corpus pass found, and no per-document status audit can see it because both documents are accurate about the tree.
- **The dead-dep count came back three different ways.** Nine is right for `src=0` (reproduced in 3.2 and by the plugin-db verifier, which re-measured all of the adapter's normal deps rather than only the claimed subset). The undercount of six omitted `base64`, `zeroship-data-postgres` and `zeroship-data-sqlite` - in the lens whose thesis was that the adapter's fence does not exist.
- **`change_stream_pg.rs` was assigned three states.** It names no vendor: `grep -c compio_postgres crates/zeroship-plugin-db/src/change_stream_pg.rs` returns 0 (CONFIRMED). The graph lens's headline correction - "the right unit is the FILE SET" - names it and omits `drop_namespace.rs` and `context.rs`, both of which do carry the token. `is_vendor_tier` exempts it for a vendor it never names.
- **The PITR statement.** One verifier asserted it is live in the PG vendor crate and scolded an investigator for insufficient confirmation, while itself not checking the cfg. The defects lens is right: double-gated on `feature = "test-helpers"`, ships in nothing.

### Needs a build to settle

None of the following was resolvable by reading, and each one changes a commit's shape.

1. **Whether `[features] test-helpers = ["zeroship-data-postgres/test-helpers", ...]` resolves through a `[dev-dependencies]` entry alone.** Decides whether 3.2 is one commit or two. Getting it wrong fails `cargo test -p zeroship-plugin-db --features live-db-tests` - the whole live suite - for an edit justified by a grep.
2. **Whether any data crate is in the inverse state** - needing a feature that only a sibling enables, so it builds in the workspace and fails alone. The adapter's manifest documents exactly this happening once with `with-uuid-1` (`Uuid: FromSql is not satisfied` under `cargo check -p` while every wider build passed). It needs per-crate `cargo check`; no grep can see it.
3. **Whether `cargo test -p zeroship-data-engine --lib` is feature-blind for the SC-1 arms.** It is right by luck at this commit (`reducer/tests.rs` carries no feature gate), and the crate declares `test-helpers` and `live-db-tests`. Pin the feature set in the corrected invocation rather than writing a bare `--lib`.
4. **Whether `tests/e2e_db_app_end_to_end.sh` is red.** By reading, it deploys a descriptor-carrying `.zship` before creating the database and applying migrations, and `Registry::set_deploy_with_manifest`'s predicate refuses that with a 409 whose body has no `deploy_hash` key - which the harness greps for. Nothing in `.github/` runs it. **Run it before changing anything**: if the fix is a reorder, it must not delete the pre-migrate `pg_roles` control, which is the only thing binding a green to the migrate step doing work. Note also that `--defer-deploy` is a `dev-provision` flag, not a `zeroship deploy` one, so the escape used by `tests/e2e_dev_vs_deployed_db.sh` is not directly available here.
5. **Whether `protection_floor`'s fail-open is creator-reachable** (item 10 above). Needs a partitioned creator table on a live database under the confined policy.
6. **Whether `zeroship_workflow_owner` - which `zeroship_worker` INHERITs - reaches any of the nine forced-RLS tables.** Decides whether dropping `BYPASSRLS` from the worker is free or silently empties reads of `app_spend_state` / `app_spend_limit`, which fails open on billing enforcement because RLS denies by returning no rows rather than an error.

### Open questions

- Is the split's end state "no vendor knowledge in the engine" or "one closed sum over both drivers, in the engine"? Both are written down, in different documents, and the tree implements the second.
- Does `zeroship-data-query-builder` land or get deleted? A second dialect and a production caller are the two things that would make its test suite mean anything, and neither exists.
- Where do PITR targets live, now that `__zeroship_admin` does not?
- The SQLite CDC path (`crates/zeroship-data-sqlite/src/cdc.rs`, reached through `BackendHandle::as_change_stream_sqlite`) is a complete second change-data-capture implementation that no lens opened. The shape proposal's verdict for it is "Deleted", reachable only once `RunningConsumer::Postgres` is a relay subscription handle. Dev/deployed CDC parity is untouched by this review.
