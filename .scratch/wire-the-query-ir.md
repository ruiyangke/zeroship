# Wire the query IR: migrating the data plane off string-built SQL

Written against HEAD `b3c1ff84e`, working tree clean except `?? .scratch/`. Nothing in this document was built, run, tested or linted. Every claim is marked CONFIRMED (read in the tree during this pass), PLAUSIBLE (read but not chased to its last consumer) or NEEDS-BUILD (requires execution to settle), and every NEEDS-BUILD carries the command that settles it.

The directive this plan serves, verbatim: *"for the query, I dont want raw sql or do string append, i want to build sql from structured query, just like other orms."*

---

## 1. What you get, and what it costs

**What you get.** Today a creator's filter key becomes a column name by arriving as a `&str` at a `format!` inside `crates/zeroship-schema/src/query.rs`, and its safety rests on a validator having been called by some caller, somewhere upstream, on a path nothing checks. After the migration a name cannot reach a statement without passing `Ident::parse_as`, because `RenderedSql` in `crates/zeroship-data-query-builder/src/render/mod.rs` has private fields and a `pub(crate)` constructor, so the only expression of that type outside the builder crate is one a renderer returned, and a renderer takes a `&DbPlan` whose every identifier position is already an `Ident` (CONFIRMED). That is stronger than a source gate saying "no `format!` outside a renderer": privacy constrains what can *arrive*, not merely where text is assembled. Four concrete defects die on the way and none of them is a rename: the `__zsbin__<col>` marker key, which smuggles a *type* decision through a JSON sibling key so the builder can pick a placeholder shape, is replaced by `Literal::Bytes`; `SQLITE_BINARY_BIND_PREFIX`, a value-level sentinel checked at the far end of an actor message queue, is replaced by the same thing; `build_having_condition`'s `col_expr: &str`, the one place in the shipped CRUD path where a fragment of SQL text is a first-class value passed between functions and looked up out of a `HashMap<String, String>` by alias, becomes `Operand::Aggregate(AggregateRef)`; and `build_write_target_probe`'s `built.sql.push_str(" FOR UPDATE")`, text surgery performed on generated text, becomes a field. You also get statement determinism for free: `LIMIT` and `OFFSET` are interpolated as integer literals today, so every page size is a distinct statement, and `build_insert_with_dialect` inlines the SQL keyword `NULL` rather than binding it, so a document's null-ness is part of the statement text and N nullable columns give 2^N statements. The IR binds all three.

**What it costs.** Months, not weeks, and the first *useful* commit is a day. The full port is roughly twenty commits, of which four are genuinely hard: a second renderer (there is exactly one `impl ValueFormat` in the crate today and exactly two files under `src/render/`; check with `grep -rn "^impl ValueFormat" crates/zeroship-data-query-builder/src/ && ls crates/zeroship-data-query-builder/src/render/`), a JSON-to-`Predicate` translator that does not exist anywhere in the tree, a typed-parameter seam that must land on both backends in one commit because `BackendHandle` hands one parameter vector to both arms, and an upsert node whose three sub-shapes the write grammar currently refuses by construction. Three of the crate's normative decisions have to be reopened before a single operation can move, and reopening them is design work, not typing: `RowLimit` is `1..=MAX_ROW_LIMIT` with no absent value and a default of the maximum (CONFIRMED), so a mandatory bound lands on reads that have none today; `Projection::rows` unconditionally unions `PLATFORM_FIELD_NAMES` (CONFIRMED), so `distinct("role")` is unrepresentable and every explicit `select` silently widens; and `Ident::parse_as` runs one charset check for every role, `is_ascii_alphanumeric() || '_'`, which refuses the hyphen that `SchemaName` exists to admit and whose own test `new_accepts_the_identifier_shapes_the_platform_actually_mints` asserts is legal for a bare UUID (CONFIRMED, both sides read this pass). **The IR crate is the right vehicle for the grammar and is currently the wrong shape for the coverage; the owner has ruled that it stays, and this plan does not relitigate that, but the three decisions above are not implementation details and cannot be settled by whoever ports first.**

## 2. The gap between the IR and an ORM-grade query builder

He said "just like other orms", so this section rules on the seven capabilities directly. The judgement column is *what `env.db` needs given the surface it offers creators today*, taken from `docs/reference/db.md` and the `#[v8_method]` set in `crates/zeroship-plugin-db/src/v8_classes/collection.rs`, not from what an ORM generally has.

| Capability | State in the IR | What `env.db` actually needs |
| --- | --- | --- |
| **Joins** | ABSENT. No node. `Select` holds one `collection: Ident`, and `FieldPath` is `{ root, segments }` with no qualifier field, so a column cannot even be *named* relative to a second relation. Not a stub: nothing. | **Almost nothing, and this is the most important line in the table.** The shipped relation loader is a batched second read in TypeScript (`sdks/db/src/collection/relations.ts`); `docs/reference/db.md` documents its v1 limitations as shipped. Exactly one join shape is required by the port, and it is on the dev tier: SQLite vector search JOINs a `vec0` shadow table on rowid. Building a general join grammar for this migration is building for no caller. |
| **Subqueries** | ABSENT as a node; ONE exists hard-coded inside the renderer's `write_bounded_target`, which emits `WHERE "id" IN (SELECT "id" FROM ... LIMIT $n FOR UPDATE)`. A caller cannot express `WHERE x IN (SELECT ...)`. | Two shapes. The bounded write target, which the renderer already has. And `$pull`, whose shipped lowering is a scalar subquery over `jsonb_array_elements` and which is the largest single node in the project. `$push` and `$addToSet` need a JSON node but not a subquery. |
| **Aggregation** | PARTIAL, and better than production where it is built. `AggregateFunc` is `{Count, Sum, Avg, Min, Max}`; grouping is checked at build time (every projected non-aggregate must be a grouping key, every order key too), and `HAVING` takes an `Operand::Aggregate` instead of a text fragment. | `$first` is missing and is documented in `db.md`. Its shipped lowering is `(array_agg(col ORDER BY ...))[1]` -- an ordered aggregate with an array subscript. That is a genuinely new node and it is the one aggregation shape that forces a shared-grammar decision. `AggregateRef.argument` is also an `Ident`, not a `FieldPath`, so an aggregate over a JSON path is unrepresentable. |
| **Ordering** | PRESENT and stronger than production: `OrderKey` carries an explicit `NullOrder`, keys are deduped and never sorted. | It needs the translation set *correctly*, which is a trap rather than a gap: `build_order_term_expr` spells null placement out on BOTH dialects today (`NULLS FIRST` when descending, `NULLS LAST` when ascending on PostgreSQL; a two-key `col IS NULL <dir>, col <dir>` emulation on SQLite). `OrderKey`'s three fields are `pub` with no `Default`, so getting the mapping backwards is a silently wrong sort with nothing to catch it. |
| **Pagination** | PRESENT for reads, and bound rather than interpolated, which is the improvement. `Search` has no OFFSET, matching production. | The problem is that the bound is *mandatory*. `render_select` emits `LIMIT $n OFFSET $m` outside every conditional. `build_count_with_soft_delete`, `build_distinct_with_soft_delete_with_dialect` and the no-`$limit` arm of `build_aggregate_with_result_columns` emit none. See section 6. |
| **Upsert** | ABSENT, and the write grammar refuses two of its three sub-shapes. There is no conflict-target node (`grep -n "ON CONFLICT\|Conflict\|Upsert" crates/zeroship-data-query-builder/src/write.rs` returns nothing); `Assignment` has no arm that reads the `excluded` pseudo-relation; and `Assignment::Arithmetic` writes the assigned column BARE, while the shipped upsert writes `"version" = COALESCE("app"."t"."version", 0) + 1`. | `upsert(doc, { conflictFields })` is a first-page `db.md` verb with one production caller. The bare form was a live `42702 column reference "version" is ambiguous` on every PostgreSQL upsert, fixed by the qualified COALESCE and caught by nothing because the executing upsert tests run on SQLite. **A faithful port through today's `Arithmetic` node reintroduces exactly that bug.** |
| **RETURNING** | PRESENT and stronger than production: `Returning` reuses `Projection`, has no star, and refuses an aggregate. The no-star rule matters -- `build_returning_expr`'s own doc records that a column-granted role cannot execute `SELECT *`. | It needs the `field_is_readable` filter it does not have. `implicit_read_projection_parts` skips `is_schema_metadata_key`, `SYSTEM_FIELD_NAMES` and `!field_is_readable(def)`; `Projection::rows` adds fields and never filters them (CONFIRMED: `grep -rn field_is_readable crates/zeroship-data-query-builder/src/` is empty). The projection is the only thing keeping a `readable: false` column out of a creator's hands, because `read_surface_columns`'s own doc says its row predicate is deliberately wider. |

**Not needed and deliberately not planned:** window functions, CTEs, a general expression grammar, lateral joins, unions, materialised views. `env.db` offers none of them and building any of them is work for no caller.

**The gap that is not in the table and blocks everything:** the execution seam. `BuiltQuery` is `{ sql: String, params: Vec<String> }` and every executor below it takes `params: &[&str]`. `RenderedSql` is `{ sql: String, params: Vec<Literal> }`. There is no adapter in any `src/` in the tree; the only one written is `bind_text` in `crates/zeroship-plugin-db/tests/search_ir_live.rs`. No plan can execute until that seam is typed.

## 3. The recommended migration

**One strategy: the per-operation ladder, with the renderer pair hoisted in front of it.**

The ladder comes from Design 1: migrate one creator-facing operation per commit, ordered by how much new shared grammar the operation forces you to invent, each commit deleting the string builder for the surface it just moved; keep the typed-parameter seam *late*, paid for by the write family that needs it, rather than early where it is throwaway work on a `BuiltQuery` you are about to delete. The hoist comes from Design 2 and is not optional: `exec_count` in `crates/zeroship-data-engine/src/exec.rs` dispatches ONE `BuiltQuery` to both backends through an exhaustive `match route.backend()`, so the first operation that renders through the IR needs BOTH renderers or it renders PostgreSQL text onto SQLite. Design 1's ladder scheduled the second `ValueFormat` implementor near the end and is unbuildable at its own first operation commit. The string-layer fixes at the front come from Survey A, and they are independent of the IR on purpose: if the migration slips, and a migration this size in a crate under active re-cut will slip, those must already be closed.

### Decisions that must be made before any commit in phase B

- **D1 (measurement, NEEDS-BUILD): does a deployed app's physical schema name carry hyphens?** `crates/zeroship-migrate-server/src/apply.rs` derives it through `app_derivation::schema_name(&AppId::from_uuid(app_id))`, and `AppId::from_uuid` sets its text from `uuid.to_string()`, which is hyphenated. Every engine fixture uses `app_...`, so this stays green through every unit test and fails on the first live app. Settle it with `PG_TEST_URL=<live dsn> cargo test -p zeroship-plugin-db --features test-helpers --test integration -- --test-threads=1` against a fixture whose app id is a hyphenated UUID.
- **D2 (owner decision, in writing): what happens to unbounded `updateMany` / `deleteMany`?** `build_update_many_with_system_fields`, `build_delete_many` and `build_soft_delete_many_with_system_fields` emit no LIMIT (CONFIRMED). `write_bounded_target` emits one unconditionally, and its own doc says that is what makes an unbounded write unrepresentable. Truncate at `MAX_ROW_LIMIT` and a 10,000-row `updateMany` writes 500 and reports success; refuse and a documented verb becomes an error. There is no third option and no commit should be written until this is answered.
- **D3 (owner decision): `$ilike` on SQLite, refuse or emulate?** Refusing breaks a documented `db.md` operator on the tier creators develop on. Emulating with `COLLATE NOCASE` is what `query.rs` does and what the renderer's own header says a backend must not do. One fact should inform it and NEEDS-BUILD to confirm on the shipped build: SQLite's `LIKE` is already ASCII case-insensitive by default, so `$like` and `$ilike` are already the same operator there, and refusing `ILike` breaks the documented operator while leaving the undocumented equivalence in place, which is the worst of the two outcomes.

- **7** is the hyphen. `IdentRole::Namespace` must admit `-` or no `DbPlan` can name the schema of an app whose id arrives as a bare UUID. Do it as a per-role charset, not a global relaxation: only `Namespace` gains the hyphen, and the reservation tables are untouched.

This commit adds the two hooks the SQLite delta needs and PostgreSQL already implies -- a row-lock suffix and a null-order spelling -- and must leave PostgreSQL output byte-identical, which the crate's opposite-permutation determinism fixtures already assert.
- **9** must also fix `ValueFormat::current_timestamp_expr`'s own doc, which says SQLite's is `CURRENT_TIMESTAMP`. Production uses the parenthesised `strftime('%Y-%m-%dT%H:%M:%fZ','now')` form, and `query.rs` records why: `CURRENT_TIMESTAMP` renders space-separated whole seconds, every millisecond bind renders ISO-8601 with a `T`, the columns carry no `COLLATE`, and 0x20 sorts before 0x54, so two spellings in one column invert same-day ordering. A renderer written from the trait doc corrupts ordering.
- **11** is three changes to one rule and they belong together: a `Projection::distinct_on` constructor that opts out of the platform union; a narrowing arm so an explicit `select` does not widen; and a `readable: false` filter so the union cannot surface a field the descriptor marks unreadable. The union rule's justification is that the read pipeline needs the system fields to strip or serve them; a distinct returns a value set with nothing to strip, and an explicit select is the creator asking for a narrower row.
- **18** is the one commit a re-cut partly wastes, because it edits trait signatures in `crates/zeroship-data-core/src/storage.rs`. Its enumeration gate must exist and go red under a deliberate mutation **before** the widening starts. Scope it to the CRUD executors and explicitly exclude `crates/zeroship-data-core/src/lock_policy.rs` and `crates/zeroship-data-engine/src/transaction/driver.rs`, which also carry `&[&str]` signatures and are session plumbing, not data plane.
- **25** deletes `BuiltQuery`, `build_where_with_dialect`, `build_field_condition_with_dialect`, `push_creator_value_bind`, `value_to_param`, `compose_where_with_soft_delete`, both probes, and the `SqlDialect` renderer trait's query methods. **The DDL family in `query.rs` survives this migration** -- but do not read that as "the file is permanent". `docs/proposals/2026-08-31-data-crate-shape.md` deletes `zeroship-schema`, and it can: `crates/zeroship-migrate-core/src/schema/query.rs` carries its own DDL builders, and the surviving non-migrate consumers of `zeroship-schema`'s copy are test fixtures. The ordering consequence is one-directional and worth stating: **the IR migration runs before that deletion**, because every builder ported is a builder the reshape does not have to rehome.
- **Not planned, and deliberately:** SC-3's ledger. Its gate arm asserts set equality against `zeroship-schema`'s export list, and the reshape deletes that crate; the 2026-09-03 engine extraction already moved the CRUD passes out of the crate it keys on. The completion criterion is `RenderedSql`'s privacy plus a shell gate over the data-plane roots, keyed off the ROOTS list in `tests/sync_claim_gate.sh` rather than hard-coded crate directories.

## 4. The passes

**The single most expensive misconception about this project is that the passes rewrite SQL text. They do not.** Every pass under `crates/zeroship-data-engine/src/crud/` walks a `serde_json::Value`. None of them composes a statement (CONFIRMED for `bytes_pass`, `encryption_pass`, `mask_pass`, `read_pipeline`, `system_fields_pass`, `protection_floor`, `write_pipeline` and `unmask`; the SQL-shaped hits in those files are doc comments and code below a `#[cfg(test)]` boundary). So "re-express the passes as IR transforms" is largely a non-task: the passes stay where they are, still walking JSON, and what changes is what consumes their output.

The concrete shape is one new module, `crates/zeroship-data-engine/src/crud/bind.rs`, holding four total functions. It lives in the engine and not in the IR crate because the IR crate has no `serde` dependency and that absence is load-bearing (`serialize_derive_is_structurally_impossible` in `tests/no_sql_text_escape_hatch.rs` asserts the manifest keeps it that way).

```
pub fn bind_filter(schema: &Value, filter: &Value)        -> Result<Predicate, DbError>;
pub fn bind_projection(schema: &Value, select: Option<&Value>) -> Result<Projection, DbError>;
pub fn bind_document(schema: &Value, doc: &Value)         -> Result<Vec<ColumnValue>, DbError>;
pub fn bind_patch(schema: &Value, patch: &Value)          -> Result<Vec<ColumnAssignment>, DbError>;
```

Those four are where every type decision currently spread across marker keys, dialect-conditional value rewrites and `push_creator_value_bind` goes to live. Then, pass by pass:

| Pass | What it does today | What it does after |
| --- | --- | --- |
| `bytes_pass` | Base64-encodes a `t.bytes()` value in place and inserts a sibling JSON key `__zsbin__<col>` that is not data but a message to the builder, read back by `collect_binary_bind_cols`. | Emits `WriteValue::Bind(Literal::Bytes(..))`. Still a JSON walk; only the output type changes. The placeholder spelling becomes `ValueFormat::bytes_placeholder`, a total function of the literal's type. |
| `encryption_pass` | Same mechanism: replaces the column with base64 ciphertext, inserts the same marker, and `strip_encryption_markers` removes them after the build. | `Literal::Bytes(ciphertext)`. **`strip_encryption_markers` is deleted outright** -- there is no marker to strip, because the type carries what the key was carrying. That is the whole argument for the IR in one function. |
| `mask_pass` | `relocate_masked_columns` moves the authoritative value to a `__zs_raw__<col>` JSON key and moves the marker with it. | Choosing the target `Ident` for a `ColumnValue` instead of renaming a JSON key. **This needs a new permission and it is the security-critical piece:** `COLUMN_RESERVATIONS` carries both `Reservation::Prefix("_")` and `Reservation::Prefix("__zs_")`, so `Ident::parse_as("__zs_raw__ssn", IdentRole::Column)` is refused twice over and the *legitimate* write is unrepresentable by the same fence that makes the attack unrepresentable. The right answer is `IdentRole::PlatformColumn`, whose reservation table permits `__zs_raw__` and nothing else, fed from `declared_raw_column`, which already validates the name against a written threat model. Argue it as *adding a permitted path to the raw column*, not as plumbing -- and note that `ProjectedField`'s three fields are all `pub` (CONFIRMED), so a struct literal already bypasses every constructor and the new role is a documented door, not the only one. |
| `system_fields_pass` | Mutates the doc, then populates `SystemFieldAutoBump`, a struct of five booleans and options that the text builder interprets into `"version" = "version" + 1`, `updated_at = NOW()` and `updated_by = $N`. | The five flags become three explicit `ColumnAssignment`s -- `Assignment::Arithmetic { Add, Literal::Int(1) }`, `Assignment::CurrentTimestamp`, `Assignment::Set(..)` -- and the three `skip_*` flags become the *absence* of the corresponding assignment. All three nodes exist. This is the cleanest win in the migration: "did this update bump the version" stops being a question about how a builder read a flag. Its two `sql.contains` assertions, which split generated SQL on `" VALUES "` and `" RETURNING "`, become assertions on `Insert::columns()` and `Insert::returning()`, which is strictly better because they stop depending on clause spelling. |
| `protection_floor` | Issues a live catalog read and refuses the write if the descriptor claims fewer protections than the catalog records. Composes nothing, mutates nothing. | **Unchanged.** It is a pre-plan guard and it stays one, running before the plan is built. |
| `read_pipeline` | Six post-execution stages over returned rows. Never sees a statement. | **Unchanged, with one coupling removed.** `plan_distinct` returns a tuple whose second element is a `distinct_reads_masked_sibling: bool` steering the decrypt stage away from a column holding a mask rather than ciphertext. That is a side channel carrying a fact the plan already knows; it becomes `Exposure` on the projected field, which is what `Exposure` is for. |
| `write_pipeline` | Composes no text but calls two builders, and one call is the text-surgery site: `build_write_target_probe` returns a `BuiltQuery` and the caller does `built.sql.push_str(" FOR UPDATE")`. | The probe stops pretending to be a `Select` and becomes its own bounded-target node, or `Select` gains a row-lock field. Either way the append disappears. It also needs `RowLimit` to hold `MAX_QUERY_LIMIT + 1`, because the probe asks for one past the ceiling to distinguish "exactly full" from "overflowing" and `RowLimit::new` refuses it (CONFIRMED). |
| `unmask` | Composes nothing. Its statements live in `backend_handle::read_raw_column_bytes` / `read_raw_column_text`, whose PostgreSQL arm interpolates with literal escaped quotes and **no `quote_ident`**, while the SQLite arm just below calls `sq.quote_ident`. | A `Select` whose projection names the raw column under `IdentRole::PlatformColumn`, with the `id` predicate as a bound `Literal`. The missing `quote_ident` dies by construction because there is no `&str` position left to forget it in. Commit 3 fixes it at the string layer first, because this is late in the ladder. |
| `maybe_lower_sqlite_boolean_*` (four helpers plus their `lower_boolean_*_with_schema` bodies) | **A pass no survey listed and a pure artefact of the untyped seam.** `lower_boolean_scalar` rewrites `Value::Bool(true)` into `Value::Number(1)` in the creator's own filter document, conditionally on the dialect, because a text parameter cannot carry a boolean. Its recursive filter walk re-handles `$and`/`$or`/`$not` and so duplicates the predicate grammar. | **Deleted.** `Literal::Bool` plus the dialect's value encoder. The creator's filter stops being rewritten in place and the dialect decision moves from "mutate the input document" to "encode a typed value". |
| `sqlite_blob_param` / `encode_sqlite_binary_scalar` | Produce the `"__zsbin_blob__:" + base64` sentinel. | **Deleted with the seam (commit 18), never before.** |

Read the shape of that table rather than its rows: three passes unchanged, four stop encoding a decision in a JSON key and start producing a typed node, and one pass plus two helper families are deleted because they exist only to compensate for the untyped seam. **None of it is "rewrite a text-editing pass as a plan-editing pass", because no such pass exists.**

One more thing the passes must not lose. `sanitize_app_actor` fences DB-3 at five sites spanning two crates since the engine extraction; count them with `grep -rn 'sanitize_app_actor(' crates/zeroship-data-engine/src crates/zeroship-plugin-db/src` over **both** roots and do not pipe it through `head`. No commit in this plan touches them, and any commit that appears to should be stopped.

## 5. The differential test

**Two oracles, not one, and a plan that funds only the first is worse than a plan that funds neither, because the first one reports green.**

The result-set oracle catches translator bugs. The clause oracle catches everything the IR changes about the statement *around* the predicate, and that is where the data loss is.

**Oracle 1: the filter corpus, compared on result sets.** Lives at `crates/zeroship-plugin-db/tests/filter_parity_live.rs`, a `[[test]]` target with `required-features = ["test-helpers"]`, modelled on `search_ir_live.rs`, whose header already states the pattern: both builders handed the same input, both statements run against the same rows through the same execution channel, the two results must match, with a control so agreement cannot be a fixture artefact, and nothing asserting on SQL text. Text comparison is *useless* for predicates, because canonicalisation reorders conjuncts and LIMIT/OFFSET become binds. The corpus covers the fourteen creator operators (`$and $or $not $eq $ne $gt $gte $lt $lte $in $nin $exists $like $ilike`) plus the desugarings `LiteralSet`'s non-empty-and-homogeneous rule forces: `$in: []`, `$nin: []`, a null member, a mixed-type member list. **It must run on both live backends, and it must have a mutation arm** -- delete one conjunct from the translator, re-run, the corpus must go red. A corpus that stays green under that mutation is measuring nothing, and a corpus of equality filters passes a broken translator.

**Oracle 2: the clause oracle, comparing rendered text.** Lives beside it as `crates/zeroship-plugin-db/tests/clause_parity.rs`, needs no database, and compares the *rendered statement's clause shape* against the shipped builder's for the same input: the projected column list against `implicit_read_projection_parts`, the presence or absence of a LIMIT clause, the presence or absence of a row lock, the null-order spelling on each dialect, and the RETURNING list. This is the oracle that catches the four regressions in section 6 that the corpus is blind to *by construction*, and the blindness is not fixable by making the corpus better:

- the write truncation is only observable above `MAX_ROW_LIMIT` matching rows, and a corpus built to exercise predicates inserts a handful of rows per case;
- the `readable: false` skip is only observable when the descriptor declares one, and `field_is_readable`'s own doc records that every hand-written test schema in this tree carries no flag at all, so the corpus is systematically drawn from the population that cannot see it;
- the column-grant executability change is only observable under a role narrowed enough to lack a grant on a system column, which is `run_plugin_db_live_suite.sh`'s `column_grants` target and not the corpus's;
- the distinct and aggregate truncation is only observable above `MAX_ROW_LIMIT` distinct values.

**If only one is fundable, fund the clause oracle.** A wrong predicate returns wrong rows a creator can see and report. A silently truncated `updateMany` returns success.

**Both harnesses are gated from the commit that creates them** -- added to `tests/run_plugin_db_live_suite.sh` with their own arms and floors per `tests/lib/gate_arms.sh`, and the suite's composed floor re-measured against a live server in the same commit.

**When they are deleted.** Oracle 1 dies in the same commit as `build_where_with_dialect` (commit 25), because after that there is no second implementation to differ from and the corpus degenerates into a fixture test. Oracle 2 does not die there: its subject is the clause shape, and after commit 25 it is re-pointed from "the IR versus the builder" to "the IR versus the documented contract" and kept, with its expectations written out rather than derived from the deleted builder. That re-pointing is part of commit 25, not a follow-up.

Two further gates every commit that touches a `zeroship-data-core` trait must run and that both designs omitted: `./tests/shipped_config_gate.sh`, which builds lib and bins on **default** features after the shipped binaries failed to build on main for a day while `--all-targets`, `--all-features`, `clippy_gate.sh` and every `cargo test` were green; and `./tests/clippy_gate.sh`, which no per-crate run invokes. And note that `cargo test -p zeroship-data-engine --lib` is feature-blind and says nothing about the encrypted-column paths commits 18 and 20 endanger.

## 6. What silently changes

Ordered by how quietly the change does damage. Every item is a difference in SQL behaviour or a query that becomes an error under a stricter IR.

**1. Unbounded writes become bounded, or become errors.** The headline, and D2 above. CONFIRMED that the shipped many-writes carry no LIMIT and that `write_bounded_target` emits one unconditionally. The encrypted `updateMany` arm does probe (`resolve_target_row_ids` with `MAX_QUERY_LIMIT + 1`, and `update_many_target_limit_exceeded` above the ceiling); the unencrypted arm in the same function calls the builder directly with no probe, and `deleteMany` has no probe on either arm. Fixing `RowLimit` to hold 501 fixes the *encrypted* arm's probe and does not give the unbounded arm a bound.

**2. Parameter typing stops being an encoding change and becomes a type-resolution change.** `query_text_params` in `libs/compio-postgres/src/query.rs` parses with an empty OID list and text format on an unnamed statement, so **PostgreSQL infers every parameter's type from position and implicit-casts the text into it**. `Client::query`/`query_raw` over `ToSql` send the Rust-derived OID instead. The shipped path depends on that inference for most of the column vocabulary in `def_to_pg_type`: a `json`/`object`/`array`/`union` field lands in `JSONB` today via inferred jsonb and becomes `text` (42883 on comparison, 42804 on insert); `calendarDate` in `DATE`, `inet` in `INET`, and a `date` column compared to an ISO *string* all become `text`; an `id` column filtered with a JS number becomes `int8` against a `TEXT` column. Loud on PostgreSQL. **Silent on SQLite, which has no type errors** -- a mismatched comparison returns the wrong rows and commits. The escape exists and the design closes it: `search_ir_live.rs`'s `bind_text` maps `&[Literal]` to `Vec<String>` with no dialect branch, and sending typed literals *in text format with unspecified OID* preserves inference. But `PostgresValueFormat::bytes_placeholder` returns a bare `$slot` and its doc says the `decode($N,'base64')::bytea` wrapper "is deleted, not moved", and a bytea cannot go as an untyped text param without a wrapper. **So the bytes decision and the loss of inference are one decision**, and both designs priced it as neither.

**3. The timestamp coercion fails loudly on PostgreSQL and silently on SQLite.** `push_creator_value_bind` emits `to_timestamp($n/1000.0)` on PostgreSQL and `strftime('%Y-%m-%dT%H:%M:%fZ', $n/1000.0, 'unixepoch')` on SQLite when the declared field is a creator timestamp and the value is a number. Note the trigger is `type == "date"`, not `"timestamp"`. On PostgreSQL `date` maps to `TIMESTAMPTZ` and an int8 bind gives 42883. On SQLite `date` maps to **TEXT** holding the ISO string; a bound parameter has no affinity, the column has TEXT affinity, so SQLite applies TEXT affinity to the parameter and compares `'2026-09-07T...'` against `'1757203200000'` lexicographically. Every ISO string sorts after every digit-leading string, so `$lt` matches nothing and `$gt` matches everything, with no error. `db.sessions.deleteMany({ expiresAt: { $lt: Date.now() } })` is a documented `db.md` shape: under this it deletes zero rows in `pnpm dev` and errors in production, which is the worst possible pairing. `Literal::TimestampMillis` (commit 10) is the fix and it must land before commit 12.

**4. Mandatory LIMIT truncates two unbounded reads.** `render_select` emits `LIMIT $n OFFSET $m` outside every conditional and `RowLimit::default()` is the maximum (CONFIRMED). `build_count_with_soft_delete` has no LIMIT and is harmless (one row either way). `build_distinct_with_soft_delete_with_dialect` has none, so `db.users.distinct("role")` returns at most `MAX_ROW_LIMIT` distinct values with no indication it was truncated, and a truncated value set is indistinguishable from a complete one. `build_aggregate_with_result_columns` emits a LIMIT only when the pipeline carries `$limit`, so group rows truncate the same way. `find` is safe: `effective_query_limit` always supplies one.

**5. Three accepted shapes become errors.** `validate_limit_bound` refuses only negatives and over-max, so `limit: 0`, `offset: 0` and `search.k = 0` are all accepted today. `RowLimit::new(0)` returns `LimitOutOfRange` and `search::Search` carries a `RowLimit` too.

**6. An explicit `select` widens from one column to eight, and the row shape changes.** `build_masked_aware_select_expr_with_unmask`'s explicit-select arm returns only the listed columns; `Projection::rows` unconditionally appends all seven platform fields and canonicalises. So `find({}, { select: ["email"] })` goes from a one-column statement to an eight-column one, and `read_surface_columns` admits the seven, so they reach the creator. It also changes what a column-granted role must hold: `build_returning_expr`'s own doc records that a role missing a grant on a projected column makes PostgreSQL reject the whole statement, not the column.

**7. `readable: false` stops being fenced.** `implicit_read_projection_parts` skips `!field_is_readable(def)`; `Projection::rows` has no analogue and only adds. `read_surface_columns`'s own doc says its row predicate is deliberately wider than what the projection emits and admits every declared key including one marked unreadable. **The projection is the only thing keeping such a column out of a creator's hands** (CONFIRMED: `field_is_readable` exists in `crates/zeroship-schema/src/query.rs` and has no occurrence anywhere in `crates/zeroship-data-query-builder/src/`). Commit 11 must carry this or commit 15 reopens it.

**8. `Ident` is stricter than the platform's own schema names, and this is a hard blocker.** `Ident::parse_as` runs `is_ascii_alphanumeric() || '_'` for **every** role; `SchemaName` allows `[A-Za-z0-9_-]` and its own test asserts a hyphenated UUID is legal (CONFIRMED, both read this pass). Every engine fixture uses `app_...`, so this stays green through every unit test and fails on the first live app. It sits ahead of every operation commit and is commit 7.

**9. `LiteralSet` is homogeneous and non-empty.** `$in: [10, 10.5]` on a number column splits Int/Float and hits `HeterogeneousSet`; `$in: ["a", 1]` likewise. Both work today, because `build_field_condition_with_dialect` binds each member through `push_creator_value_bind` with no type agreement required. And production handles all four empty/null quadrants explicitly for `$in` and mirrors them for `$nin`; the translator must reproduce all four or hit `EmptyLiteralSet`.

**10. Aggregate `$group` aliases become validated.** Today the alias is app-supplied and only `quote_ident`'d, while every *field* in the same function is validated. `IdentRole::Alias` refuses hyphens, spaces, non-ASCII, over-length names and the `__zs_` / `sqlite_` prefixes. Contained today, so this is a strictness change and not a fix, but it is a creator-visible refusal.

**11. Refusals move from build time to render time, changing the error code the SDK sees.** A nested `FieldPath` is refused by `write_path` as `RenderError::Unsupported`, not as `QueryError::InvalidFilter`. `QueryError::ReservedSystemFieldName` exists so the SDK can branch on a stable code; moving a refusal changes which code a creator gets.

**12. Null ordering: no behaviour change if and only if the mapping is set correctly.** `build_order_term_expr` spells null placement out on both dialects and both spellings produce the same placement. So set `NullOrder::Last` for ascending and `NullOrder::First` for descending and nothing changes. Getting it backwards is a silently wrong sort with nothing to catch it, and `OrderKey`'s fields are `pub` with no `Default`. Separately, `build_aggregate_order_by`'s doc still claims a masked column is lowered to its `_masked` sibling; the code validates and orders by the field's own column. Stale comment over live code, and a port written from it reintroduces a plaintext sort key.

**13. Bind numbering moves, and two callers pre-seed slots.** `build_vector_search` pushes the vector and `k` first and writes `$1::vector` twice plus `LIMIT $2`; `build_spatial_near` reserves four. `render_search` binds criterion, then projection, then filter, then limit last. Internally consistent, but the param vectors are not positionally comparable, so no test may compare them. There is also one cross-crate splice: `crates/zeroship-data-sqlite/src/lib.rs` calls `build_where_with_dialect` into a fresh vector and pastes the resulting `$1..$M` fragment into a SELECT it composes itself, formatting `k` and the query vector as literals. That splice is impossible once numbering belongs to the renderer, and it must be resolved inside commit 15.

**14. `$ilike` on SQLite.** Whatever D3 decides, note the fact that makes refusing the worse option: SQLite's `LIKE` is already ASCII case-insensitive by default (NEEDS-BUILD on the shipped build), so `$like` and `$ilike` are already the same operator on the dev tier.

**15. Prepared-statement plan quality, which is a non-issue today and becomes one later.** There is no statement cache on either backend: `libs/compio-postgres/src/config.rs` sets `statement_cache_capacity: 0` in `Default`, `query_text_params` uses the unnamed statement, and `crates/zeroship-data-sqlite/src/session.rs` uses `prepare`, not `prepare_cached`. So the migration invalidates no cache keys and the first request after deploy costs nothing extra. It also means binding LIMIT/OFFSET is free *because* PostgreSQL plans the unnamed statement at Bind with the actual values in hand. The day someone turns the cache on and switches to named statements, `LIMIT $n` becomes a generic-plan candidate where `LIMIT 10` was a constant. "Bind the limit" and "turn the cache on" are two halves of one change (NEEDS-BUILD: `EXPLAIN` a paginated read under a named statement after five executions).

**16. What does not change, so nobody looks for it.** The mask and encryption *protection point* does not move: no `crud/` pass composes SQL, so masking is decided in the same place before and after. The `storage.valueColumn` divergence is preserved rather than introduced -- `build_field_condition_with_dialect` never calls `value_column_for_field`, so the projection names the physical column and the filter names the logical one, and today they agree because the fold emits them equal. A `Select` that projects `"amount_v2" AS "amount"` and filters `"amount"` is a perfectly legal plan whose two `Ident`s the type system has no way to relate. **The IR does not fix that and commit 2 must.**

## 7. The first commit

**`refactor(dbplan)!: delete the masked-sibling projection and add the stored projection`**

Entirely inside `crates/zeroship-data-query-builder`. Delete `ProjectionSource::MaskedSibling`, `ProjectedField::masked`, `Ident::masked_sibling_of`, the `MASKED_SUFFIX` export from `lib.rs`, the two `ProjectionError` variants that serve them, the `MaskedSibling` arms in `SelectBuilder::build` and `write_projected_field`, and the two tests that pin the emitted text (`a_narrowed_projection_over_a_masked_column_renders_the_sibling` in `tests/projection_rules.rs` and `a_returning_list_over_a_masked_column_renders_the_sibling` in `tests/write_family.rs`).

Add, in the same commit, `ProjectedField::stored(physical: Ident, logical: Ident)`. After the storage flip the real divergent shape is `"<storage.valueColumn>" AS "<field>"`, and `ProjectedField::column` derives the alias *from* the name, so deleting `masked` without adding `stored` removes the only expressible form of physical/logical divergence -- and commit 15 needs it.

Keep `Reservation::Suffix("_masked")` in `COLUMN_RESERVATIONS`. Production still refuses `ssn_masked` as an inbound document key via `write_pipeline::validate_user_doc_keys`; deleting the node and the fence together opens a name production rejects.

**Why this one and not another.** It is the only change that is simultaneously required by every version of this plan, correct on its own terms whether or not the migration ever happens, and confined to a crate whose `[dependencies]` table is empty (CONFIRMED by reading the manifest) so no rename, re-cut or test-helpers change can reach it. The node renders `"<field>_masked"`, a column the storage flip stopped creating: the platform's sibling is `RAW_COLUMN_PREFIX = "__zs_raw__"`, `_masked` is a suffix `validate_field_name` refuses, and `grep -rn "_masked" db/migrations-ts/` returns nothing (CONFIRMED this pass). And `masked_sibling_of` is `Self(format!("{}{MASKED_SUFFIX}", parent.0))` -- the crate's only `Ident` constructed without `parse_as`, which means deleting it restores the "the only constructor validates" claim the entire design rests on.


That compiles the crate, runs the ten integration targets, and rules on the two literal floors and the `SOURCE_FILE_FLOOR` in `tests/no_sql_text_escape_hatch.rs`, which the deletion shrinks the crate against. The floors are literals and this is the run that says whether they still clear.
