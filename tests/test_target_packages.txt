# This list stood at 30 rows against 44 members for weeks. The note that used to
# sit here explained why it could not be fixed, in two successive versions, and
# BOTH are now obsolete:
#
#   - The first said `cargo test --workspace --no-run` could not be produced at

#   - The second said the command failed on ONE package, `zeroship-migrate-node`,
#     whose integration targets could not LINK (`undefined reference to
#     napi_create_function`), and concluded: "The census cannot be made correct
#     until either the CI command excludes that package on purpose or the addon
#     stops defaulting to `napi`. Decide that first."
#
# THAT QUESTION HAS A THIRD ANSWER, and it is the one that shipped. The addon
# KEEPS `napi` as a default feature - so src/bridge.rs is still compiled and
# type-checked by `cargo check --workspace` - and its test binaries link because
# `crates/zeroship-migrate-node/Cargo.toml` declares `napi` in
# `[dev-dependencies]` with the `dyn-symbols` feature, which resolves the Node
# ABI through libloading instead of static externs. Under resolver v3 that
# reaches test targets and NOT the shipped `--lib` build, so the `.node` is
# unchanged: tests/napi_symbol_shape_gate.sh holds the emitted cdylib's symbol
# shape (52 undefined `napi_*`, a defined `napi_register_module_v1`) and refuses
# the repair that would quietly change it.
#
# So the package now DECLARES test targets and BUILDS them, which is what arm 1
# wants, and no exclusion is needed anywhere.
#
