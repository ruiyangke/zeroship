# compio-redis red-team review

**BOTTOM LINE.** This client is **not safe to point at an untrusted or potentially-compromised Redis/Dragonfly server, and not safe to share across tenants on a multi-tenant worker.** It treats the server as fully trusted on a plaintext (no-TLS) link, and that trust is load-bearing for both memory safety and tenant isolation. The single worst exploitable issue is **CR-CLUSTER-1**: in cluster mode, one canned `-MOVED 40000 6.6.6.6:6379` reply panics the worker via an unchecked direct `Vec` index in `set_slot` — a deterministic, server-driven, unauthenticated-by-the-app worker crash with co-tenant blast radius, re-triggered on every retry. Tied for worst in *class* is the **pool's complete absence of a dirty/poison barrier** (RED-POOL-1 / REDIS-DESYNC-1): the `poison()` method the pool doc promises is **dead code with zero call sites**, so a timed-out or errored connection — with a pending/partial reply still on the wire — is returned to a **URL-keyed, cross-tenant** idle stack, and the next app (a different tenant) can read the previous app's KV reply. That is a confidentiality break of the exact per-app isolation the `{app_id}:` scoping is supposed to guarantee, reachable under ordinary load against a merely-slow server.

Overall risk posture: **high / do-not-ship-against-hostile-server.** Five confirmed criticals (one remote panic, three flavors of cross-tenant reply desync, one — counting both pool desync findings). The cluster redirect surface is **seriously exploitable** (remote panic + SSRF + credential exfiltration + persistent per-worker slot hijack, all from a single compromised/MITM'd node). The read path lacks the 64 MB frame cap the *sibling* `compio-postgres` driver already ships, so a single crafted reply OOM-kills the worker. The command-construction/auth surface is the one genuinely **hardened** area (length-prefixed RESP, no string-concat, redacted creds). The library's own header comment still claims cluster/MOVED-ASK is "out of scope" while shipping a 976-LOC exported `ClusterClient` that `plugin-kv` uses in production — i.e. the most dangerous code ships behind a comment saying it doesn't exist.

### Incidentally mitigated by the above
- **CR-CLUSTER-3 / RED-POOL-4 / REDIS-POOLGROW-1** (unbounded per-node pool-cache growth from server-spammed MOVED addresses): the SSRF allowlist (`b1c45621`) now refuses to create a pool for any non-allowlisted address, so a malicious node can no longer inflate the `pools` map with arbitrary addresses — growth is bounded by the (operator-derived) known-node set.
- **REDIS-TOPO-1** (slot-map poisoning by a single MOVED): a MOVED can now only repoint a slot to an *already-trusted* node (allowlist) and only to an in-range slot (CR-CLUSTER-1) — arbitrary-address poisoning is blocked.

### Remaining (out of the criticals+highs scope chosen for this pass — recommended follow-ups)
- **RED-POOL-3** (medium): no liveness/health check on checkout for a connection that died while *idle* (server-side close). The dirty barrier covers conns that errored *in use*, not idle-death; add a cheap probe or first-command reconnect-retry.
- **REDIS-INVARIANT-1** (low): `lib.rs` header still says cluster/MOVED-ASK/pipelining are "out of scope" while shipping `ClusterClient`. Rewrite to describe the shipped surface + trust model (and track TLS as a concrete gap).
- **REDIS-RECONNECT-1** (low) / **REDIS-CMD-1** (info): no reconnection on idle-death; `connect_tcp` skips AUTH/SELECT and the connect timeout (gate it `#[cfg(test)]`/`pub(crate)`).

## Confirmed exploitable findings

### CRITICAL

#### CR-CLUSTER-1 — Out-of-range MOVED/ASK slot panics the worker (remote crash via `set_slot` direct index)
- **Attacker / category:** malicious-server (or plaintext MITM) / dos-hang (remote panic).
- **Location:** `crates/compio-redis/src/cluster.rs:18` (parse), `:489`/`:491` (`set_slot` write), `:548` (MOVED arm).
- **Attack path:** A routed op (`env.kv.get` → `ClusterClient::get` → `send_to_slot`) gets a reply `-MOVED 40000 6.6.6.6:6379`. `parse_redirect` parses the slot as a bare `u16` (any value `0..=65535`) with **no `NUM_SLOTS` upper bound**, yielding `Error::Moved{slot:40000,…}`. The MOVED arm calls `self.set_slot(40000, …)`, which does `b.topology.slots[slot as usize] = …` — a **direct index** into a `Vec` that is exactly `NUM_SLOTS = 16384` long. `40000 >= 16384` → index-out-of-bounds panic. `MAX_REDIRECTS=2` does **not** gate it (first redirect: `0 >= 2` is false, so flow reaches `set_slot`).
- **Evidence:** `parse_redirect`: `let slot = it.next()?.parse::<u16>().ok()?;` (no bound). `set_slot`: `b.topology.slots[slot as usize] = Some(addr.to_string());` (direct index). Contrast the **safe** read path `node_for_slot`: `self.slots.get(slot as usize).and_then(...)`. Empirically reproduced: `index out of bounds: the len is 16384 but the index is 40000`. The existing test `parse_slot_out_of_u16_returns_none` only rejects `>65535` overflow, never in-`u16`-range-but-out-of-bounds values like 40000 — the gap is untested.
- **Containment:** No `catch_unwind` in `crates/worker` or `crates/plugin-kv`; no `panic = "abort"` in any profile (default unwind). The panic unwinds the per-request `!Send` future on the thread-per-core compio worker; every retry re-triggers it.
- **Impact:** Remote, app-unauthenticated, deterministic worker crash / request abort from one crafted reply, on a worker hosting many co-tenant apps. Sole precondition: cluster mode (`?cluster=true`), which is operator config (a deployment caveat, not a code guard) — the default single-node path never calls `set_slot`.
- **Fix:** Bound the slot before indexing — in `parse_redirect` reject `slot as usize >= NUM_SLOTS` (treat as a non-redirect server error), and/or make `set_slot` use a checked write (`if let Some(s) = b.topology.slots.get_mut(slot as usize) { *s = … }`). Mirror the safe `.get()` already used by `node_for_slot`.
- **Verify vote:** 2/2 confirmed (critical).

#### RED-POOL-1 — No connection reset/dirty barrier: timed-out/cancelled/errored connection returned to a URL-shared pool → cross-tenant response desync
- **Attacker / category:** co-tenant-state-bleed (or slow/hostile server, or packet-delaying network) / state-leak-cross-request.
- **Location:** `crates/compio-redis/src/pool.rs:160`/`:165` (Drop), `crates/compio-redis/src/client.rs:320`/`:337` (timeout + leftover-`rx`), `crates/plugin-kv/src/backend/redis.rs:142` (URL-only pool key).
- **Attack path:** App A issues `env.kv.get` → `pool.acquire()` + `send_recv(GET aKey)`; the command is **written to the socket**. Before a full reply decodes, the 5 s `cmd_timeout` fires (or the runtime drops A's in-flight future on isolate eviction/shutdown). A's reply is now pending — leftover bytes in the owned `self.rx` and/or the complete reply still in the kernel socket buffer. The temporary `PooledConn` drops; because `poisoned` is **always false** (never set anywhere), Drop pushes the **dirty** `Client` back onto `idle`. App B (different tenant, same worker) calls `env.kv.get(bKey)`; the pool is **keyed only by URL** (no `app_id`), so B pops the *same* `Client`, and `try_decode` returns App A's buffered reply. **B receives A's value for B's key**, and every subsequent op on that connection is shifted by one reply (persistent desync).
- **Evidence:** `pool.rs:160-169` Drop returns the conn unconditionally unless `poisoned`; `grep` for `poison` across `compio-redis` + `plugin-kv` returns **only** the definition (`pool.rs:153`), the doc comment, and `poisoned: false` init — **zero call sites**. `client.rs:337-341`: `self.rx` is owned by the `Client`, trimmed only via `split_to(consumed)` on a *successful* decode, so leftover/partial bytes survive into the next checkout. Pool key: `POOLS...get(&self.url)` — no `app_id`. `cleanup_cancelled_requests` does **not** abort in-flight op futures, so the live trigger is the 5 s timeout (always reachable) and isolate eviction/shutdown.
- **Impact:** Cross-request *and* cross-tenant exposure of KV values, existence bits, counters, TTLs, and `SCAN` key lists, plus persistent reply-stream desync (writes acked with the wrong reply). The `{app_id}:` scoping only chooses the server-side key; it cannot re-align a desynced reply stream. Triggerable by ordinary load against a slow server.
- **Fix:** Make poisoning automatic + add a dirty barrier instead of relying on the never-called `poison()`. Add a `dirty: bool` on `Client`, set it at the **start** of `send_recv_inner` (before write) and clear it only after a full frame is consumed; `PooledConn::drop` must refuse to return a `dirty` `Client` (drop it instead) — the start-of-send flag is the only thing readable at Drop time after a cancellation. Additionally assert `self.rx.is_empty()` on checkout and discard otherwise. Apply the same at the cluster acquire site.
- **Verify vote:** 2/2 confirmed (critical).

#### REDIS-DESYNC-1 — Timed-out/errored connection returned to pool unpoisoned with undrained buffer → cross-request reply confusion
- **Attacker / category:** malicious-server (or a single >5 s command) / state-leak-cross-request.
- **Location:** `crates/compio-redis/src/pool.rs:160`, `crates/compio-redis/src/client.rs:320`/`:337`, `crates/plugin-kv/src/backend/redis.rs:179`.
- **Attack path:** Worker checks out conn C, `send_recv` writes the command (it **is** on the wire), then awaits. The server delays past 5 s (or the deterministic hostile variant: appends an extra frame after a *successful* reply). `compio::time::timeout` drops the inner future; `self.rx` and/or the socket retain bytes. The error propagates via `?`; the `PooledConn` drops **unpoisoned** and C returns to idle. A later checkout of C runs a new command; `if !self.rx.is_empty() && try_decode(&self.rx)` returns the **leftover frame** (or the next read returns the previous command's late reply). Across tenants sharing the per-worker pool this is cross-app data exposure; it also corrupts `SET-NX` results → double-acquire of the lock primitive.
- **Evidence:** Same dead-`poison()` + leftover-`rx` mechanism as RED-POOL-1; cluster path identical (`cluster.rs:524-536` `conn.send_recv(...).await?` drops without poison). The two verifiers split on the timeout sub-mechanism: one holds that the cancelled io_uring read targets a separate `read_scratch` (so the rx-already-populated branch needs a *hostile server that appends type-matching trailing bytes*, plus the cancelled future leaves an empty `read_scratch` that wedges the next read with `UnexpectedEof`); the other holds the late reply lands in the kernel socket buffer of a still-open pooled fd and is read by the next command. **Both agree** the missing `rx.is_empty()` guard + non-poisoning drop is a real, reachable cross-request desync; the disagreement is only on the *easiest* trigger.
- **Impact:** Cross-request/cross-tenant response confusion: wrong key's value, stale `OK`/`NX` (breaking `SET-NX` locks), or mis-parsed frames. A confidentiality + integrity break, not just availability. The deterministic confidentiality break requires a hostile server emitting trailing bytes; the reliability/desync facet trips on any honest-server timeout under load.
- **Fix:** Self-poison the connection on any non-clean outcome (set a `dirty`/`broken` flag on `Client` whenever `send_recv` errors or leaves a partial frame; `PooledConn::drop` discards a dirty client). Assert `rx.is_empty()` at `send_recv` entry and discard if not. After cancellation, drain-to-boundary is impossible, so **discard** the connection on any timeout/error/partial-frame and let the pool open a fresh one.
- **Verify vote:** 2/2 confirmed; one verifier rated `high` (confidentiality break needs a hostile server, not a mere timeout), one `critical`. **Cross-tenant confidentiality break + lock-integrity break with no auth gate → critical retained.**

#### REDIS-READ-002 — Connection desync on decode-error/timeout: leftover `self.rx` bytes never drained or poisoned, pool recycles the conn → next command reads a stale, mis-attributed frame
- **Attacker / category:** malicious-server / protocol-desync.
- **Location:** `crates/compio-redis/src/client.rs:338` (`try_decode(&self.rx)?` returns before any `split_to`), `:321` (timeout drops inner future), `crates/compio-redis/src/pool.rs:160` (unpoisoned re-pool).
- **Attack path:** Two triggers leave the conn desynced then LIFO-recycled into the shared pool. **(A, the robust one) Pipelined extra frame:** the server sends a valid reply for command N **plus** a trailing frame in one segment (`+OK\r\n+OK\r\n`); `try_decode` consumes only N (`split_to(consumed)` removes only frame N), N **succeeds**, and the second frame stays in `self.rx`. **(B) Decode error / timeout:** an invalid frame-kind byte makes `try_decode(&self.rx)?` propagate `Err` **without** any `split_to`, or the 5 s timeout drops the inner future mid-read; either way bytes survive in `rx`. The next `acquire()` LIFO-pops the same conn (`pool.rs:107`), and `send_recv_inner`'s first action `if !self.rx.is_empty() && try_decode(&self.rx)?` returns the **leftover frame from N as the reply to M**. A seeded `+OK` makes a later `set_nx` falsely report lock success; a stale bulk makes a later `get` return another key's value.
- **Evidence:** Only `split_to` is on the success branch (`client.rs:340`); the `?` on `:338` returns `Err` without draining. `poison()` has **zero callers** (the `pool.rs:10` doc "On command error the guard is marked poisoned" is an unimplemented invariant). plugin-kv call sites (`get/set/del/incr/set_nx/...`) and `cluster.rs:536` only `.map_err(...)` and drop. The vendored decoder errors on a junk frame-type (`should_error_on_junk`), confirming the decode-error path.
- **Caveat:** PATH A *as originally framed* ("decode error with a valid `+OK` tail → fake success") is **not** achievable via the decode-error branch alone — a malformed *lead* frame blocks decode from ever advancing past offset 0, so the tail is never reached (that variant wedges the conn rather than silently faking success). The silent misattribution comes from the **pipelined-success-tail** variant and the **timeout** path, both real.
- **Impact:** Cross-command response confusion on a shared pooled connection, with a lock-integrity flavor (false `set_nx`) and cross-key data confusion within an app's KV namespace; the leftover bytes are attacker-steerable. The KV URL is operator-configured (not creator-reachable), so the trigger needs a malicious/compromised/MITM Redis or a malicious cluster-redirect target; an always-present reliability facet (honest-server timeout) broadens reachability.
- **Fix:** Wire poisoning into the pooled call path (a `with_conn` helper that poisons on `Err`) so callers can't forget; never reuse a connection whose `self.rx` is non-empty after a returned error.
- **Verify vote:** 2/2 confirmed (high). *Severity note: classed high by both verifiers; listed here under CRITICAL alongside its siblings only for the shared root cause — the standalone rating is high.*

### HIGH

#### REDIS-READ-001 / REDIS-OOM-1 — Unbounded read-buffer growth: a malicious server declares a giant bulk/array length and OOMs the worker (no frame-size cap, unlike compio-postgres)
- **Attacker / category:** malicious-server (compromised Redis/Dragonfly, plaintext `redis://` MITM, or any cluster node named by a MOVED/ASK redirect) / dos-oom.
- **Location:** `crates/compio-redis/src/client.rs:335`/`:354` (uncapped read loop), `crates/compio-redis/src/protocol/mod.rs:44` (decode wrapper), `redis-protocol-6.0.0/src/resp2/decode.rs:186` (`Incomplete → Ok(None)`).
- **Attack path:** Any KV op writes a command; the server replies with a bulk header declaring an enormous length (`$2000000000\r\n`) and streams filler, never sending the closing CRLF. Each loop iteration does `self.rx.extend_from_slice(&buf[..n])` with **no `rx.len()` ceiling and no declared-length check**. `redis-protocol`'s streaming `take(len)` returns `NomErr::Incomplete` mapped to `Ok(None)` ("keep reading") and **never pre-allocates** the target. The loop appends forever; the only backstop is the 5 s `cmd_timeout`, so the real bound is "bytes the server can push in 5 s" — multiple GB on a fast/local link. RSS climbs until the cgroup OOM-killer fires.
- **Evidence:** Read loop has no cap (only `READ_CHUNK=4096`, `pool.max_size`, `MAX_REDIRECTS`, and a `u16::MAX` slot check exist). The **sibling** `compio-postgres` caps this exact attack: `buf_stream.rs:61 MAX_MESSAGE_SIZE = 64*1024*1024` with `validate_length` + a `fill` guard whose comment names "a malformed/malicious server ... crafted 4-byte length field (e.g., 0xFFFFFFFF = 4 GB)." `compio-redis` has **no equivalent**. Secondary double-copy: `plugin-kv/src/backend/redis.rs:200` `String::from_utf8_lossy(&b).into_owned()` roughly doubles peak memory for sub-OOM large values.
- **Impact:** Remote, app-unauthenticated OOM/crash of a V8-per-thread worker — taking down all co-tenant apps — from a *single* crafted reply within the 5 s window. Not raised to critical only because the attacker must control/MITM the configured Redis backend or a cluster node, not arbitrary end-user input — the same bar the Postgres team set for the identical threat.
- **Fix:** Mirror `compio-postgres`: add a configurable `MAX_FRAME_SIZE`/`MAX_BUFFER` (e.g. 64 MB) enforced in `send_recv_inner` **before** reading more — bail with a protocol error if `self.rx.len()` would exceed the cap, and ideally peek the leading `$`/`*` length prefix and reject an over-cap declared length up front. Keep reads chunked so the cap bounds total buffered bytes. On exceed, discard the connection (do not return it to the pool).
- **Verify vote:** 4/4 confirmed across the two duplicate IDs (high).

#### CR-CLUSTER-2 / REDIS-SSRF-1 — SSRF + credential exfiltration: client connects (with the cluster password) to any IPv4:port a node names via MOVED/ASK or CLUSTER SLOTS
- **Attacker / category:** malicious-server (compromised node or no-TLS MITM) / ssrf.
- **Location:** `crates/compio-redis/src/cluster.rs:472`/`:480`/`:482` (`pool_for` connects), `:174` (SLOTS addr), `:18`/`:19` (MOVED addr verbatim), `:860` (`build_node_url` raw concat), `crates/compio-redis/src/client.rs:57` (IpAddr gate + AUTH replay).
- **Attack path:** The operator's seed URL is trusted, but the server at it is not. Two server-controlled channels feed a connect target: **(a)** `CLUSTER SLOTS` at bootstrap builds `addr = format!("{host}:{port}")` from server bytes with shape validated but **content never checked**; **(b)** a `-MOVED`/`-ASK` reply where `parse_redirect` takes `addr = it.next()?.to_string()` **verbatim**. `send_to_slot` → `pool_for(addr)` → `build_node_url(addr, password, db)` → `Pool::connect` → `Client::connect`, which TCP-connects to that address **and replays the cluster AUTH password to it**. `Client::connect` requires the host to parse as an `IpAddr` (DNS names and bracketed `[::1]` are rejected), but **any IP literal passes** — including `169.254.169.254:80` (cloud metadata), `127.0.0.1:5432` (local Postgres), `10.0.0.7:6379` (internal), and bare IPv6 incl. `::1`.
- **Evidence:** `pool_for` builds + connects with creds; MOVED addr verbatim; SLOTS host via `String::from_utf8_lossy`. `grep` for allowlist / `is_private` / `is_loopback` / `is_link_local` / `169.254` across the crate returns **nothing**. Empirically: `169.254.169.254:80`, `127.0.0.1:5432`, `10.0.0.5:6379`, `0.0.0.0:22`, `::1` all pass `IpAddr::parse`; the built URL is `redis://:HUNTER2@169.254.169.254:80` with the password present. `MAX_REDIRECTS=2` caps redirect *count*, not *target* (the first redirect already connects); bootstrap SLOTS has no cap at all.
- **Impact:** Every worker becomes an SSRF pivot to internal IPv4 (and IPv6 literal) services and the cloud metadata endpoint, and the Redis cluster password is exfiltrated to an attacker-chosen host; connect success/timeout/refused (5 s `connect_timeout`) is an internal port-scan oracle. High, not critical: the precondition is a malicious/MITM'd node, not an unauthenticated remote — but on a multi-tenant platform metadata-SSRF + credential exfil over a no-TLS link is solidly high.
- **Fix:** Restrict redirect/topology connect targets to an operator allowlist (only addresses present in the authoritative `CLUSTER SLOTS` topology from the trusted seed, or hosts in a configured CIDR). At minimum reject loopback, link-local (`169.254.0.0/16`, `fe80::/10`), unspecified, and any addr not matching a known cluster node. Parse `addr` through a strict host:port parser, not string concat. Prefer `rediss://` (TLS) + server identity pinning so MITM can't inject redirects.
- **Verify vote:** 4/4 confirmed across the two duplicate IDs (high).

#### RED-POOL-2 — Capacity (`busy`) counter leaked when `acquire()` is cancelled during `Client::connect` — no RAII guard, back-out only on the `Err` branch → pool bricks to permanent exhaustion (POOL-1 analog)
- **Attacker / category:** cancellation-fault (slow/unreachable Redis widens the window; an attacker who can force isolate eviction or wall-timeout mid-connect controls the trigger) / cancel-safety.
- **Location:** `crates/compio-redis/src/pool.rs:110` (`busy += 1`), `:125` (await `Client::connect`), `:129` (Err-only decrement), `:136` (PooledConn built only after success).
- **Attack path:** idle is empty → `acquire` takes the open-new branch: `inner.busy += 1` runs synchronously. Control reaches `Client::connect(&url).await` (the await point). The `acquire` future is **dropped here** (isolate eviction/shutdown drops in-flight op futures mid-connect). Neither the success arm nor the `Err(e) => { busy -= 1 }` back-out runs, and **no `PooledConn` was ever constructed** — the RAII decrement lives only in `PooledConn::drop`, which never runs. `busy` is now permanently incremented with no live connection behind it. After `max_size` (default 16) such cancelled-mid-connect acquires, `busy >= max_size` forever → every future `acquire` returns `Error::Pool("pool exhausted")` with **zero real connections in use**. The per-worker pool is bricked until process restart.
- **Evidence:** `pool.rs:110-118` reserves capacity with a bare counter, no guard; the only open-new-path decrement is the manual Err-only `self.inner.borrow_mut().busy -= 1`. There is no scope guard held across the await; the idle-pop branch is safe (no await between `busy += 1` and PooledConn construction). The **sibling** `compio-postgres` already fixed this exact class with a `PermitGuard` RAII (`compio-postgres/src/pool.rs:770-821`) whose doc literally names "POOL-1" and "a post-await `total -= 1` ... skipped on cancellation, leaking the permit forever." `compio-redis` is the un-fixed twin.
- **Impact:** Monotonic, irreversible per-worker capacity loss → permanent pool exhaustion for **all** apps sharing that Redis URL on the worker thread, requiring process restart. Needs no malicious server; ordinary timeouts/evictions during a connect window suffice.
- **Fix:** Reserve capacity with an RAII `BusyPermit` that increments `busy` on creation and decrements in its own `Drop`; hold it across `Client::connect().await` and convert/`disarm` it into the `PooledConn` only on success. Delete the manual `busy -= 1` Err back-out (the guard subsumes it). Apply the same at the cluster acquire site (`cluster.rs:524`). This is precisely the Postgres `PermitGuard` pattern.
- **Verify vote:** 2/2 confirmed (high, unchanged).

### MEDIUM

#### CR-CLUSTER-3 / RED-POOL-4 / REDIS-POOLGROW-1 — Unbounded per-node pool cache: a malicious node spamming distinct MOVED addrs exhausts memory/FDs
- **Attacker / category:** malicious-cluster-node / dos-oom (resource-leak).
- **Location:** `crates/compio-redis/src/cluster.rs:472`/`:483` (`pool_for` insert), `:421` (`pools: HashMap<NodeAddr, Pool>`), `:549`/`:536`.
- **Attack path:** `pool_for` inserts a freshly-created (and connection-warmed, `min_idle.max(1) >= 1`) `Pool` into the shared `Inner.pools` for every distinct addr it reaches, and **nothing ever removes entries** (no `remove`/`clear`/`retain`/evict anywhere). `MAX_REDIRECTS=2` caps *new pools per request* to 2, but each request can be redirected to a *fresh distinct* addr; `set_slot` permanently rewrites the slot owner so the next request to that slot restarts at the attacker addr. Over many requests, distinct `(addr → Pool)` entries — each with ≥1 live authenticated socket — accumulate without bound. The `ClusterClient` is cached per-worker (`CLUSTER_CLIENTS`, keyed only by sorted seeds) and shared across all apps, so the leak is worker-wide.
- **Evidence:** `pool_for` is insert-only; no eviction path in the file. Each `Pool::connect` warms ≥1 socket; the addr carries the cluster password (also an SSRF/credential-spray amplifier). Entries persist for the worker's lifetime; no periodic `CLUSTER SLOTS` refresh re-bounds the map.
- **Impact:** Slow-burn memory + file-descriptor exhaustion of the worker driven by a malicious node's redirect addresses, degrading/killing KV for all co-tenant apps. Accrues per-request rather than in one shot; gated on cluster mode + a malicious node / plaintext MITM.
- **Fix:** Bound `Inner.pools` (LRU-evict idle pools above a small multiple of the known topology size) and/or only ever create pools for addresses present in the authoritative topology. Tie pool lifetime to topology membership: drop a node's pool when it leaves the slot map. The allowlist from CR-CLUSTER-2 also blunts this.
- **Verify vote:** RED-POOL-4 & REDIS-POOLGROW-1 2/2 confirmed (medium). CR-CLUSTER-3 1/1 with verdict **severity-overstated → low**: the code defect is real, but the attacker must already have compromised a node inside the operator-trusted KV cluster (or MITM the operator-internal link), a position from which they can already read/corrupt all tenants' KV — so the marginal DoS is defense-in-depth, not a fresh medium exploit. **Consolidated severity: medium** (the dedup'd findings carry the higher rating; treat as a hardening fix).

#### REDIS-TOPO-1 — Slot map persistently poisoned by a single unvalidated MOVED; no topology re-fetch
- **Attacker / category:** malicious-server / topology-poisoning.
- **Location:** `crates/compio-redis/src/cluster.rs:489` (`set_slot` write), `:547` (MOVED arm).
- **Attack path:** On MOVED, `set_slot(s, new_addr)` writes the attacker address **directly into the shared `Rc<RefCell<Inner>>.topology.slots[slot]`** with no validation, no quorum, no cluster-membership check. Because the `ClusterClient` is cached per-worker and cloned across all requests on the thread, the mutation **persists** for every subsequent request hitting that slot — all future traffic for that slot routes to the attacker address (then chains to the SSRF in CR-CLUSTER-2). `CLUSTER SLOTS` runs **exactly once** at bootstrap; `set_slot` is the only post-bootstrap mutator, so a single poisoned slot is sticky for the worker's lifetime.
- **Evidence:** `set_slot` is an unconditional write of the server-supplied addr; the only post-bootstrap `.slots[...]` write. No code re-issues `CLUSTER SLOTS` after bootstrap (`CLUSTER`/`SLOTS` appears only at `cluster.rs:458`). Shared lifetime confirmed by `plugin-kv` caching + cloning the client. `MAX_REDIRECTS` bounds the per-command retry loop only; `set_slot` fires *before* the retry, and one MOVED (under the cap) already poisons.
- **Impact:** Persistent per-worker routing hijack of a slot (and thus an app's keys, since keys are `{app_id}`-hash-tagged to one slot) to an attacker-controlled endpoint, enabling silent data interception/forgery for that app across all subsequent requests until restart. Chains with the SSRF finding.
- **Fix:** Validate MOVED targets against allowlisted cluster membership before applying; treat repeated/oscillating MOVEDs as a signal to re-fetch authoritative topology via `CLUSTER SLOTS` from a trusted seed rather than trusting the redirect; add periodic/triggered topology refresh and reconcile `set_slot` writes against it.
- **Verify vote:** 1/1 confirmed (medium, unchanged).

#### RED-POOL-3 — No broken/dead-connection eviction or health check on checkout: an EOF/RST/half-closed connection is returned to idle and handed to the next caller
- **Attacker / category:** malicious-server (or normal Redis `timeout`/flaky network) / resource-leak.
- **Location:** `crates/compio-redis/src/pool.rs:107` (idle pop, no liveness probe), `:165` (unpoisoned re-pool), `crates/compio-redis/src/client.rs:348` (EOF), `crates/compio-redis/src/cluster.rs:536`.
- **Attack path:** The server closes the socket mid-reply or sends RST; `send_recv_inner` returns `Error::Io(UnexpectedEof)` (or an io error). The error propagates via `?`; the `PooledConn` drops; because `poisoned` is never set, Drop pushes the dead/half-closed `Client` back onto `idle`. `acquire`'s only idle-stack filter is the staleness age check — **no liveness/health probe**. The next caller pops the dead connection and its first write/read fails immediately. The cluster path is identical (`conn.send_recv(...).await?` propagates without poisoning), so a redirect-target node that resets connections poisons the per-addr pool with corpses.
- **Evidence:** `acquire`'s idle filter only checks staleness (`pool.rs:100-107`), never liveness; the EOF that should poison is returned via `?` and `PooledConn::drop` re-pools because `!self.poisoned` (same dead-code `poison()` as RED-POOL-1).
- **Impact:** Errored/dead connections are recycled instead of evicted, so a faulty or hostile server can keep handing the next caller a connection guaranteed to fail on first use; a transient blip leaves dead conns lingering in idle for up to `idle_timeout` (default 600 s). Lower severity than the desync findings because it **fails closed** (observable error, no silent wrong-reply). Minor overstatement in "every checkout fails fast" — when idle is empty `acquire` opens a fresh conn, so a single blip self-heals on the next acquire after the corpse is consumed.
- **Fix:** Couple to the RED-POOL-1 fix: any `send_recv` that returns an IO/protocol error must mark the `Client` dead so Drop discards it. Independently, treat a non-empty `self.rx` or a prior IO error as "do not return to pool." Optionally add a cheap liveness check or lazy reconnect on checkout so a popped-but-dead connection is transparently replaced.
- **Verify vote:** 1/1 confirmed (medium, unchanged).

#### CR-CLUSTER-5 — Cluster path never poisons a connection on error: timed-out/partial-frame conn returns to idle and desyncs the next command
- **Attacker / category:** malicious-server / protocol-desync.
- **Location:** `crates/compio-redis/src/cluster.rs:524`/`:536`, `crates/compio-redis/src/pool.rs:160`.
- **Attack path:** `send_to_slot` acquires a `PooledConn` and calls `conn.send_recv(cmd.clone()).await?`. A slow/hostile node trickles a partial frame so the 5 s timeout fires (or errors mid-decode); `send_recv` returns `Err` and `?` drops the conn **unpoisoned** (cluster path never calls `poison()`). Leftover/partial bytes remain in `Client.rx` (and the late reply may still arrive on the socket). The next checkout runs a different command but `try_decode` first returns the stale buffered frame — and since the `ClusterClient` is shared across co-tenant apps, command A and B can belong to different apps, so app B can receive app A's value.
- **Evidence:** `conn.send_recv(...).await?` drops with `poisoned=false`; Drop re-pools unless poisoned; `poison()` appears only in `pool.rs` with no callers. `send_recv_inner` only `split_to(consumed)` on success, so leftover bytes survive. The single-node path has the identical gap.
- **Impact:** Stale buffered replies leak across subsequent commands on a reused connection — including across apps sharing the per-worker `ClusterClient`. Rated **low** because the realistic trigger is a flaky/overloaded *operated* node (outside the tenant trust boundary), and the worst-case silent cross-app wrong-data requires leftover bytes that decode into a valid frame of the next command's shape; the fully attacker-steerable case needs the Redis node itself to be malicious. (This is the cluster-specific instance of the same root cause as RED-POOL-1 / REDIS-DESYNC-1 / REDIS-READ-002 — fixing the pool dirty barrier closes it.)
- **Fix:** On any `send_recv` error in `send_to_slot` (and the single-node callers), `poison()` the conn before/at drop, or have `send_recv_inner` clear `self.rx` / mark the `Client` dead on timeout/decode error.
- **Verify vote:** 1/1 confirmed (low).

#### REDIS-INVARIANT-1 — Stale/misleading security posture: `lib.rs` documents cluster + redirects as out-of-scope while shipping and exporting a 976-LOC `ClusterClient`
- **Attacker / category:** none / quality (assurance gap).
- **Location:** `crates/compio-redis/src/lib.rs:11` (out-of-scope claim), `:29` (`pub use cluster::ClusterClient;`), `crates/compio-redis/src/cluster.rs:1` (module doc that contradicts it).
- **Attack path:** Not attacker-triggered. `lib.rs:11-12` states the crate "deliberately doesn't do (out of scope for v1): Cluster mode (no MOVED/ASK redirection handling)" and "TLS." In reality `cluster.rs` is 976 LOC, `ClusterClient` is publicly re-exported, implements MOVED/ASK handling (`cluster.rs:537-559`), and is the **primary path** `plugin-kv` takes for any cluster URL. Anyone relying on the documented scope to bound the trust surface (e.g. assuming no server-controlled connect targets) is misled into skipping review of the most dangerous code.
- **Evidence:** `lib.rs:11-17` out-of-scope list vs. `cluster.rs:1-6` module doc ("Handles CLUSTER SLOTS topology, slot-to-node routing, and MOVED/ASK redirect retries"); `plugin-kv` `ClusterClient::connect(...)` confirms production use; `wc -l cluster.rs` = 976.
- **Impact:** Misleading security documentation: the redirect/SSRF/topology-poisoning surface (CR-CLUSTER-2, REDIS-TOPO-1, the pool-growth findings) ships behind a comment claiming it doesn't exist, raising the odds it goes unreviewed and un-hardened. Also flags TLS is still absent, leaving all of the above exploitable by a plaintext MITM.
- **Fix:** Update `lib.rs` to accurately describe the shipped surface and document the trust model (server-supplied redirect/topology addresses **are** connected to). Put the redirect/topology code under the same scrutiny as the wire parser; add the SSRF allowlist + buffer caps above. Track TLS as a known gap with a concrete plan, not a one-line "add when we need it."
- **Verify vote:** 1/1 confirmed (low, unchanged).

#### REDIS-RECONNECT-1 — No reconnection/health-check: a dead idle connection yields EOF with no retry, and `connect_tcp` bypasses AUTH
- **Attacker / category:** malicious-server (or normal idle-drop / RST) / correctness.
- **Location:** `crates/compio-redis/src/client.rs:348` (EOF, no reconnect), `crates/compio-redis/src/pool.rs:107` (no liveness check), `crates/compio-redis/src/client.rs:87` (`connect_tcp`).
- **Attack path:** An idle connection within `idle_timeout` is popped with no liveness check; the first command's `send_recv` reads `n==0` → `Err(UnexpectedEof)`, with **no reconnect/retry** — the error surfaces as a hard failure. Separately, `connect_tcp` is `pub`, applies **no connect timeout** and runs **no AUTH/SELECT**; if ever wired beyond tests it opens an unauthenticated, untimed connection.
- **Evidence:** `pool.rs:107` hands out the idle conn with no validation; `client.rs:348-352` returns `UnexpectedEof` on `n==0` with no reconnect; no retry wrapper in `plugin-kv`. `connect_tcp` (`client.rs:87-96`) does `TcpStream::connect(addr).await` with no timeout and no auth/select, marked "Dev-only" but `pub` — and repo-wide `grep` shows **zero callers** (dead code today, latent footgun).
- **Impact:** Availability papercut: transient command failures whenever the server reaps idle connections, with no automatic recovery; fails **closed** (error, not mis-route). `connect_tcp` is a latent footgun if misused.
- **Fix:** On `UnexpectedEof`/reset for the *first* command on a freshly-acquired pooled conn, transparently open a fresh connection and retry once (safe for idempotent reads). Make `connect_tcp` `#[cfg(test)]`/`pub(crate)`, or give it the same timeout/auth handling as `connect`.
- **Verify vote:** 1/1 confirmed (low).

#### REDIS-CMD-1 — `connect_tcp` bypasses AUTH/SELECT and has no connect timeout (dev-only constructor)
- **Attacker / category:** none / auth-info-leak (footgun).
- **Location:** `crates/compio-redis/src/client.rs:87-96`.
- **Attack path:** Not reachable by an external attacker on the production path. `Client::connect_tcp((ip, port))` returns a usable `Client` **without** AUTH/SELECT and **without** a connect timeout. If a future caller routed production traffic through it, it would (a) talk to a password-protected Redis unauthenticated — every command fails with `NOAUTH` (a self-inflicted DoS, **not** a bypass; Redis enforces auth server-side), and (b) hang indefinitely on a black-holed SYN (no 5 s cap, unlike `connect`). Production uses `Pool::connect` → `Client::connect`, so this is latent.
- **Evidence:** The constructor never calls `self.auth(..)`/`self.select(..)` and has no `timeout(...)` wrapper; the doc comment says "Dev-only constructor for in-process tests." Repo-wide `grep` returns only the definition (zero callers).
- **Impact:** None today (dev/test-only). Risk is purely the footgun: misuse → `NOAUTH` failures (no bypass) or an unbounded connect hang. No secret leak, no injection.
- **Fix:** Gate `connect_tcp` behind `#[cfg(test)]` (or a `test-util` feature), or add the same `timeout(DEFAULT_CONNECT_TIMEOUT, …)` wrapper used by `connect` and document the no-auth invariant as fixtures-only.
- **Verify vote:** 1/1 confirmed (info, unchanged).

## Prioritized hardening

Ordered; **must-fix first.**

1. **Pool dirty/poison barrier — STOP cross-tenant reply bleed (RED-POOL-1, REDIS-DESYNC-1, REDIS-READ-002, CR-CLUSTER-5, RED-POOL-3).** This is the single highest-leverage fix: it closes four confirmed cross-request/cross-tenant desync findings and the dead-connection-recycle bug at once. Add a `dirty`/`broken` flag on `Client`, **set it at the start of `send_recv_inner` before the write** and clear it only after a full frame is consumed; `PooledConn::drop` must **discard** (not re-pool) any `Client` that is dirty or whose `self.rx` is non-empty. The start-of-send flag is the only state readable at Drop time after a cancellation — relying on the never-called `poison()` cannot work. Assert `rx.is_empty()` on checkout. Wire this into a `with_conn` helper so callers can't forget. (Cross-tenant state bleed — call-out: confirmed.)

2. **Bound the MOVED/ASK slot before indexing — STOP the remote worker panic (CR-CLUSTER-1).** In `parse_redirect` reject `slot as usize >= NUM_SLOTS`; make `set_slot` a checked write (`.get_mut(...)`) mirroring the safe `node_for_slot`. One canned reply currently crashes the worker.

3. **Add a read-buffer / frame-size cap — STOP the single-reply OOM (REDIS-READ-001, REDIS-OOM-1).** Mirror compio-postgres's `MAX_MESSAGE_SIZE = 64 MB`: enforce in `send_recv_inner` *before* extending `self.rx`, peek the `$`/`*` length prefix and reject over-cap declarations up front (the decode crate reports oversized-valid as `Incomplete`, never an error), and discard the connection on exceed. (OOM-cap — call-out: confirmed; no cap exists today.)

4. **Allowlist redirect/topology connect targets — STOP SSRF + credential exfiltration + slot-hijack (CR-CLUSTER-2, REDIS-SSRF-1, REDIS-TOPO-1).** Only connect to addresses present in the authoritative `CLUSTER SLOTS` topology learned from the trusted seed (or a configured CIDR); reject loopback, link-local (`169.254.0.0/16`, `fe80::/10`), and unspecified addresses; validate MOVED targets against known membership before `set_slot` applies; add triggered topology re-fetch so a single bad MOVED can't stick. Adopt `rediss://` (TLS) + identity pinning to remove the plaintext-MITM precondition for *every* cluster finding. (SSRF/redirect-cap — call-out: confirmed.)

5. **RAII capacity permit — STOP the bricked-pool cancel-leak (RED-POOL-2).** Introduce a `BusyPermit` that increments `busy` on creation and decrements in its own `Drop`; hold it across `Client::connect().await` and convert/`disarm` it into the `PooledConn` only on success; delete the manual `busy -= 1` Err back-out. Apply at both the single-node (`pool.rs`) and cluster (`cluster.rs:524`) acquire sites. This is the exact `PermitGuard` pattern compio-postgres already shipped for POOL-1.

6. **Bound the per-node pool cache (CR-CLUSTER-3, RED-POOL-4, REDIS-POOLGROW-1).** Cap `Inner.pools` (LRU-evict above a small multiple of topology size) and only create pools for addresses in the authoritative topology; tie pool lifetime to slot-map membership. Largely subsumed by fix #4's allowlist.

7. **Reconnect/health on checkout (REDIS-RECONNECT-1, RED-POOL-3).** Transparently open a fresh connection + retry once on first-command EOF/reset for idempotent reads; optionally a cheap liveness probe for conns idle beyond a threshold.

8. **Constructor + documentation hygiene (REDIS-CMD-1, REDIS-INVARIANT-1).** Gate `connect_tcp` behind `#[cfg(test)]`/`pub(crate)` (or give it `connect`'s timeout + auth). Rewrite `lib.rs` to describe the *shipped* surface (cluster mode, MOVED/ASK handling) and its trust model (server-supplied addresses are connected to), and track TLS as a concrete planned gap rather than "add when we need it."
