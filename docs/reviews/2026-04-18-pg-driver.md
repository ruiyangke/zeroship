# `zeroship-pg` Driver Review & Fix Plan — 2026-04-18

## Verdict

**NOT production-ready.** Driver has real correctness bugs, not just polish issues.

| Dimension | Score | Notes |
|---|---|---|
| Correctness | 4/10 | Pool rollback path is dead code; waker leak; race on connection count; URL password bug |
| Robustness | 4/10 | Length-field DoS partially mitigated; no query cancellation; timeouts hardcoded |
| Security | 5/10 | TLS defaults OK; password percent-decode stub is a bug; no TCP keepalive |
| Performance | 5/10 | No statement cache; alloc-heavy encode; buffer copy on every flush |
| API design | 6/10 | Matches rust-postgres shape; binary format + unknown OIDs silently corrupts |

| Test coverage | 5/10 | Integration-only; critical pool concurrency paths untested |

## Ship-blocking Critical bugs

### C1. Pool's ROLLBACK-on-reuse path is unreachable dead code
**File:** `crates/pg/src/pool.rs:239-250, 306-311`
**Issue:** `get_inner` has a branch that runs `ROLLBACK` when `entry.conn.needs_rollback` is set on checkout. But `return_conn` evicts any connection with `status() != b'I'`. A dropped `Transaction` sets `needs_rollback=true` AND leaves status as `b'T'` (after BEGIN) or `b'E'` (after error), so the connection is evicted on return before the ROLLBACK branch can ever run. Confirmed by `integration.rs:179-181`: the test has to manually issue `ROLLBACK` and manually clear `needs_rollback` because the pool can't.
**Fix:** Keep the connection and issue ROLLBACK on return path for `needs_rollback` connections (async, so do it at next `get()` as currently intended, but DO NOT evict based on status alone — let `needs_rollback` OR `status==b'E'` flow into the rollback-or-evict logic). Or simpler: synchronously evict on Transaction drop and document that unrolled tx forfeits the connection. Recommend: on return, if `needs_rollback || status != b'I'`, keep entry for attempted recovery; on next get, attempt ROLLBACK; if it fails or status is still dirty, evict then. Clear `needs_rollback` after successful ROLLBACK.

### C2. Waiter queue leaks wakers → starvation under load
**File:** `crates/pg/src/pool.rs:287-296`
**Issue:** Two bugs in one `poll_fn`:
1. Every poll pushes a fresh `cx.waker().clone()` into `self.waiters`. No dedup check — a single waiter accumulates entries every time it's polled.
2. If the outer `timeout(...)` at `pool.rs:211` cancels the future, the waker stays in the queue. On next return, `return_conn` pops the dead waker and wakes nothing — live waiters starve until their own timeouts.

**Fix:** Replace the `poll_fn` with a small `Waiter` guard struct that holds a slot ID, registers its waker once (via `will_wake`), and unregisters from the queue on Drop. Store wakers in `VecDeque<Option<Waker>>` or `HashMap<WaiterId, Waker>` so drop can remove the slot.

### C3. `total` counter race can exceed `max_size`
**File:** `crates/pg/src/pool.rs:272-283, 373-378` (housekeeper)
**Issue:** Single-threaded, but with awaits. Multiple concurrent `get_inner` tasks all see `total < max`, all call `Conn::connect` (which yields on TCP+TLS handshake), all bump total on return — pool silently exceeds `max_size` by the number of racers. Same race in housekeeper refill.
**Fix:** Reserve the slot before the await: bump `total` first, decrement on connect failure.

### C4. URL password percent-decoding is a no-op stub
**File:** `crates/pg/src/conn.rs:931-933, 967-972`
**Issue:** `Url::password()` returns the **percent-encoded** form per WHATWG spec; the `percent_decode` helper is literally `s.to_string()`. Any password containing `@`, `:`, `/`, `%`, `#`, `?`, `&`, `=`, `+`, `[`, `]` fails SCRAM auth. Cloud providers auto-generate such passwords routinely.
**Fix:** Use `percent_encoding::percent_decode_str(p).decode_utf8_lossy().into_owned()`. Add `percent-encoding` to Cargo.toml.

### C5. Length-field DoS mitigation is weak
**File:** `crates/pg/src/stream.rs:63-82`, `crates/pg/src/conn.rs:978-995`
**Issue:** `MAX_MESSAGE_SIZE` check gates `min_bytes`, but `read_message` grows `min_bytes` by 1 per outer-loop iteration. An attacker-controlled server can force buffering up to 64 MB before the cap trips. With N connections that's 64 MB × N of RAM.
**Fix:** In `read_message`, after `stream.fill(5).await?`, peek the 4-byte length field (big-endian, bytes 1..5 of the buffer, excluding the 1-byte tag) and check `length + 1 > MAX_MESSAGE_SIZE` before filling further. Reject with a clean Protocol error. This makes the cap O(1) on malicious input.

### C6. Binary result format + unknown OID → silent data corruption
**File:** `crates/pg/src/lib.rs:115-119`, `crates/pg/src/conn.rs:380, 562`
**Issue:** `query_inner` requests **binary** format for all result columns (`std::iter::once(1i16)`). Row::try_get does `Type::from_oid(col.oid).unwrap_or(Type::TEXT)` — but the bytes are binary! For unknown OIDs (custom enum, domain, extension types like `citext`, `ltree`, `hstore`) this silently mis-decodes.
**Fix:** Track format code per column. Easiest: when RowDescription is parsed, also request per-column format in Bind. Request text format (`0`) for columns with unknown OID — but we don't know OID until after Bind. Better solution: for any OID not supported by `postgres-types`, return Err from `try_get`. Alternative: request text format for all results unconditionally (safer default, slightly slower). Recommend: request text format by default (set `std::iter::once(0i16)` in Bind), and keep binary as a future-opt-in when we have full type coverage.

## High-severity

### H1. `encode_params` type guessing is broken *(DEFERRED — larger refactor)*
**File:** `crates/pg/src/conn.rs:1047-1089`
Loops through 11 types. Only 11 supported — no JSONB, TIMESTAMPTZ, DATE, NUMERIC, arrays. 11 allocations per param. No param index in error.
**Fix (future):** After `Parse`, send `Describe(Statement)` to get param type OIDs, then encode with the authoritative type. For now: improve error message to include param index and attempted types; reduce alloc count.

### H2. No query cancellation protocol
**File:** `crates/pg/src/conn.rs:47-49, 276-279, 333-346`
`pid`/`secret` stored, never used. On query timeout the inner future is dropped but the server keeps executing — one stuck query can block VACUUM/migrations for a multi-tenant platform.
**Fix:** On timeout, open a second TCP connection and send `CancelRequest(pid, secret)` via `frontend::cancel_request`. Best-effort: don't error if cancel itself fails. Keep `Conn` still marked as poisoned.

### H3. No statement cache *(DEFERRED)*
Every query re-parses. rust-postgres caches prepared statements by SQL hash. Skip for this pass.

### H4. Buffer copies on every flush
**File:** `crates/pg/src/stream.rs:108-115`
`self.write_buf.split().freeze().to_vec()` — split → Bytes → copy to Vec. Pass the `BytesMut` directly (`AsyncWriteExt::write_all` accepts any IoBuf).
**Fix:** Pass `self.write_buf.split()` directly. Reclaim capacity with `write_buf.reserve()` afterwards.

### H5. Housekeeper never exits; Rc cycle
**File:** `crates/pg/src/pool.rs:194-203`
`Rc::clone(self)` into a detached spawn → task holds Rc<Pool> → Pool never drops → task never stops. Memory leak for every Pool created.
**Fix:** Store `Weak<Pool>` in the spawned task; `upgrade()` at each tick; break the loop when `upgrade()` returns None.

### H6. No TCP keepalive *(partial in Agent C)*
**File:** `crates/pg/src/conn.rs:85-93`
NAT boxes kill idle connections after 30–120s. 30s housekeeper + 500ms validation-bypass misses this.
**Fix:** After `TcpStream::connect`, set `SO_KEEPALIVE=1`, `TCP_KEEPIDLE=60`, `TCP_KEEPINTVL=30`, `TCP_KEEPCNT=3`. Use `socket2::SockRef::from(&tcp_stream)` or compio's socket options API if available.

### H7. Timeouts hardcoded at module level
**File:** `crates/pg/src/conn.rs:61, 65`
`CONNECT_TIMEOUT=10s`, `QUERY_TIMEOUT=30s` as const. Migrations, COPY, long admin tasks need minutes. No per-call override.
**Fix:** Add a `ConnectOptions` (or `ConnConfig`) struct with `connect_timeout`, `query_timeout`; default values = today's consts. Store on `Conn`. Add `Conn::with_query_timeout(dur)` setter for per-connection override. Plumb into `Pool::connect_with_config`.

### H8. `Error::Io(ErrorKind::TimedOut)` conflates I/O and app timeout
**File:** `crates/pg/src/conn.rs:341-344, 698-701`, `crates/pg/src/pool.rs:213-222`
Callers can't distinguish a server-down timeout from a slow-query timeout.
**Fix:** Add `Error::Timeout { kind: TimeoutKind, after: Duration }` with `enum TimeoutKind { Connect, Query, PoolAcquire }`. Keep `Error::Io` strictly for I/O errors.

### H9. `NotificationResponse` breaks every query path
**File:** `crates/pg/src/conn.rs:404-503, 583-683, 752-835`
Async NOTIFY from another session crashes the client. In every response loop, unmatched messages error with `"expected X, got NotificationResponse"`.
**Fix:** Add `backend::Message::NotificationResponse(_) => continue` alongside `NoticeResponse` in every read loop (also in `drain_until_ready`).

### H10. No MD5 password auth
**File:** `crates/pg/src/conn.rs:143-260`
Servers with `md5` in pg_hba.conf fail with "unexpected message during auth: AuthenticationMd5Password". MD5 is deprecated but still common on older PG / pgbouncer.
**Fix:** Handle `AuthenticationMd5Password(body)` using `postgres_protocol::authentication::md5_hash(user, password, salt)` and send via `frontend::password_message`.

## Medium-severity

### M1. `parse_command_tag` misreports SELECT row counts
**File:** `crates/pg/src/conn.rs:1124-1129`
`"SELECT 5"` parses to 5 "affected rows" — but SELECT affects zero rows. Integration test codifies this bug (`integration.rs:237`). Leaving as-is for back-compat but adding a comment that `execute()` on SELECT returns the number of rows returned, not affected.
**Fix:** Document the behavior; optionally parse `INSERT oid rows` / `UPDATE rows` / `DELETE rows` explicitly and return 0 for SELECT.

### M2. Housekeeper uses loose borrow scoping
**File:** `crates/pg/src/pool.rs:328-395`
Logs at line 388 take multiple fresh borrows. Works today; collect into locals before drop of `idle` borrow for defensive style.

### M3. Row column lookup is O(N)
**File:** `crates/pg/src/lib.rs:108-112, 141-143`
For wide tables × many `row.get()` calls, this is O(N²). Build a `HashMap<String, usize>` once per `Arc<Vec<Column>>`.
**Fix:** Extend `Row`/`Column` metadata to a shared `Columns { list: Vec<Column>, by_name: HashMap<String, usize> }` wrapped in `Arc`. Or keep `Vec<Column>` but include lookup map alongside.

### M5. `drain_until_ready` has no bound
**File:** `crates/pg/src/conn.rs:1133-1142`
Theoretical unbounded loop on a malicious server. Outer query timeout bounds it today; add a message count cap (e.g., 10_000) for defense in depth.

### M7. No connection warm-up
**File:** `crates/pg/src/pool.rs:164-184`
`Pool::connect` opens exactly 1 connection. `min_idle` is only populated after the first 30s housekeeper tick. First burst of traffic pays full connect latency.
**Fix:** In `connect_with_config`, open `config.min_idle.max(1)` connections upfront in parallel.

### M8. No retry/backoff on connect
**File:** `crates/pg/src/pool.rs:164-184, 373-385`
Docker ordering / DNS blips / brief PG restarts → permanent failure.
**Fix:** Optional: in `Pool::connect`, retry with exponential backoff (max 3 attempts, starting at 100ms). Leave `Conn::connect` single-shot.

### M11. Error fields dropped
**File:** `crates/pg/src/conn.rs:998-1031`
Only S/V, C, M captured. Position, Hint, Detail, Schema, Table, Column, Constraint — lost.
**Fix:** Extend `Error::Postgres` with optional `detail`, `hint`, `position`, `where_`, `schema`, `table`, `column`, `constraint`, `routine` fields. Or add a `fields: Vec<(u8, String)>` grab-bag.

### M12. No `ConnectOptions` for programmatic config
**File:** `crates/pg/src/conn.rs:75-307`
All config via URL parsing. Can't set keepalive/TLS/callbacks in code.
**Fix:** Add a `ConnectOptions` struct; `Conn::connect_with(options)`; `Pool::connect_with_options(options, config)`. URL form stays as sugar.
