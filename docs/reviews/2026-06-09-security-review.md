## 1. Method

Seventeen finder agents ran in parallel against the current working tree: 13 module-scoped finders (gateway, auth-idp, authz-engine, runtime, control-api, platform-billing, worker, bundle-cli, sandbox, data-plane, sdk-server, builder-and-client-sdks, infra) and 4 cross-cutting lenses (tenant-isolation, endpoint-authz, secrets-crypto, resource-bounds). All finders ran on model `fable`. Candidate findings were duplicate-clustered, then put through adversarial verification: **two independent refuters per critical/high finding and one per medium**; low-severity items were filed by their finder but not independently verified. Each finder also reconfirmed the status of items in the prior ledger, `docs/reviews/2026-06-03-codebase-security-audit.md` (4-pass codebase audit), and the auth-pipeline reviews (`2026-06-02-*`). This report synthesizes only what survived verification, plus the ledger-status deltas.

Result: **10 confirmed findings** (1 critical, 5 high, 4 medium), 0 disputed, 4 unverified lows, 4 refuted. No regressions were found in previously-applied fixes.

## 2. Executive summary

The runtime V8 sandbox boundary and the core crypto / JWT / auth-token surfaces are genuinely well-hardened, and every previously-applied fix that was re-checked (P2-A2 host allowlist, RT-1 fastcall signature, RT-7 eviction leak, P2-C1 transaction role funnel, P4-B-* WebSocket/SSE bounds, P4-C-F1 audit-retention GUC) holds with no regression. The headline new finding is **SEC-1 (critical): a cross-tenant database transaction hijack** — plugin-db keeps transaction/connection state in a single per-OS-thread `thread_local!` that is not keyed by app, but the worker multiplexes up to 200 mutually-untrusted isolates per thread, so one creator's `env.db.transaction(async () => await fetch(slow))` parks its dedicated tx connection in the shared slot and co-resident apps' `env.db.*` calls then execute inside that transaction snapshot under that role — overturning the 2026-06-03 audit's "tx path airtight" negative. Four high findings follow: a gateway/worker **path-normalization desync** that bypasses per-route auth via dot-segment variants (SEC-2), the auth service's per-IP rate limiter keyed on a **client-spoofable X-Forwarded-For** with unbounded auth-DB row growth (SEC-3), an **aggregation pipeline that returns masked-column plaintext** without the unmask audit path (SEC-4), and two defects in the previously-unreviewed `apps/zeroship-builder` server — a config-key typo that leaves all `projects.*` RPCs **unauthenticated** (SEC-5) and a dev-user fallback that **fails open in production**, collapsing every creator's sandbox onto one owner identity (SEC-6). Remaining risk concentrates in two seams: cross-tenant isolation inside shared per-thread/per-namespace state, and the builder application server, which had no coverage in the prior audit. The bulk of the legacy `crates/platform` crate was confirmed dead (excluded from the workspace, no binary, no dependents) and is not attacker-reachable.

## 3. Confirmed findings

### Critical

#### SEC-1 — Cross-tenant DB transaction hijack via thread-shared `ISOLATE_CTX` under multi-isolate-per-thread worker
- **File:** `crates/plugin-db/src/context.rs:738`
- **Sources:** lens-tenant-isolation
- **Description:** plugin-db keeps all per-isolate transaction/connection state in a single per-OS-thread `thread_local!` `ISOLATE_CTX` (context.rs:734-740). Its `tx_conn` slot (context.rs:189) is **not keyed by app_id**. The module assumes "one isolate per worker thread" (context.rs:24), but `crates/worker/src/cache.rs` multiplexes up to `max_isolates=200` (worker/main.rs:64) mutually-untrusted app isolates on each ntex worker thread, each driven by its own pump task. `pump_loop` exits the isolate and `.await`s pending ops with no thread-wide dispatch lock (runtime.rs:1054-1106), so any `.await` inside one app's work yields the thread to another app's pump. When app A runs `env.db.transaction(async () => { await fetch(slowUrl) })`, `exec_begin_or_savepoint` installs A's dedicated tx client into the shared slot under `SET LOCAL ROLE app_A` (transaction/mod.rs:351-368) and it stays parked for the whole `await`. A co-resident app B's `env.db.*` op then reads `has_tx()==true` (exec.rs:87) and runs B's SQL on A's transaction connection via `take_tx_client()` (exec.rs:90-101) — `run_sql` ignores the `app_id` it was passed on the tx path. B's queries execute inside A's transaction snapshot under A's role: B sees A's uncommitted rows for any commonly-readable object, B's writes are folded into A's COMMIT/ROLLBACK, and B's own `env.db.transaction()` hits `debug_assert!(_previous.is_none())` (transaction/mod.rs:369) — worker crash in debug, or in release `tx_conn.replace()` silently drops/aborts A's live transaction.
- **Attack:** A malicious creator deploys app A whose handler calls `env.db.transaction(async () => { await fetch('http://attacker/hang') })` and keeps the fetch hanging, holding the transaction (and the shared `tx_conn`) open indefinitely. Every other creator app whose isolate is resident on the same worker thread (near-certain at 200 isolates/thread) then has its `env.db.*` calls executed on A's dedicated connection: co-tenant reads run inside A's uncommitted snapshot under A's role, co-tenant writes join A's transaction, and any co-tenant `env.db.transaction()` either crashes the shared worker (debug) or silently aborts A's transaction (release). One deployed app thus achieves cross-tenant data-snapshot read, cross-tenant write-integrity violation, and a persistent DB denial-of-service against all ~199 co-resident tenants.
- **Suggested fix:** Move the transaction/connection state (`tx_conn`, `savepoint_depth`, `pending_emits`, `mig_lock`) out of the crate-wide thread-local into per-isolate state keyed by app_id (e.g. stash on the runtime's per-isolate slot the worker already owns), OR stamp the owning app_id onto `tx_conn` and have `has_tx()`/`take_tx_client()`/`transaction_dispatch` treat a parked tx belonging to a different app_id as "no active tx for me". The single-tenant `serve`/bench path is unaffected either way.
- **Verifier note:** Both refuters confirmed at high confidence after tracing the full path; the pump drops its runtime borrow before awaiting and DB op futures run with no borrow held across `.await`, so the interleave is real. Explicitly **not** a ledger duplicate — the 2026-06-03 audit's "tx path airtight" verdict (P2-C1) was scoped to the pool-checkin/`SET LOCAL` leak axis, not the shared thread-local slot read. Calibration: cross-*different*-app uncommitted-read bleed may be bounded to permission-denied by per-app role/schema grants, but the same-app two-isolate snapshot bleed, the cross-tenant write-integrity violation, and the unconditional worker-crash/tx-abort DoS all land — critical stands.

### High

#### SEC-2 — Gateway resource auth-policy matching is not path-normalized while the worker re-parses with WHATWG URL → per-route auth bypass
- **File:** `crates/gateway/src/compiled.rs:146`
- **Sources:** gateway
- **Description:** The gateway is the sole authz enforcement point (audit P2-B3: app-layer authz does not exist). For non-RPC (SSR/fetch) requests it resolves per-resource policy by matching the **raw** request path: `PathMatcher::find` (compiled.rs:146) does an exact `literals.get(path)` then `match_glob_simple` (compiled.rs:160), which only `path.trim_start_matches('/').split('/')` — it does **not** resolve `.`/`..` dot-segments, collapse `//`, or strip a trailing `/`. The matched policy's `auth` is enforced in `resolve_auth`. The gateway then forwards the **same raw** `tail` to the worker as `format!("{scheme}://{host}/{tail}")` (dispatch.rs:1216). The worker/app re-parses with `new URL(req.url).pathname`, and WHATWG parsing collapses `/foo/../`, `/./`, and `%2e`/`%2E` segments. So `/api/foo/../admin`, `/api/./admin`, and `/api/%2e/admin` carry 3-4 segments at the gateway (never matching the 2-segment literal `/api/admin` the creator gated `auth:"user"`), fall through to the permissive catchall glob (Anon) that every SPA/SSR app declares, get forwarded, and there normalize to `/api/admin` — running the protected handler with the gateway having applied Anon auth. RPC (`/__zeroship/v1/<id>`) is **not** affected: strip+exact-index miss returns None and the gateway 404s before forwarding (dispatch.rs:439).
- **Attack:** A malicious unauthenticated end-user sends `GET https://victimapp.zeroship.ai/api/foo/../admin` (or `/api/%2e/admin`) to any creator app that declares a catchall/SSR resource forwarding `*`/glob to the worker (universal for SPA/SSR) **and** has a stricter sub-route (e.g. `/api/admin` with `auth:"user"`) whose handler routes on `new URL(req.url).pathname`. The gateway matches the Anon catchall, skips the `user` gate, forwards to the worker; the worker normalizes to `/api/admin`, runs the admin handler, and returns admin data — a full per-route auth bypass against the platform's single authz checkpoint.
- **Suggested fix:** Canonicalize the request path **before** resource matching: resolve `.`/`..`/`%2e` dot-segments, collapse repeated `/`, decide a single trailing-slash policy — then match the resource tree **and** derive the worker-forwarded URL from that same canonical form. Reject (400) any request whose normalized form differs from the raw form on a security-relevant resource rather than silently forwarding.
- **Verifier note:** Both refuters confirmed at high confidence; one empirically reproduced the gateway-side half (`CompiledManifest::lookup_resource_key` returns the ANON `/[...path]` glob for `/api/foo/../admin`, `/api/./admin`, `/api/admin/`). ntex-router 1.0.0 does not collapse dot-segments and there is no NormalizePath middleware. Reach caveat: the bare `*` root does not dispatch by URL, so the bug requires an app declaring an explicit URL-glob catchall plus a stricter literal sub-route (a legitimate, expressible shape) — not literally every app, but the idiomatic SSR shape.

#### SEC-3 — Auth-service per-IP rate limits keyed on a client-spoofable X-Forwarded-For (gateway forwards it unscrubbed, ungated by `trust_proxy`)
- **File:** `crates/auth/src/identity/credentials.rs:118`
- **Sources:** auth-idp
- **Description:** The auth service deliberately keys its DB-backed leaky-bucket rate limits on the forwarded client IP: `client_ip` (headers.rs:160) = `req.connection_info().remote()` → buckets `login:ip:{ip}` (credentials.rs:118), `magic:ip:{ip}`/`magic_complete:{ip}` (magic.rs), `signup_ip:{ip}` (signup.rs:133), `forgot_ip:{ip}` (forgot.rs:94). ntex 3.7.2 `ConnectionInfo::remote()` returns the `Forwarded: for=` directive or the leftmost `X-Forwarded-For` token **verbatim** with no IP-format validation and **no trust gate**. The fronting gateway routes `auth.zeroship.ai` via `route_auth_host` (dispatch.rs:276-277, 374-378), which copies the **entire** inbound header set — including a client-supplied `X-Forwarded-For`/`Forwarded` — to the auth upstream with no reserved-header scrub, and the auth-host path is reached **before** any gateway rate-limiter. Crucially this is **not** gated by the gateway's `trust_proxy` flag (the GW-3 mitigation), so it works at the default `trust_proxy=false`. Two impacts: (1) the per-IP buckets are fully bypassable by rotating XFF, defeating the credential-stuffing/abuse defense across many accounts and email-amplification across many victims; (2) `zeroship.rate_limits` is `bucket_key TEXT PRIMARY KEY` with no TTL/eviction (0002_auth.sql:107) and no GC cron, while `store::ratelimit::consume` does an INSERT-on-conflict per attempt, so every forged IP creates a permanent row → storage-exhaustion + write-load DoS on the shared multi-tenant auth Postgres.
- **Attack:** An unauthenticated end-user sends requests to `https://auth.zeroship.ai/login` (and `/signup`, `/magic/start`, `/forgot`) each carrying a fresh forged `X-Forwarded-For: <random-N>` or `Forwarded: for=<random-N>`. The gateway proxies them verbatim; the auth service lands each in a brand-new per-IP bucket that never throttles, and inserts an unbounded number of permanent rows into `zeroship.rate_limits`, exhausting auth-DB storage and write capacity and degrading login for every tenant.
- **Suggested fix:** On the gateway auth-host path, strip inbound `X-Forwarded-For`/`Forwarded`/`X-Real-IP` and inject a single authoritative client-IP header derived from the real peer (mirror the worker-dispatch reserved-header scrub). In the auth service, parse XFF right-to-left by a configured trusted-hop count (or read the gateway's injected authoritative header), and validate the value parses as an IP before using it as a bucket key. Add a TTL/size bound + periodic GC to `zeroship.rate_limits`.
- **Verifier note:** Both refuters confirmed at high confidence against the vendored ntex source; the auth crate has zero trust/proxy config, so the bypass works at `trust_proxy=false`, distinguishing it from the trust_proxy-gated GW-3 and the in-memory GW-4. **Not** a ledger duplicate: GW-14 (LOW) recorded only the raw header forwarding and never connected it to the auth limiter's XFF-keyed buckets, the unbounded DB rows, or the trust_proxy-ungated reachability. Calibration: the "defeats the SOLE defense → unbounded single-account guessing" framing is overstated (the IP-independent `login:email` 10/h bucket plus `record_login_failure` lockout cap single-account guessing), but cross-account spray, forgot/magic email-amplification, and the persistent shared-DB row growth remain genuinely unbounded — HIGH is appropriate.

#### SEC-4 — Aggregation pipeline bypasses field masking and returns masked-column plaintext (un-audited)
- **File:** `crates/plugin-db/src/query.rs:3892`
- **Sources:** data-plane
- **Description:** For a mask-only column (`.mask({...})` without `.encrypted()`), plaintext is stored in the base column `<col>` and `<col>_masked` holds the masked string (mask_pass.rs:104-150). The normal read path projects `"<col>_masked" AS "<col>"`, and `build_distinct_with_soft_delete_with_dialect` was hardened to do the same substitution (query.rs:4127-4133 via `column_is_masked`). The aggregate builder was **not**: `build_aggregate_with_soft_delete_with_dialect` lowers `$group.by` (query.rs:3891-3895) and `$sum/$avg/$min/$max/$first` (query.rs:3944-3994) with a bare `quote_ident(field)` against the **base plaintext column** — no sibling substitution. Result rows flow through `read_pipeline::apply` → `mask_pass::wrap_row_on_read`, which does **not** re-apply the mask transform: with no `<col>_masked` sibling selected, it wraps the parent slot value verbatim (mask_pass.rs:442-448), so `$group.by:"ssn"` yields `{ssn: MaskedValue{masked: <PLAINTEXT>}}` whose `.masked` getter returns plaintext. Worse, for an alias like `{by:"tenant", top:{$max:"ssn"}}`, `aggregate_group_fields` (crud/mod.rs:480-502) returns only the `by` field, so `SchemaFieldScope::Only(["tenant"])` drops `ssn`, `schema_has_masked_columns` is false, wrapping is skipped entirely, and the alias column returns **raw plaintext with no wrapper**. `dispatch_aggregate` always passes `unmask_columns: &[]` (crud/mod.rs:1754), so this never touches the unmask-authorization/audit path that `.unmask()` requires after the DB-3 fix. `$having`/`$sort` on a masked column are weaker oracles of the same root cause.
- **Attack:** A creator app whose schema masks end-user PII/SPI/PHI/PCI (e.g. `ssn`, `email`) so handler code and UIs only see the masked form calls `env.db.users.aggregate([{ $group: { by: "ssn" } }])` (or `[{ $group: { by: "region", maxSsn: { $max: "ssn" } } }]`). The platform returns plaintext SSN values — every distinct value via `$group.by`, or the lexicographic extreme via `$min`/`$max` — directly to the app's JS, with no `.unmask()` call, no actor authorization, and no `audit_events` entry. The app exfiltrates its own end-users' regulated plaintext PII through the path the masking control was designed to withhold it from.
- **Suggested fix:** In the aggregate builder, treat masked columns exactly as `build_distinct` does: substitute the `<field>_masked` sibling for `$group.by`/`$sum`/`$avg`/`$min`/`$max`/`$first`/`$sort` masked fields, or reject with a typed `aggregate_on_masked_column` error unless an authorized unmask is in play. Harden `mask_pass::wrap_row_on_read` to not fall back to the parent slot as if already masked, and include aggregate-alias columns in the masking scope. Add a regression test asserting `aggregate`/`$group.by`/`$max` on a mask-only column never returns plaintext.
- **Verifier note:** Both refuters confirmed at high confidence after end-to-end trace (storage model → SQL → read pipeline → wrap); the existing guard test only rejects the *sibling* name `ssn_masked`, never the base column. This is genuinely new surface the 5-lane/4-pass plugin-db reviews missed — they verified masking on the `find`/`distinct` paths but the aggregate builder was never hardened. The threat model (`unmask.rs:285`: "app JS reading its own PII/PHI/PCI at will") is exactly what DB-3 defends against; own-app scope keeps it HIGH not critical.

#### SEC-5 — Auth + rate-limit bypass on all `projects.*` builder RPC procedures (config key `rpc:apps` vs wireIds `projects.*`)
- **File:** `apps/zeroship-builder/src/server/config.ts:22`
- **Sources:** builder-and-client-sdks
- **Description:** config.ts declares `"rpc:apps": { auth: "user", rateLimit: { rpm: 600 } }` (a relic of when the module was `apps.ts`). But the actual procedures in `projects.ts` carry wireIds `projects.listProjects/getProject/createProject/deleteProject/archiveProject/unarchiveProject/getEnv/setEnv/deleteEnv/getLogs` (projects.ts:82-270), declared via `action()/mutation()` with only `{id}`, no `auth`/`rateLimit`. The vite-plugin auto-derives one resource per procedure keyed `rpc:<wireId>` (manifest.ts:667), pulling auth from the procedure's own (empty) config. The merge (manifest.ts:738) leaves `rpc:apps` an orphan matching no procedure, and `rpc:projects.*` keep auth=undefined. `Manifest::validate` only rejects resources whose auth is *explicitly* `Some(Anon)` without `publicly_accessible` (manifest.rs:455), so auth-less entries pass. `resolve_effective_policy` then defaults `auth = AuthLevel::Anon`, `rate_limit=None` (compiled.rs:328) because neither `rpc:projects` nor `*` exists in the chain, and `resolve_auth` returns `Allowed` for Anon regardless of session (auth.rs:399). Net: all 10 `projects.*` procedures are reachable **unauthenticated** and without the intended 600rpm cap. Sibling namespaces (sandbox/agents/chat/wizard/pm/sre) are not drifted and remain protected.
- **Attack:** An unauthenticated attacker POSTs directly to `/<builder-host>/__zeroship/v1/projects.setEnv` / `projects.getEnv` / `projects.getLogs` / `projects.createProject` (no cookie, no session). Effects: (a) unauthenticated, unthrottled access to the project-management + sandbox-env + dev-log surface; (b) `createProject` spam rewrites the shared `projects:<DEV_SANDBOX_USER_ID>` KV list each call, filling it to the 256KiB value cap and wedging the dev/anon registry; (c) via the sibling dev-fallback bug (SEC-6), `getEnv({appId})`/`setEnv({appId,key,value})` resolve the sandbox owner to the constant `DEV_SANDBOX_USER_ID` and read/write the `.env` of sandbox `(DEV_SANDBOX_USER_ID, appId)` — so an anonymous caller with a victim's projectId reads/overwrites that preview sandbox's `.env` secrets.
- **Suggested fix:** Rename `"rpc:apps"` → `"rpc:projects"` in config.ts (keeping auth:user + rateLimit). Add a `"*": { auth: "user" }` fail-closed root for the app, and/or add a manifest-validator rule that rejects any RPC procedure whose effective auth resolves to Anon without an explicit `publicly_accessible: true` (close the gap where absent-auth silently means anon).
- **Verifier note:** Both refuters traced the full chain at high confidence: the derived `rpc:projects.*` entries carry auth=undefined, both JS and Rust validators only reject *explicit* anon, the inheritance chain finds neither `rpc:projects` nor `*`, and `resolve_auth_inner` returns Allowed for Anon. The builder is a gateway-fronted zeroship app, so the public `/__zeroship/v1/` surface is reachable by external clients. This surface had no coverage in the 2026-06-03 audit.

#### SEC-6 — Dev-user fallback fails open in production → every builder user's sandbox collapses onto one owner identity
- **File:** `apps/zeroship-builder/src/server/internal/sandbox-backend.ts:162`
- **Sources:** builder-and-client-sdks
- **Description:** `resolveSandboxUserId` determines the sandbox owner for every file/exec/preview/env operation. It calls `typedUserIdOrNull(currentUser().id)`, which **requires** a `usr_`-prefixed typed id (sandbox-backend.ts:144,151) and otherwise returns null when `isLocalDevRuntime()` is true; `resolveSandboxUserId` then falls through to a single constant `DEV_SANDBOX_USER_ID` (sandbox-backend.ts:127,171). Two facts make this fire in production: (1) the gateway forwards the per-app **pairwise** subject as the user id — `WorkerUser.id = claims.sub` is a `pws_…` value, never `usr_…` (gateway/router/auth.rs:1091; session_token.rs), so the `usr_` check always fails; (2) `isLocalDevRuntime()` keys on `process.env.NODE_ENV !== "production"` (and a `ZEROSHIP_BUILDER_DISABLE_DEV_USER` kill-switch that is set nowhere), but the V8 runtime never injects NODE_ENV (init.rs env-build carries only worker/app vars; the console seed `CONSOLE_RUNTIME_ENV` writes only OPENAI_API_KEY/SANDBOX_TOKEN/SANDBOX_URL/ZEROSHIP_SDK_REGISTRY), and the Vite build-time define only folds the literal `process.env.NODE_ENV` member-expression, which `isLocalDevRuntime` reads indirectly via a local `env?.NODE_ENV` and so does not touch. So in the deployed builder `isLocalDevRuntime()` is true and every authenticated user (all `pws_…`) collapses to `DEV_SANDBOX_USER_ID`. The controller's `(user_id, project_id)` dedup + `?user_id=` ownership check no longer separate users; sandbox isolation degrades to the secrecy of the client-minted `prj_<uuid>` projectId. (If NODE_ENV=production were ever set, the `usr_`-only assertion instead throws for all `pws_` users — total breakage — which itself shows this path is untested against real prod identities.)
- **Attack:** Builder users A and B both reference an app under a non-random/shared appId (the `/p/:appId` route and `getProject` accept any id) — both resolve to sandbox `(DEV_SANDBOX_USER_ID, deriveProjectId(appId))` and thus the SAME container/workspace, exposing each other's source, `.env` secrets, dev logs, and a shared shell. More generally, since the user dimension of ownership is nullified, anyone who learns a victim's projectId (shared preview link `/api/preview/<appId>/…`, referer, history, logs) — including an anonymous caller via SEC-5 — reads/writes that victim's sandbox files and `.env`.
- **Suggested fix:** Derive the sandbox owner from a stable, always-present identity (use the `pws_` subject itself, or a server-stamped per-request user) instead of requiring a `usr_` typed id, and **hard-fail closed** when unauthenticated in production. Gate the dev fallback on an explicit positive signal that is unset in prod (e.g. a `ZEROSHIP_DEV=1` boot flag), never on the mere absence of NODE_ENV; relocate the check so the Vite production define (or a runtime-stamped flag) actually reaches it.
- **Verifier note:** Both refuters confirmed at high confidence: no prod NODE_ENV setter exists, the kill-switch is set nowhere, `WorkerUser.id` is the `pws_` subject, and the sandbox controller's `require_owner` only matches the now-collapsed `?user_id=`. The console ships as a multi-tenant gateway-fronted app (Dockerfile → `/opt/zeroship/console/app.zship`), and sandbox/project RPCs accept a client-supplied appId with no per-creator ownership check. Not in the 2026-06-03 ledger (the builder TS was outside audited modules).

### Medium

#### SEC-7 — Env-var/secret rotation never reaches a running isolate (reconcile refreshes `SharedEnvs` but never reloads on an env-only change)
- **File:** `crates/worker/src/sync.rs:199`
- **Sources:** worker
- **Description:** In `reconcile_once` PHASE 2, `needs_update` is `deploy-hash-changed OR limits-changed` (sync.rs:196-199). `env_changed` (line 205) is computed but only consulted **inside** the `if needs_update` block (line 238). So a pure env-version bump (env_changed=true, needs_update=false) refreshes the process-wide `SharedEnvs` entry in PHASE 1 (sync.rs:158-178) but **never reloads the V8 isolate**. The runtime materializes the `env` argument object once (runtime.rs:1240 builds `env_obj` only `if is_none()`) and builds `process.env`/`__env__` once at bootstrap (init.rs:1857-1899); `set_env_snapshot` keeps Rust-side typed fields fresh per request but the already-built V8 objects are never re-materialized. Net: an env-var or secret change made via the dashboard (an env-version bump, not a code redeploy) is silently not applied to any isolate already running. It only takes effect on LRU eviction or a code redeploy. For a hot, stable app, the stale value persists indefinitely — contradicting PHASE 1's own comment promising staleness bounded to ~2x poll_interval.
- **Attack:** A creator gates privileged behavior on an env value (e.g. `env.ADMIN_TOKEN`) or stores a third-party API key as a secret. The value leaks; the creator rotates/removes it via the dashboard expecting the old value to stop working. The control plane bumps `env_version` and the worker refetches into `SharedEnvs`, but the live isolate keeps the OLD value in its already-built `process.env`. The attacker who knows the old credential retains access indefinitely while the dashboard reports the change as applied; revocation is ineffective until something unrelated evicts or redeploys the app.
- **Suggested fix:** Reload the isolate (or rebuild the cached `state.env_obj` / `process.env`) on an env-version change even when bundle hash and limits are unchanged: include `env_changed` in the `needs_update` predicate at sync.rs:199, and rebuild `env_obj` on a snapshot-version bump rather than only at first init.
- **Verifier note:** Confirmed at high confidence end-to-end; env-store mutations call only `bump_env_version` (never `deploy_hash`), and `set_env_snapshot` mutates only Rust-side fields, so a hot non-redeployed app serves the rotated-away credential. Not a ledger duplicate (W-3 is about zeroizing old plaintext, not stale-serving); actor is external.

#### SEC-8 — Verdaccio private registry allows open self-registration plus `$authenticated` publish/unpublish to `@zeroship/*` and `**` → supply-chain poisoning
- **File:** `config/verdaccio/config.yaml:8`
- **Sources:** infra
- **Description:** `auth.htpasswd.max_users: 1000` enables open self-service account creation (any client can `npm adduser` / PUT `/-/user` up to the cap). Combined with the package ACLs (`@zeroship/*` and `**` both `publish: $authenticated` / `unpublish: $authenticated`, lines 16-24), any self-registered user can publish or overwrite the platform's own `@zeroship/db`, `@zeroship/bootstrap`, etc. `scripts/e2e-private-registry-sandbox.sh:69-80` demonstrates the self-register→token→publish flow; `docker-compose.yml:41-43` publishes Verdaccio on `0.0.0.0:4873`. Sandbox build containers reach it via `--add-host host.docker.internal:host-gateway` (crates/sandbox/src/backend/docker.rs), and the builder writes `@zeroship:registry=http://host.docker.internal:4873` into the sandbox `.npmrc` before `npm/pnpm install`, so untrusted AI-generated build code in one tenant's sandbox can poison the shared registry consumed by other tenants' builds.
- **Attack:** Untrusted code building inside one sandbox self-registers, then `npm publish`es a backdoored `@zeroship/db`; the next tenant's build resolves the poisoned package from the same registry and executes attacker code in that build (and the produced app bundle) — a cross-tenant supply-chain compromise. Anyone on the host's network can do the same against `0.0.0.0:4873` directly.
- **Suggested fix:** Set `max_users: -1` to disable self-registration; provision publisher accounts out of band (operator-managed htpasswd) and restrict `@zeroship/*` and `**` `publish`/`unpublish` to a named publisher group rather than `$authenticated`. Bind the registry to an internal interface, not `0.0.0.0`, and never expose it to sandbox build containers.
- **Verifier note:** Confirmed at **medium** confidence — all factual claims verify (open self-register, `$authenticated` ACLs, sandbox `.npmrc` redirect, `.env.example` ships the `host.docker.internal:4873` default). Not a ledger duplicate (pass-4 supply-chain covered rustls-webpki + TCB pinning, never the registry auth posture). Severity held at medium: the `**`-shadows-npmjs (malicious `react`/`lodash`) claim is **overstated for the sandbox vector** — only the `@zeroship` scope is redirected in-sandbox, non-scoped packages still resolve from npmjs; and the cross-tenant blast radius assumes a single shared publish-enabled Verdaccio reachable from sandboxes. This is the dev registry config today, but it is the only registry config in the repo.

#### SEC-9 — App-controlled `Set-Cookie` with attacker `Domain` forwarded verbatim → cross-subdomain cookie injection + platform cookie-bomb DoS
- **File:** `crates/gateway/src/proxy.rs:305`
- **Sources:** lens-tenant-isolation
- **Description:** A creator app's `default.fetch` Response headers are forwarded to the browser unmodified except for a small hop-by-hop denylist. The worker copies every app-supplied response header verbatim (`make_http_response`, worker/handler.rs:289-295), and the gateway re-forwards every header whose lowercased name is not in `hop_by_hop = [connection, keep-alive, transfer-encoding, te, trailer, upgrade, proxy-authorization, proxy-authenticate]` (proxy.rs:305-316). `Set-Cookie` is not in that list and is not otherwise scrubbed or scoped, so an app at `evil.zeroship.ai` can return `Set-Cookie: <name>=<value>; Domain=zeroship.ai; Path=/` and the browser attaches that cookie to every `*.zeroship.ai` host — sibling creator apps, `auth.zeroship.ai`, `console.zeroship.ai`. The platform's own session/stash/anchor cookies are `__Host-` prefixed in prod (oidc_rp.rs:999, anchors.rs:72), which blocks shadowing/fixation of the platform session itself, but nothing constrains the cross-tenant blast radius for other apps' cookies or the request-header bloat.
- **Attack:** A malicious creator's app returns many large `Set-Cookie: pad{i}=<4KB>; Domain=zeroship.ai` headers (or a single fixed `session=KNOWN; Domain=zeroship.ai`). Any end-user who visits that app then carries those cookies on every subsequent request to `console.zeroship.ai`, `auth.zeroship.ai`, and every other `*.zeroship.ai` app: the oversized cookie jar trips request-header size limits (431 / upstream reject) — a cross-tenant + platform availability DoS for that browser — and any victim creator app reading a same-named cookie receives an attacker-chosen value (cross-tenant cookie injection / session fixation between mutually-untrusted apps).
- **Suggested fix:** At the worker→client boundary (or in the gateway forward), parse app-emitted `Set-Cookie` headers and reject/strip any `Domain` attribute that is not exactly the app's own host (force host-only cookies for creator apps), and cap the number/size of cookies an app response may set.
- **Verifier note:** Confirmed at high confidence; `extract_response_headers` pushes every separate `set-cookie` entry with zero filtering, and the hop-by-hop denylist is exactly the 8 entries listed with no Domain check or count/size cap. Not a ledger duplicate. Medium severity given the precondition that the victim must visit the malicious app and that platform sessions stay protected by `__Host-`.

#### SEC-10 — Cross-tenant read of another creator's issue tracker + quality scorecard via builder RPC (appId IDOR, no ownership check)
- **File:** `apps/zeroship-builder/src/server/agents.ts:233`
- **Sources:** lens-endpoint-authz
- **Description:** The builder console is a single shared zeroship app; all creators share its one `@zeroship/kv` namespace. Two registered, user-auth-default RPC procedures key shared-KV reads purely on a client-supplied `appId` with **no** `currentUser()` ownership check: `getQualityScores({appId})` (agents.ts:233) reads `quality:${appId}`, and `listIssues({appId})` (agents.ts:134 → loadIssuesOrSeed → issuesKey) reads (and seed-writes) `issues:${appId}`. `appId` is an arbitrary `z.string().min(1).max(256)`. The KV-key comment conflates collision-avoidance with access-control. This contradicts the sibling `projects.ts` in the same module, which scopes its registry by `projects:${currentCreatorId()}`. The issue tracker exposes another creator's planning notes (titles/descriptions/PM-SRE-Builder agent comments); the scorecard exposes per-dimension grades + rationales (e.g. security/CVE notes).
- **Attack:** Any authenticated console creator (the procedures default to auth:'user', so the gateway 401s anon but admits any logged-in creator) learns victim A's random `prj_`/`app_` appId — not enumerable, but routinely leaks via shared preview links `/api/preview/{appId}/...`, the `/p/{appId}` route, screenshots, or support threads. They POST `{appId: "<victimA_appId>"}` for wireIds `agents.quality.get` and `agents.issues.list`, reading A's private quality scorecard and issue tracker. `listIssues` additionally seed-writes the victim's empty slot.
- **Suggested fix:** In `getQualityScores`/`listIssues` (and any other appId-keyed shared-KV procedure), resolve `currentCreatorId()` and either (a) verify the appId is in the caller's `projects:${creatorId}` registry before serving, or (b) namespace the KV keys by creator (e.g. `quality:${creatorId}:${appId}`) — matching how `projects.ts` already scopes its registry.
- **Verifier note:** Confirmed at high confidence; neither handler calls `currentUser()`/`currentCreatorId()`, both are live RPC exports, gateway auth is level-only (any valid session passes a User route), and the correctly-scoped sibling sandbox/projects paths corroborate the intended design. Not a ledger duplicate. Severity rests on the appId-leak precondition (downgrade to low if appIds are effectively never shared).

## 5. Unverified lows

Reported by a finder but not put through independent verification:

- **Operator dynamic policy overrides (`zeroship.platform_policies`) are written + audited but never loaded into the enforced PolicySet** — `crates/control/src/main.rs:920`. The admin write path (upsert/delete + audit + 204) ships, but no `engine.reload_static()`/DB-merge consumes the table; `enforce()` always uses the boot-time static `.cedar` set, so every operator policy override is inert (the documented emergency-override lever silently no-ops). Harm is to incident response, not creator-reachable.
- **SSRF IPv6 blocklist omits NAT64 (`64:ff9b::/96`) and IPv4-compatible (`::a.b.c.d`) ranges** — `crates/runtime/src/transport/ssrf.rs:56`. `is_blocked_v6` blocks v4-mapped (`::ffff:…`) but empirically returns false for `64:ff9b::a9fe:a9fe` (NAT64 of 169.254.169.254) and `::a9fe:a9fe`. For a literal IPv6 URL the DNS-layer filter is bypassed and `is_blocked_ip` is the sole gate. LOW because a strictly RFC-6052-compliant NAT64 won't translate non-global IPv4 via the well-known prefix; exploitation needs a permissive/non-compliant NAT64 deployment.
- **Hand-rolled agent WebSocket listener has no read/idle timeout and no concurrent-connection cap (slowloris)** — `crates/sandbox-agent/src/proxy_ws.rs:449`. `read_request_head` loops `stream.read(...).await` with no deadline and the accept loop imposes no in-flight cap, all before Ed25519 verification; a stalled-handshake flood pins compio tasks/fds. Bounded value: the agent runs inside the per-sandbox VM (largely self-DoS); cross-tenant amplification depends on the already-recorded SB-A1 L3 egress gap.
- **`CONTROL_KEY` has no strength floor while every peer inter-service secret enforces ≥32 bytes + dev-sentinel rejection** — `crates/control/src/main.rs:538`. `control_key` is checked only for non-empty; `validate_worker_key`/`validate_stash_key`/`validate_pairwise_salt`/`validate_master_key_material` all abort boot on weak values. CONTROL_KEY bears `/internal/*` (decrypted env/secrets + route registry). LOW/defense-in-depth: the verifier compare is constant-time, so this is online-brute-force from an internal network position only.

## 9. Recommended fix order

1. **SEC-1 (critical) — plugin-db cross-tenant transaction hijack.** Highest blast radius (cross-tenant data read + write-integrity + persistent DoS against ~199 co-tenants), reachable by any deployed creator app. Re-key the tx/connection state per app_id (or stamp+check the owner) before anything else. This is the single change that closes a multi-tenant data-integrity hole the prior audit believed sealed.
2. **SEC-2 (high) — gateway path-normalization auth bypass.** Unauthenticated per-route auth bypass against the platform's sole authz checkpoint. Canonicalize the path once and forward the canonical form; this also subsumes trailing-slash/double-slash siblings.
3. **SEC-5 + SEC-6 (high, builder) — fix together.** They compound: SEC-5 (rename `rpc:apps` → `rpc:projects`, add a fail-closed `*` root + a validator rule rejecting absent-auth-resolving-to-anon) makes the surface authenticated again; SEC-6 (derive the sandbox owner from the `pws_` subject, hard-fail closed in prod, gate the dev fallback on a positive boot flag) restores per-user isolation. Cheap, self-contained, and they currently expose sandbox `.env` secrets to anonymous callers.
4. **SEC-4 (high) — aggregation masking bypass.** Completes the DB-3 masking-control work; mirror `build_distinct`'s sibling substitution in the aggregate builder, harden `wrap_row_on_read`, add the regression test. Regulated-PII disclosure, own-app scope.
5. **SEC-3 (high) — auth XFF rate-limit bypass + unbounded auth-DB rows.** Strip/inject the client-IP header at the gateway auth-host path and parse XFF by trusted-hop count in auth; add TTL + GC to `zeroship.rate_limits`. Closes both the abuse-defense bypass and the durable shared-DB DoS.
6. **Medium tier — SEC-9, SEC-7, SEC-10, SEC-8.** SEC-9 (scope app `Set-Cookie` Domain to host-only + cap count/size) and SEC-7 (include `env_changed` in `needs_update` so secret rotation actually applies) are small, high-value gateway/worker fixes. SEC-10 (namespace `agents.ts` KV keys by creator) is a one-line keyspace change. SEC-8 (disable Verdaccio self-registration, restrict publish ACLs, bind internal, keep it off sandbox build containers) is a config hardening that should be settled before any real private-registry deployment.
7. **Carry forward the open ledger backlog in its existing priority**, with two adjustments this round: (a) note that the **control-plane remediation branch (CT-A1/CT-B1/CT-B2/CT-B3/CT-C1 …) was never merged** — re-land or re-implement those; (b) **RT-6** (off-heap memory escapes the heap cap) gained two more reachable instances (zlib decompress, EventSource buffers) and remains the right umbrella fix (`adjust_amount_of_external_allocated_memory`). The four unverified lows (inert `platform_policies` override path, NAT64 SSRF gap, agent WS slowloris, CONTROL_KEY strength floor) are defense-in-depth and can follow.
