## Summary
- 11 findings (2 critical, 5 important, 4 minor)
- Themes: (1) **lifecycle has terminal sinks no code can drain** — `SnapshottingAborted` and the entire `RestoringCold` lane are written but never read into a recovery path; (2) **migration 0007 ships 4 columns nobody writes or reads** (`drain_failure_count`, `last_drain_failure_at`, `last_running_worker_id`, `idle_snapshot_count_long_poll`); (3) **lease lifecycle is unwired** — `update_lessee` is defined in `db.rs` + tested in pg-e2e, but **no handler bumps it**, so any snapshot/restore longer than `SANDBOX_TRANSIENT_STATE_TIMEOUT_SECS` (default 120 s) gets reaped mid-flight; (4) **AEAD config is half-wired** — `snapshot_root_kek_path` is parsed, logged, and dropped on the floor (the L1 store is never wrapped with `AeadSnapshotStore`); (5) wrapper-script env contract is duplicated across `nomad_ch.rs` + `restore_handler.rs::build_restore_nomad_job_json` with no shared producer.

## CRITICAL

**`crates/sandbox/src/db.rs:2305` — `update_lessee` defined but never called from any handler**
  Why: § 6.1 lease-takeover model requires the in-flight controller to bump `lessee_updated_at` every ~10 s. `update_snapshot_metadata` writes `lessee_updated_at = NULL` at the END of a snapshot; `restore_sandbox` never touches the lessee. Between the CAS-to-`snapshotting` (`snapshot_handler.rs:269`) and the L1 put completing (~2.1 s normal, **but +GCS upload + ch-remote 30 s budget**), nothing is bumping. `sweep::run_transient_takeover_once` filters on `lessee_updated_at IS NOT NULL AND … < now() - 120s` (`db.rs:2361`). For the very first transient (lessee NULL), the WHERE skips it — so this **isn't fatal today**, but the moment any retry-style code calls `update_lessee` once and then stalls, the sweep WILL reap a live op. More directly: the design says transient rows have a heartbeat; the implementation has none. The only thing keeping correctness today is that the IS NOT NULL filter silently turns the sweep into a no-op for fresh transients.
  Fix: spawn a 10 s-cadence task per in-flight snapshot/restore (or a single per-controller task that scans `state = transient AND host_id = self`) that calls `update_lessee`. Alternative: drop the IS NOT NULL filter and use `coalesce(lessee_updated_at, status_changed_at)` so a missing bump still allows recovery.

**`crates/sandbox/src/db.rs:1185,1188` + `sweep.rs:103-105` — `SnapshottingAborted` and `RestoringCold` are terminal sinks**
  Why: `SnapshottingAborted` is written ONLY by `sweep::recovery_target(Snapshotting) → SnapshottingAborted`; **no path drains it back**. Same for `RestoringCold` — `recovery_target(RestoringCold) → SnapshottedSuspect`, but no handler ever puts a row INTO `RestoringCold` to begin with (`cold_boot_sandbox` is a 501 stub at `admin_handlers.rs:1287`). Net effect: rows that crash mid-snapshot get marked `snapshotting_aborted` and **stay there forever**; operators have no API to either retry or expunge. The `restoring_cold` lane is six lines of enum/migration carrying dead weight. § 9.2 lifecycle table is half-implemented.
  Fix: either (a) ship the cold-boot orchestrator (which `RestoringCold` exists to serve) and add an admin endpoint to drain `SnapshottingAborted → Running` after operator confirmation, or (b) delete `RestoringCold` + `SnapshottingAborted` from the enum, CHECK constraint, and sweep, and route `Snapshotting`-takeover to `Running` (re-snapshot is destructive, so rollback IS the correct recovery). Shipping both states with no consumer is worse than shipping neither.

## IMPORTANT

**`crates/sandbox/migrations/0007_sandbox_snapshot_columns.sql:26-30` — four columns NEVER read or written**
  Why: `last_running_worker_id`, `idle_snapshot_count_long_poll`, `last_drain_failure_at`, `drain_failure_count` are added (with NOT NULL DEFAULT on the last two) but a Grep over `crates/sandbox/src/` returns zero references. Migration scaffolding for features that haven't shipped is a back-compat tax we can't take back. Either land the readers or drop the columns.
  Fix: pull these four columns into a separate migration (`0009_*`) that ships alongside the consumer. Migration 0007 should only ship what 0007's code actually uses.

**`crates/sandbox/src/lib.rs:354-358` + `config.rs:163` — `snapshot_root_kek_path` is parsed, logged, ignored**
  Why: `AeadSnapshotStore` exists (`snapshot_aead.rs:325`), `RootKek::from_path` exists, the config knob is plumbed all the way to `AppState::from_config`. But the wiring at `lib.rs:326` is `let l1 = LocalDiskSnapshotStore::new(...)` and at `:338` `TieredSnapshotStore::new(l1, l2)` — **no `AeadSnapshotStore::new(inner, root_kek)` layer anywhere**. The pg column `snapshot_aead_dek_id` is then unconditionally set to `Some("v1")` (`snapshot_handler.rs:357`) regardless of whether AEAD ran. Two failure modes: (a) operators believe they're getting envelope encryption because they set `SANDBOX_SNAPSHOT_ROOT_KEK_PATH`, but artifacts are stored plaintext on the L1 disk + GCS; (b) the pg `dek_id` lies about the artifact format.
  Fix: at `lib.rs:326` wrap with `AeadSnapshotStore` when `snapshot_root_kek_path.is_some()`. Set `aead_dek_id = None` at `snapshot_handler.rs:357` when AEAD is off — the column truthfully reflects format.

**`crates/sandbox/src/restore_handler.rs:843-969` vs `crates/sandbox/src/backend/nomad_ch.rs:2032-2069` — restore jobspec duplicates cold-boot env contract by hand**
  Why: `build_restore_nomad_job_json` re-derives `workspace_img`, `user_home_img`, MAC/tap derivation rules, `cpus_boot` (with its own copy of the ceil-with-min-1 logic), the entire `Resources { CPU: 500, MemoryMB, MemoryMaxMB: memory_mb*2 }` shape, and the 8-env contract. The wrapper-script contract lives in `crates/sandbox/scripts/nomad-vm-wrapper.sh` (lines 30-74). Restore and cold-boot must emit IDENTICAL env keys or the wrapper's `:?missing` checks fire. Today they happen to match because they were written near-simultaneously, but there's zero compile-time or test-time enforcement — a cold-boot env addition (`ZSBX_FOO_NEW`) will silently fail on restore in production. The `derive_mac` / `derive_tap` Rust copies (`restore_handler.rs:421-429`) acknowledge this explicitly with "Source-of-truth is the wrapper script; this Rust copy must match."
  Fix: extract a single `build_zsbx_env(vm_index, paths, mem, cpus, restore_from: Option<&Path>) -> BTreeMap<&str, String>` that both `nomad_ch::build_nomad_job_json` and `restore_handler::build_restore_nomad_job_json` consume. Add a single source-of-truth test that asserts the env keyset matches the wrapper's `:?required` block.

**`crates/sandbox/scripts/nomad-vm-wrapper.sh:359` — `sed -i` rewrite of `config.json` is silent contract with controller**
  Why: the wrapper rewrites `/opt/nomad/data/alloc/[^/]+/[^/]+/local` → `${NOMAD_TASK_DIR}` inside the snapshot's `config.json` (`disks[].path`, `serial.file`, and any leftover `fs[].socket`). The controller-side rewrite (`restore_handler.rs:439-477`) explicitly leaves these fields alone with a long comment "the wrapper handles path rewrites at exec time." This is a **layer boundary inversion**: the controller has a typed `serde_json::Value` already deserialized, yet hands off to a shell `sed` regex on the same file moments later. The regex assumes a specific Nomad path layout (`/opt/nomad/data/alloc/<alloc>/<task>/local`); a different Nomad data-dir layout silently no-ops the rewrite and CH crashes with "Error creating console device." No test pins this.
  Fix: do the path rewrite in `restore_handler::rewrite_config_json` after the controller learns the alloc UUID. The cleanest split: controller stages the snapshot at a stable path the wrapper can read via env (`ZSBX_RESTORE_STAGED_DIR`), wrapper does not touch JSON. Alternatively, if the controller really can't know the alloc UUID at job-submit time, codify the regex + Nomad-data-dir-prefix as a typed constant (e.g. `ZSBX_NOMAD_ALLOC_PATH_PREFIX` env) so the contract is in the source, not in a regex.

**`crates/sandbox/src/lib.rs:440-450` — `spawn_idle_eviction_sweep` is *not* called in production**
  Why: the comment is candid ("For v1, leave the sweep dormant"), but the design's § 7 explicitly counts on it for the snapshot eviction story. The `sweep::IdleSnapshotter` trait has only `RecordingIdleSnapshotter` as an impl in tree — there is no `RealIdleSnapshotter` that closes over `db + store + ch + state.backend`. Without this, the snapshot feature has no production trigger except the manual `POST /admin/.../snapshot` admin handler. The four pg columns from migration 0007 that govern eviction (`idle_snapshot_opted_in`, `idle_snapshot_count_long_poll`) sit ready but unread. § 13 step 3-4 ("Idle eviction GA") cannot ship without this glue.
  Fix: land a `ProductionIdleSnapshotter` struct in `sweep.rs` (or a sibling) that adapts the snapshot-handler chain into `IdleSnapshotter::snapshot_one`, and call `spawn_idle_eviction_sweep` from `lib.rs:451` gated on `state.config.snapshot_enabled`. Until that lands, the sweep code is shelfware that drifts.

## MINOR

**`crates/sandbox/src/restore_handler.rs:320-322` — `snap.artifact_path` discarded with a let-underscore**
  Why: `let _ = &snap.artifact_path;` is a no-op kept "for tracing/logs" per the comment, but no tracing call uses it. The pg column drives no decision in the restore path (the store re-derives from sandbox-id). Either honour the column (e.g., validate `dest.starts_with(snapshot_l1_root)` and refuse on mismatch — operator-friendly drift check) or remove it from the SELECT to stop pretending it's load-bearing.

**`crates/sandbox/src/backend/mod.rs:359-373,424-442` — three near-identical `Err` arms for non-NomadCh backends across `restore_from_sealed`, `restore_from_pg_and_sealed`, `lookup_source_vm_ops`, `teardown_source_for_snapshot`**
  Why: the Backend enum's snapshot-related methods each match `Docker(_) | K8s(_) => Err("backend X doesn't support …")` four times with hand-written messages. The "is this backend snapshot-capable?" predicate is implicit and scattered. A new backend variant (e.g. Firecracker) would need to remember to update all four arms.
  Fix: add `Backend::supports_snapshot(&self) -> bool` (single source of the capability matrix); each snapshot method does `if !self.supports_snapshot() { return Err(...) }` at the top. Or, cleaner: extract a `SnapshotCapableBackend` sub-trait that only `NomadCh` implements, and expose it via `Backend::as_snapshot_capable() -> Option<&dyn SnapshotCapableBackend>`.

**`crates/sandbox/src/snapshot_handler.rs:294` — temp_dir cleanup runs only on rollback, not on success**
  Why: After `store.put` (`snapshot_handler.rs:345`) the source `temp_dir` has had its three files `rename`'d out (`snapshot_store.rs:209-217`), but the directory itself stays. Successive snapshots on the same sandbox stack empty dirs at `<snap-stage>/<sbx_id>/`. Cleanup-on-success would be a one-line `let _ = std::fs::remove_dir(&temp_dir);` after `do_snapshot_inner` returns Ok.

**`crates/sandbox/src/restore_handler.rs:1131` + `snapshot_handler.rs:692` — two near-identical test-only `spawn_fake_nomad`/`write_script` helpers**
  Why: both inline a small TCP server / shell-script harness. Not a correctness issue, but a 1-day-onboarding ask ("where do I add a new fake-Nomad test?") has two answers. A `crate::test_helpers` mod (cfg(test)) would unify them.

## Things that surprised me (positively or negatively)

- **Positive**: the CH v51.1 post-snapshot VMM-down quirk is captured with a clear comment and a regression test (`snapshot_handler.rs:467-510` + `snapshot_succeeds_when_ch_remote_exits_nonzero_but_artifact_on_disk` at :799). The on-disk-fallback signal is well-chosen.
- **Positive**: `SourceVmOps` / `RestoreBackend` / `ChRemoteClient` trait split makes the handler unit-testable without a real CH; `StubSourceVmOps` + `StubRestoreBackend` + `MockChRemoteClient` are all in-tree. Good leverage.
- **Negative**: `restore_handler.rs` does sync HTTP via `ureq` in the handler path (`nomad_post_blocking`, `wait_for_alloc_running_blocking`); the comment at :650 acknowledges this blocks a compio worker. The "infrequent op" justification is plausible, but the comment "the handler invokes them from an async task and will block its compio worker for the duration" is not paired with a `compio::runtime::spawn_blocking` hop at the call site (`admin_handlers.rs:1259-1266` calls directly into `restore_handler::restore_sandbox` from the ntex handler thread). This is the kind of thing that bites at 10× load.
- **Negative**: the boot loader never re-discovers `Snapshotted` rows (`lib.rs` has zero references to `Snapshotted`). Sealed-record restore (`Backend::restore_from_sealed`) handles `Running` sandboxes; snapshotted rows just sit in pg. If a controller restarts and a user hits `POST /wake`, it works — but there's no scheduled awareness that "these N artifacts are waiting." The `snapshot_artifact_path` column in pg is the only handle, and as noted above it's discarded by the restore path. Worth a /readyz metric at least.
- **Surprise**: `DEFAULT_BACKING_VERSIONS` (`snapshot_handler.rs:211`) is hard-coded to `"unknown"` placeholders. The proposal § 5 talks about backing-file content hashes gating restore. Today the column is filled with sentinels; an old artifact whose backing rootfs has been re-baked is silently accepted on restore. v2 follow-up flag in the source is fine, but the production snapshot wiring should record at least the rootfs SHA so a future-shipped checker has data to compare against.
