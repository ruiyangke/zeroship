### [R14-T2] C-4's `VmIndexRetryPolicy::default()` budget envelope is asserted by arithmetic, not by behaviour (IMPORTANT, test-coverage-r14, NEW)

- **Files**: `crates/sandbox/src/restore_handler.rs:1173-1186` (`c4_default_policy_envelopes_observed_teardown`); `crates/sandbox/src/restore_handler.rs:129-148` (`VmIndexRetryPolicy::default()` — `max_attempts: 60`, `interval: 2 s` → 118 s envelope vs. observed 90 s).
- **Symptom**: the test asserts `(max_attempts - 1) * interval_ms >= 90_000`. That's a fixed assertion against the constant — it doesn't drive `reserve_vm_index_with_retry` with the default policy at all. If someone changes the field types (e.g., `interval` from `Duration` to `Option<Duration>`, or `max_attempts` from `u32` to `NonZeroU32`) the test compiles only on the new shape; if someone refactors the *retry loop itself* to ignore `max_attempts` (e.g. use a hardcoded ceiling), the policy guard fires green but the production code's effective budget is wrong. The test name promises behavioral envelope coverage; the test body delivers a constant check. The 90 s figure also lives only in the assertion — a doc-link to `T-8b-smoke-r5.md`'s observed teardown profile would prevent silent drift if the source-teardown cadence changes.
- **Why it matters**: r13 noted that C-3's regression test is a false-negative against the actual failure mode. R14 finds C-4's `#4` test has a similar shape — the assertion is on the *arithmetic* of the constant, not on the *behaviour* of the loop using the constant. If the value-flow drifts (e.g. someone caps the loop early via `min(max_attempts, 10)` in the helper body), the test still passes. The other 3 c4_* tests do test behaviour, but each uses a hand-rolled `VmIndexRetryPolicy { max_attempts: 4/5/10, interval: 5-500 ms }` — none stresses the default policy through the loop end-to-end. The cluster's actual 90 s teardown was observed BY smoke-r6 (per its timeline: `02:24:33 → 02:26:16` = 103 s wall-clock incl. host_fence + Nomad purge); the test asserts 90 s as a constant, but the cluster found 103 s. The test's envelope assertion is correct (118 s > 103 s observed), but a smoke-r7 with a worse-case teardown could close the gap silently.
- **Action**: rewrite as a `#[compio::test]` that constructs `StubRestoreBackend` with `reserve_succeeds_on_attempt = Some(46)` (slot frees at ~90 s under the default 2 s cadence) AND uses `VmIndexRetryPolicy::default()` — asserts the loop succeeds within the default budget. Pair it with a second test using `reserve_succeeds_on_attempt = Some(61)` (just past the 60-attempt budget) that asserts the loop surfaces `VmIndexUnavailable`. This pins the loop behaviour against the default policy, not just the constants. ~30 LOC for both tests. **Minor twist for this cycle**: smoke-r6's 103 s observed teardown is already higher than the 90 s the constant-assertion guards. Either widen the assertion to 105 s (with a doc-link to smoke-r6's timeline) or — better — drop the constant assertion in favour of the behavioural envelope test described above. ~20 LOC. Tracking-only this round; the arithmetic check IS correct as written, just brittle.
