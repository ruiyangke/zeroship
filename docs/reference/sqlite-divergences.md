# SQLite divergences

`zeroship-data-orm` keeps the creator-facing CRUD surface aligned across Postgres and SQLite. Array updates share complete-element and structural-equality semantics; SQLite's connection setup installs the SQL comparison helper described in [the ORM architecture](../architecture/data-orm.md). The remaining differences are in engine-specific search, transaction isolation, locking, scoring, and ordering.

Most rows below are deliberate. Typed-ID ordering is retained as an explicit
parity guarantee because column collation prevents the databases from comparing
the generated values differently.

For the **migration** authoring surface, the equivalent boundary — which DML transforms are portable across both backends, the `.splitPart` portable-expression envelope, and the `EXPR_NOT_PORTABLE` hard error out of envelope — is documented in [migrate-op-dsl.md](./migrate-op-dsl.md#the-dml-portability-boundary).

## Current differences

| Area | Postgres | SQLite | Contract |
| --- | --- | --- | --- |
| Vector metrics | `pgvector` supports cosine, L2, and inner product | `sqlite-vec` `vec0` supports cosine and L2 only | `VectorMetric::InnerProduct` returns `vector_unsupported_metric` on SQLite. |
| Spatial search | PostGIS + GIST-backed `ST_DWithin` | no index build; `spatial_near` does a haversine flat scan over the stored geopoint BLOB | Result semantics aim to match, but the SQLite path is a dev-scale scan. |
| Transaction isolation | An explicit level selects `BEGIN ISOLATION LEVEL ...`; omitting it uses the database default | Accepts the default or `serializable`; other levels return `unsupported_isolation_level` before the callback runs | Rust and V8 share this contract. Nested callbacks inherit the enclosing isolation and reject an explicit level with `nested_isolation_level`. |
| Transaction isolation under contention | two requests handled by different runtime threads hold genuinely concurrent transactions, and `serializable` arbitrates them: measured over 16 concurrent write-write pairs on one row, the loser returned `SERIALIZATION_FAILURE` and only one row landed, 16 times out of 16 | one thread, one isolate — the second transaction **waits** for the first, so both succeed and neither is ever aborted (16 of 16) | **A conflicting-writer abort is a production-only outcome; `pnpm dev` cannot produce one.** Two transactions for the same app on the *same* thread are serialized on both tiers, so the isolation level has no second writer to arbitrate there — this is why the deployed abort depends on the request landing on another thread and the local tier, which has only one, never sees it. Write for the production case: handle `SERIALIZATION_FAILURE` by retrying the whole transaction, and do not treat a clean local run as evidence that a transaction is conflict-free. |
| Ordinary writes overlapping a transaction | a write with no transaction in its call chain takes its own pooled connection, so it is unaffected by a transaction another request holds open — measured, the transaction aborts and the ordinary write's row is still there | **same** — the actor keeps two connections per session (`tx_conn` for the one explicit transaction, `op_conn` for autocommit work), so an ordinary write is unaffected by an open transaction and survives its `ROLLBACK` | **RETIRED as a divergence on 2026-08-27.** This row used to say the opposite: SQLite ran the whole app on one connection, so a correctly pool-routed write executed inside whatever transaction that connection held and its row died with that transaction's `ROLLBACK` — while the write reported success. SC-2 Decision 1 split the connections. The remaining SQLite-only limit is the engine's, not the platform's: SQLite has **one writer per database**, so an autocommit *write* issued while `tx_conn` holds the write lock waits up to the lock budget (`budgets::DB_LOCK_TIMEOUT_MS`) and then reports lock contention. Concurrent *readers* are unaffected. |
| Concurrent `db.transaction()` calls | each transaction takes its own connection from the app's pool, so several can be open at once; a transaction beyond the pool's size **waits** for a free connection and fails only if that wait expires | one transaction connection **per app**, opened on that app's first `db.transaction()`, so a second one *for the same app* is **refused immediately** with `TRANSACTION_CONNECTION_BUSY` | **A second transaction for one app fails on the dev tier where it would have succeeded deployed, and it fails instantly rather than waiting.** Two things differ, not one: the *ceiling* (many vs. one per app) and the *response to hitting it* (queue vs. refuse). Do not treat a clean local run as evidence that concurrent transactions work. **The cross-app case is gone as of 2026-08-28**: this row previously said one shared connection served every app, so another app's transaction produced the same error — that is fixed, `TRANSACTION_CONNECTION_BUSY` now always means *your* app, and the message names it. The same code is also raised on both tiers for a genuinely overlapping pair of operations *inside one* transaction (`Promise.all` over `tx.*` calls); the message distinguishes the two cases. |
| Concurrent transactions on purpose (`Database::independent()`) | a fork gets its own transaction lane over the same pool, schema, mask policy and protection floors, so a native host runs a bounded number of transactions per thread at once | refused with `unsupported_backend_feature` before any SQL | **The refusal is the point.** The actor reserves one transaction connection per app, so a second lane could only be refused at `BEGIN` with `TRANSACTION_CONNECTION_BUSY` - after the caller has already committed to the design - or serialize invisibly and deadlock a caller that awaits one fork from inside another. Rust host API only; creator code has no route to it. |
| Many apps in one dev process | no ceiling of this kind — connections come from a pool sized per worker | a session holds at most **8** apps' transaction connections; an idle one is closed to make room, and only a session where all 8 are mid-transaction refuses, with `TRANSACTION_LANES_EXHAUSTED` | **A distinct code because the remedy is distinct**: `TRANSACTION_CONNECTION_BUSY` is your own overlapping transaction, `TRANSACTION_LANES_EXHAUSTED` is contention with other apps sharing the dev process and is not a fault in your code — retry. Unreachable in the shipped dev vector, which hosts one app per process (the worker refuses a SQLite DSN outright, and `zeroship serve` clamps to one thread on one). |
| Row locks | the Rust ORM's `for_update()` and `for_update_of(alias)` render `FOR UPDATE [OF ...]` and hold exclusive row locks until the transaction settles | no row locks: a locking read is refused before SQL with `unsupported_backend_feature`, and the transaction stays usable | Rust host API only; the V8 adapter has no lock input. The ORM's internal write-target probes still compile on SQLite without a locking clause, because its single writer serializes writes. There is no `BEGIN IMMEDIATE` emulation. |
| Advisory locks, transaction settings and session leases | `Database::postgres()` exposes `advisory_xact_lock`, `set_local` and `try_session_lease` to native Rust hosts | `Database::postgres()` is refused with `unsupported_backend_feature`, and the transaction stays usable | A file-local engine has no server-wide lock space and no settings; the backend-instance-local lock registry cannot substitute for one. Rust host API only; creator code has no route to it on either backend. |
| Write contention | backend-native locking | WAL mode + single writer actor; busy-family SQLite errors collapse to the same typed lock-contention surface | Callers should branch on the typed error code, not raw SQLite error text. |
| Opening a file another process holds | the server arbitrates connections | every connection's busy timeout is the lock budget (`budgets::DB_LOCK_TIMEOUT_MS`), set before the first statement that takes a lock, and the switch to WAL is retried within that same budget | **A contended open waits; it does not refuse at once.** The retry is there because SQLite does not invoke the busy handler when the switch's read transaction upgrades to a write while another connection holds the write lock - a bootstrap's `BEGIN IMMEDIATE`, for instance. A hold that outlasts the budget still surfaces as typed lock contention. |
| Journal mode of app data | not applicable — one Postgres cluster, MVCC | the session's own database is **WAL**, but each app's `zs-<app>.sqlite` is **DELETE** (rollback journal). `PRAGMA journal_mode` is per database and does not propagate across `ATTACH`, and the migration engine pins app files to DELETE and refuses to run otherwise (`crates/zeroship-migrate-sqlite/src/backend/actor.rs:719-729`) | **WAL's reader-writer concurrency does not apply to your app's own tables.** A reader still proceeds while a writer holds `RESERVED`, so ordinary overlapping reads are fine, but there is no per-connection snapshot and a `SQLITE_BUSY_SNAPSHOT` write-upgrade conflict cannot arise on app data — an upgrade conflict there is a plain `SQLITE_BUSY` that waits out the lock budget (`budgets::DB_LOCK_TIMEOUT_MS`) instead of failing at once. Both are the same typed lock-contention surface to a caller; the difference is how long you wait for it. |
| Binding on schema `main` | `main` is an ordinary schema name | addresses the file the backend opened. The backend attaches no `zs-<app>.sqlite` for it; its statements, catalog reads and protection floor use that file, and its writes do not enter the change stream, which publishes only attached app files | For platform metadata kept in the file the host opens. Creator bindings name their app's schema and keep their own attached file. |
| Native text arrays | `textArray` columns and `#[orm(array_storage = "native")]` fields are `text[]`, bound in the binary array protocol; equality is array equality, and `push`/`pull`/`addToSet` use `array_append`/`array_remove`/`array_position` | the same declarations are JSON text; equality uses `zeroship_json_equal` and mutations use the JSON array renderer | **Same logical results.** Order and duplicates are significant in equality on both; `pull` removes every equal element and `addToSet` keeps existing duplicates on both; SQL NULL, `[]` and `["NULL"]` stay distinct; null and NUL elements are refused on write on both. Only raw SQL sees the difference (`{a,b}` versus `["a","b"]`). A PostgreSQL value the ORM cannot write (a NULL element, several dimensions, a non-default lower bound) fails to decode with `row_decode_failed`. |
| Text ordering | backend ordering plus the database collation | emulates PG NULL placement with `IS NULL` buckets, but does not inject a cross-engine collation | Do not depend on locale-sensitive or Unicode string ordering matching exactly across backends. |
| Ordering by `id` | sortable entity `id` columns pin `COLLATE "C"` | sortable entity `id` columns pin/use `BINARY` byte order | **Parity guarantee.** `id` is a base36 UUIDv7 typed id whose alphabet spans digits, uppercase, and lowercase. Both tiers compare its bytes, so `.sort({ id: -1 })` is newest-first and cursor range predicates use the same ordering. Ordinary text still follows the general text-ordering row above. |
| Timestamp resolution | microseconds. The Rust ORM returns every microsecond the server stored, so a value read back re-binds and matches its own row by equality | whole milliseconds, the resolution of SQLite's own clock and of the canonical fixed-width storage text. A finer value is **refused** with `ValidationFailed{timestamp_precision_unsupported}`, and nothing is written | **Refused, never floored.** Each backend declares its resolution as `SqlSupport::timestamp_resolution`, and the registration enforces it on the one path every written instant crosses. Flooring would return a *different* instant that then fails to match its own row, which is why the finer value is rejected where it is written instead. The same rule covers a sub-millisecond `TimestampExpr` offset and a sub-millisecond temporal field nested inside JSON. Carrying a PostgreSQL-derived instant into a SQLite database is therefore a typed failure, not a silent rounding. |
| Timestamps in JavaScript | the V8 adapter floors an outbound instant to the containing millisecond, toward negative infinity, and scales an inbound number | the same, and it is exact because SQLite stores no finer value | **The JavaScript contract is milliseconds on both backends**, so `env.db` is unchanged. On PostgreSQL that floor is lossy: a JavaScript caller that reads an instant and then filters by equality on it can miss the row it just read. Only the Rust API carries the microsecond. |
| Declared timestamp default precision | PostgreSQL timestamp defaults retain the database's native fractional precision | SQLite timestamp defaults use a UTC `strftime` expression with fractional seconds | Each default is stored at its own backend's resolution, per the row above. |
| Migration column-shape verify (existence-guard / drift) | compares the full `information_schema` type spelling | compares only the SQLite **type affinity** (`text`/`integer`/`real`/`numeric`/`blob`) | Several distinct SDK facets fold to the `text` affinity on SQLite (`string`/`ref`/`date`/`json`/…). A within-text-affinity facet change (e.g. `string`→`ref`) is invisible to SQLite introspection and is treated as **no change** by both the differ and the `ifNotExists` existence-guard probe (a `ref` adds no FK via `ALTER` on SQLite — it is physically the same `text` column). A genuine affinity change (`text`↔`real`, i.e. string↔number) IS detected. |
| Migration enum/domain types | `CREATE TYPE ... AS ENUM` and `CREATE DOMAIN` objects | inline column type plus `CHECK`/default/nullability at each use site | The logical constraint must match. SQLite does not create standalone named type objects. |
| Migration table `CHECK` constraints | intended closed-AST `CHECK` rendering | intended closed-AST `CHECK` rendering | Current op.* validate-refuses table-level `CHECK` until the expression renderer lands; enum/domain `CHECK` emulations are supported. |
| Migration table FK/UNIQUE constraints | table constraints render in `CREATE TABLE` | descriptor-backed `CREATE TABLE` path does not yet thread table-level FK/UNIQUE constraints | SQLite op.* validate-refuses these table-level constraints until the emitter carries them; use this as a migration-engine gap, not a runtime divergence. |
| Migration identity columns | `GENERATED {ALWAYS\|BY DEFAULT} AS IDENTITY` | `INTEGER PRIMARY KEY AUTOINCREMENT` only for the sole integer primary-key case | Other SQLite identity placements fail closed instead of emulating an unsound sequence. |
| Migration generated columns | STORED generated columns | STORED or VIRTUAL generated columns | The shared expression AST renders on both backends. Postgres virtual generated columns fail closed. |
| Migration triggers | function-backed triggers (`EXECUTE FUNCTION`) | closed inline `Body` triggers | The two trigger action forms are intentionally dialect-specific: SQLite `Body` triggers fail closed on Postgres, and Postgres `EXECUTE FUNCTION` triggers fail closed on SQLite. |
| Migration sequences/exclusion constraints | native standalone sequences and exclusion constraints | no sound general equivalent | SQLite fails closed on these PG-only facets. |
| Migration journal placement | six tables in the app's own schema, each prefixed `__zeroship_` (`"<app_uuid>".__zeroship_schema_migrations` and siblings) | six tables in a **separate attached database**, `<app>.migrations.<ext>`, with the **unprefixed** names (`schema_migrations` and siblings) | **Same records, different place, and the SQLite side needed no change on 2026-08-28.** The prefix exists on Postgres because the journal moved *into* the tenant's own schema: the engine bootstraps with `CREATE TABLE IF NOT EXISTS` and its table names are literals, so without a fenced prefix a creator declaring a table called `schema_migrations` would have it silently adopted as the journal. SQLite has no such collision to fence — its journal is a different database file, attached as `_mig`, and the backend never reads `meta_schema` at all (`crates/zeroship-migrate-backend/src/conn.rs`, the `meta_schema` doc; `crates/zeroship-migrate-sqlite/src/backend/backfill_sql.rs`). Renaming there would have churned the dev tier's on-disk journal for a hazard it does not have. A test or tool that names the journal must therefore branch on dialect. |
