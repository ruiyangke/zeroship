# SQLite divergences

The creator-facing CRUD surface is aligned across Postgres and SQLite — array updates share
complete-element and structural-equality semantics — so local development behaves like
production except where this page says otherwise.

**Local development is one app in one process.** `pnpm dev` runs a Vite dev server and
spawns a single dev runtime for that project, on one worker thread, backed by a file. A
second app means a second process, a second dev port and a second state directory — apps
never share a local process.

The remaining differences are in engine-specific search, transaction isolation, locking,
scoring, and ordering.

Most rows below are deliberate. Typed-ID ordering is retained as an explicit
parity guarantee because column collation prevents the databases from comparing
the generated values differently.

For the **migration** authoring surface, the equivalent boundary — which DML transforms are portable across both backends, the `.splitPart` portable-expression envelope, and the `EXPR_NOT_PORTABLE` hard error out of envelope — is documented in [migrate-op-dsl.md](./migrate-op-dsl.md#the-dml-portability-boundary).

## Current differences

| Area | Postgres | SQLite | Contract |
| --- | --- | --- | --- |
| Vector metrics | `pgvector` supports cosine, L2, and inner product | `sqlite-vec` `vec0` supports cosine and L2 only | `VectorMetric::InnerProduct` returns `vector_unsupported_metric` on SQLite. |
| Spatial search | PostGIS + GIST-backed `ST_DWithin` | no index build; `spatial_near` does a haversine flat scan over the stored geopoint BLOB | Result semantics aim to match, but the SQLite path is a dev-scale scan. |
| How a transaction opens | `BEGIN [ISOLATION LEVEL ...]`; the write lock is taken when the transaction first writes, and a conflicting writer is arbitrated by the isolation level | `BEGIN IMMEDIATE`, so the write lock is held from `BEGIN`, before the callback's first statement | **A transaction that only ever reads still takes the write lock.** The alternative is worse: under a plain `BEGIN` (SQLite's `DEFERRED`) the transaction's first read pins a snapshot and its first write must *upgrade*, and SQLite refuses an upgrade **without invoking the busy handler**, so the ten-second lock budget that every other statement spends is unavailable to the one statement that needed it - the second of two replicas over one file was refused outright instead of waiting its turn. The cost is that `IMMEDIATE` locks every database the connection has open, `main` included, so two apps on one backend now serialize their explicit transactions through `main` rather than overlapping; they serialize rather than deadlock, because `main` is database zero and every lane takes the locks in the same order. |
| Transaction isolation | An explicit level selects `BEGIN ISOLATION LEVEL ...`; omitting it uses the database default | Accepts the default or `serializable`; other levels return `unsupported_isolation_level` before the callback runs | Rust and V8 share this contract. Nested callbacks inherit the enclosing isolation and reject an explicit level with `nested_isolation_level`. |
| Transaction isolation under contention | two requests handled by different runtime threads hold genuinely concurrent transactions, and `serializable` arbitrates them: measured over 16 concurrent write-write pairs on one row, the loser returned `SERIALIZATION_FAILURE` and only one row landed, 16 times out of 16 | one thread, one isolate — the second transaction **waits** for the first, so both succeed and neither is ever aborted (16 of 16) | **A conflicting-writer abort is a production-only outcome; `pnpm dev` cannot produce one.** Two transactions for the same app on the *same* thread are serialized on both tiers, so the isolation level has no second writer to arbitrate there — this is why the deployed abort depends on the request landing on another thread and the local tier, which has only one, never sees it. Write for the production case: handle `SERIALIZATION_FAILURE` by retrying the whole transaction, and do not treat a clean local run as evidence that a transaction is conflict-free. |
| Ordinary writes overlapping a transaction | a write with no transaction in its call chain takes its own pooled connection, so it is unaffected by a transaction another request holds open — the transaction aborts and the ordinary write's row is still there | **same** — an explicit transaction and an autocommit write use separate connections, so an ordinary write is unaffected by an open transaction and survives its `ROLLBACK` | No divergence: an ordinary write takes its own connection on both tiers, so it survives a transaction's `ROLLBACK`. The remaining SQLite-only limit belongs to the engine — SQLite has **one writer per database** — so an autocommit *write* issued while an explicit transaction holds the write lock waits up to the ten-second lock budget and then reports lock contention. Concurrent *readers* are unaffected. |
| Concurrent `db.transaction()` calls | each transaction takes its own connection from a pool of **8** for the process, so several can be open at once; a transaction beyond the pool **waits** up to 30 seconds for a free connection and fails only if that wait expires | one transaction connection **per app**, opened on that app's first `db.transaction()`, so a second one *for the same app* is **refused immediately** with `TRANSACTION_CONNECTION_BUSY` | **A second transaction for one app fails on the dev tier where it would have succeeded deployed, and it fails instantly rather than waiting.** Two things differ, not one: the *ceiling* (eight for the process vs. one per app) and the *response to hitting it* (queue vs. refuse). Do not treat a clean local run as evidence that concurrent transactions work. Neither ceiling is configurable. `TRANSACTION_CONNECTION_BUSY` always means *your* app, and the message names it; the same code is also raised on both tiers for a genuinely overlapping pair of operations *inside one* transaction (`Promise.all` over `tx.*` calls), and the message distinguishes the two cases. |
| Many apps in one dev process | no ceiling of this kind — connections come from a pool sized per worker | a session holds at most **8** apps' transaction connections; an idle one is closed to make room, and only a session where all 8 are mid-transaction refuses, with `TRANSACTION_LANES_EXHAUSTED` | **A distinct code because the remedy is distinct**: `TRANSACTION_CONNECTION_BUSY` is your own overlapping transaction; `TRANSACTION_LANES_EXHAUSTED` would be contention with other apps sharing a dev process and is not a fault in your code — retry. Unreachable in local development, which runs one app per process. |
| Write contention | backend-native locking | WAL mode + single writer actor; busy-family SQLite errors collapse to the same typed lock-contention surface | Callers should branch on the typed error code, not raw SQLite error text. |
| Opening a file another process holds | the server arbitrates connections | every connection's busy timeout is the ten-second lock budget, set before the first statement that takes a lock, and the switch to WAL is retried within that same budget | **A contended open waits; it does not refuse at once.** The retry is there because SQLite does not invoke the busy handler when the switch's read transaction upgrades to a write while another connection holds the write lock - a bootstrap's `BEGIN IMMEDIATE`, for instance. A hold that outlasts the budget still surfaces as typed lock contention. |
| Journal mode of app data | not applicable — one Postgres cluster, MVCC | the session's own database is **WAL**, but each database's `zs-<schema>.sqlite` is **DELETE** (rollback journal). `PRAGMA journal_mode` is per database and does not propagate across `ATTACH`, and the migration engine pins app files to DELETE and refuses to run otherwise | **WAL's reader-writer concurrency does not apply to your app's own tables.** A reader still proceeds while a writer holds `RESERVED`, so ordinary overlapping reads are fine, but there is no per-connection snapshot and a `SQLITE_BUSY_SNAPSHOT` write-upgrade conflict cannot arise on app data — an upgrade conflict there is a plain `SQLITE_BUSY` rather than a snapshot conflict. An upgrade from a held read transaction is refused immediately rather than waiting out the ten-second lock budget: whether SQLite invokes the busy handler turns on the transaction already holding a read transaction, never on the journal mode, so the difference between the two files is which busy code a caller gets and not how long it waits. No creator transaction reaches that upgrade, because a transaction opens with `BEGIN IMMEDIATE`; see the row on how a transaction opens. |
| Native text arrays | `textArray` columns are `text[]`, bound in the binary array protocol; equality is array equality | the same declarations are JSON text | **Same logical results.** Order and duplicates are significant in equality on both; `pull` removes every equal element and `addToSet` keeps existing duplicates on both; SQL NULL, `[]` and `["NULL"]` stay distinct; null and NUL elements are refused on write on both. Only raw SQL sees the difference (`{a,b}` versus `["a","b"]`). A PostgreSQL value the ORM cannot write (a NULL element, several dimensions, a non-default lower bound) fails to decode with `row_decode_failed`. |
| Text ordering | backend ordering plus the database collation | emulates PG NULL placement with `IS NULL` buckets, but does not inject a cross-engine collation | Do not depend on locale-sensitive or Unicode string ordering matching exactly across backends. |
| Ordering by `id` | sortable entity `id` columns pin `COLLATE "C"` | sortable entity `id` columns pin/use `BINARY` byte order | **Parity guarantee.** `id` is a base36 UUIDv7 typed id whose alphabet spans digits, uppercase, and lowercase. Both tiers compare its bytes, so `.sort({ id: -1 })` is newest-first and cursor range predicates use the same ordering. Ordinary text still follows the general text-ordering row above. |
| Timestamp resolution | microseconds. The Rust ORM returns every microsecond the server stored, so a value read back re-binds and matches its own row by equality | whole milliseconds, the resolution of SQLite's own clock and of the canonical fixed-width storage text. A finer value is **refused** with `ValidationFailed{timestamp_precision_unsupported}`, and nothing is written | **Refused, never floored.** The resolution is enforced where an instant is written, on both backends. Flooring would return a *different* instant that then fails to match its own row, which is why the finer value is rejected where it is written instead. The same rule covers a sub-millisecond `TimestampExpr` offset and a sub-millisecond temporal field nested inside JSON. Carrying a PostgreSQL-derived instant into a SQLite database is therefore a typed failure, not a silent rounding. |
| Timestamps in JavaScript | the V8 adapter floors an outbound instant to the containing millisecond, toward negative infinity, and scales an inbound number | the same, and it is exact because SQLite stores no finer value | **The JavaScript contract is milliseconds on both backends**, so `env.db` is unchanged. On PostgreSQL that floor is lossy: a JavaScript caller that reads an instant and then filters by equality on it can miss the row it just read. Only the Rust API carries the microsecond. |
| Declared timestamp default precision | PostgreSQL timestamp defaults retain the database's native fractional precision | SQLite timestamp defaults use a UTC `strftime` expression with fractional seconds | Each default is stored at its own backend's resolution, per the row above. |
| Binding capability and masking | a binding IS a cluster role, and its two memberships are the tenant boundary: `GRANT <capability> TO <binding> WITH SET FALSE` and `GRANT <binding> TO <worker> WITH INHERIT FALSE` (`grant_binding_statements`, `crates/zeroship-migrate-server/src/datastore/cluster.rs`). Column masking rides the capability roles' grants, and a withdrawn binding is refused by the server with `42501` | there are no roles and no column ACLs. The dev binding is unconditionally read-write (`DEV_CAPABILITY`, `crates/zeroship-cli/src/dev_binding.rs`, whose rustdoc says it is the creator's own database on the creator's own machine with no control plane to have declared otherwise), so a `readonly` binding has nothing to represent it, and what production enforces in the catalog the dev tier enforces in process | **A dev-tier pass is not evidence about production for any binding, capability or revocation behaviour.** A write that a read-only binding must be refused still succeeds here, and revoking a binding is not observable at all. Anything asserting capability, masking or revocation has to run against `PostgreSQL`, where `crates/zeroship-data-orm/tests/postgres_tenant_fence.rs` holds those arms. |
| Migration column-shape verify (existence-guard / drift) | compares the full `information_schema` type spelling | compares only the SQLite **type affinity** (`text`/`integer`/`real`/`numeric`/`blob`) | Several distinct SDK facets fold to the `text` affinity on SQLite (`string`/`ref`/`date`/`json`/…). A within-text-affinity facet change (e.g. `string`→`ref`) is invisible to SQLite introspection and is treated as **no change** by both the differ and the `ifNotExists` existence-guard probe (a `ref` adds no FK via `ALTER` on SQLite — it is physically the same `text` column). A genuine affinity change (`text`↔`real`, i.e. string↔number) IS detected. |
| Migration enum/domain types | `CREATE TYPE ... AS ENUM` and `CREATE DOMAIN` objects | inline column type plus `CHECK`/default/nullability at each use site | The logical constraint must match. SQLite does not create standalone named type objects. |
| Migration table `CHECK` constraints | intended closed-AST `CHECK` rendering | intended closed-AST `CHECK` rendering | Table-level `CHECK` is not supported on either backend; `enum` and `domain` `CHECK` emulations are. |
| Migration table FK/UNIQUE constraints | table constraints render in `CREATE TABLE` | descriptor-backed `CREATE TABLE` path does not thread table-level FK/UNIQUE constraints | Table-level `FK`/`UNIQUE` constraints are not supported on SQLite; a column-level `.references()` facet is threaded and enforced. Treat the table-level gap as an authoring gap, not a runtime divergence. |
| Migration identity columns | `GENERATED {ALWAYS\|BY DEFAULT} AS IDENTITY` | `INTEGER PRIMARY KEY AUTOINCREMENT` only for the sole integer primary-key case | Other SQLite identity placements fail closed instead of emulating an unsound sequence. |
| Migration generated columns | STORED generated columns | STORED or VIRTUAL generated columns | The shared expression AST renders on both backends. Postgres virtual generated columns fail closed. |
| Migration triggers | function-backed triggers (`EXECUTE FUNCTION`) | closed inline `Body` triggers | The two trigger action forms are intentionally dialect-specific: SQLite `Body` triggers fail closed on Postgres, and Postgres `EXECUTE FUNCTION` triggers fail closed on SQLite. |
| Migration sequences/exclusion constraints | native standalone sequences and exclusion constraints | no sound general equivalent | SQLite fails closed on these PG-only facets. |
| Migration journal placement | six tables in the app's own schema, each prefixed `__zeroship_` (`"<app_uuid>".__zeroship_schema_migrations` and siblings) | six tables in a **separate attached database**, `<app>.migrations.<ext>`, with the **unprefixed** names (`schema_migrations` and siblings) | **Same records, different place.** The prefix exists on Postgres because the journal lives inside the tenant's own schema and its table names are literals: without a fenced prefix, a creator declaring a table called `schema_migrations` would have it silently adopted as the journal. SQLite has no such collision to fence — its journal is a separate attached database file. A test or tool that names the journal must therefore branch on dialect. |
