# Portable autoIncrement intent — design (DSL v2, all vendors)

**Status:** approved for build 2026-07-04. Layer-1 PORTABLE intent (Core). Creator feature (no platform use).
**Goal:** `t.int().autoIncrement()` / `t.bigInt().autoIncrement()` — one intent, lowered per dialect.

## Surface + IR

`autoIncrement()` is sugar for the existing identity facet at BY-DEFAULT strength:
`t.bigInt().autoIncrement()` ≡ `IdentityCol { always: false }`. No new IR facet — reuse `IdentityCol`.
- `always: false` (autoIncrement / identity-by-default) → **portable** (renders on all 3).
- `always: true` (explicit `.identity({ always: true })`) → **PG-vendor** (strict mode; no SQLite/MySQL equivalent).

## Per-vendor lowering (for `always: false`)

| dialect | render | note |
|---|---|---|
| Postgres | `… GENERATED BY DEFAULT AS IDENTITY` | column-type suffix (already works) |
| SQLite | `<col> INTEGER PRIMARY KEY AUTOINCREMENT` | **the column carries the PK INLINE** — see below |
| MySQL | `<col> BIGINT AUTO_INCREMENT` (column stays a key) | key requirement |

### The SQLite structural interaction (the hard part)

SQLite auto-increment requires the column be declared *exactly* `INTEGER PRIMARY KEY AUTOINCREMENT`, which is an
**inline column PK** — so when the create-table renders a SQLite autoincrement column, it must emit the PK ON THE
COLUMN and SUPPRESS the separate table-level `PRIMARY KEY (col)` clause for that column (SQLite rejects a column
that is both `INTEGER PRIMARY KEY` inline and named in a table PK). The column's declared type is forced to
`INTEGER` (SQLite ignores width; `BIGINT` won't alias rowid). This is a render-time interaction between the
column facet and the table PK — the main implementation risk.

## Validation

`always: false` (portable autoIncrement):
- valid on integer column types (Int / BigInt / SmallInt).
- on **SQLite/MySQL**: requires the column be the **single-column PRIMARY KEY** (SQLite `INTEGER PRIMARY KEY`,
  MySQL key). If it is not the single-col PK, the portable intent can't be honored → reject fail-closed on those
  dialects (on PG it's fine on any column, but for a PORTABLE authoring the DSL should require the PK shape).
- mutually exclusive with `.default(...)` and `.generatedAs(...)` (a column can't be a counter AND a default/formula).

`always: true` (PG-vendor identity): PG-only (unchanged); SQLite/MySQL reject.

## Verify (heavier — it's portable, must apply on PG + SQLite)

- Render tests: `always:false` → `GENERATED BY DEFAULT AS IDENTITY` (PG), `INTEGER PRIMARY KEY AUTOINCREMENT`
  with no duplicate table PK (SQLite), `AUTO_INCREMENT` (MySQL, render only).
- Validate tests: autoIncrement on a non-PK / composite-PK / non-integer column rejected on SQLite/MySQL;
  autoIncrement + a `.default()` rejected (facet conflict).
- Round-trip APPLY: a createTable with `id INTEGER autoIncrement PK` applies + inserts auto-assign correctly on
  live PG (:5440) AND in-process SQLite. (Reuse an existing PG + SQLite apply test harness.)
- Serde-omission: absent = byte-identical (no CURRENT_IR_VERSION bump).
- ops.test.ts: `t.int().autoIncrement()` emits `identity { always: false }`; public-vs-engine parity.

## Slice
- Single engine+surface slice (no platform re-author — the platform uses explicit PG identity/nextval, not the
  portable intent). Extend identity render (SQLite/MySQL) + validate + `autoIncrement()` surface twin + tests.
