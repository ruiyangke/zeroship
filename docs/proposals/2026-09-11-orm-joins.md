# Shared ORM joins

**Status: In progress.** Explicit joins use the shared ORM read operation,
with Rust model projections and a TypeScript adapter. Collection reads use the
same SQL statement compiler. Named forward loading lives in the shared ORM;
its contract and remaining scope are in [Named ORM relations](2026-09-13-orm-relations.md).

Support joins through the shared Rust ORM so native applications and V8 workers
have the same query, transaction and protection semantics. Keep the existing
crate boundaries and plain driver contract.

## Scope and result semantics

Support explicit `INNER JOIN` and `LEFT JOIN`, chained joins, self-joins with
distinct aliases, and composite equality conditions. An explicit join does not
require a declared foreign key. Every source must belong to the same database
binding and installed deployment descriptor. Cross-binding joins are refused.

Join conditions use typed, source-qualified column references and bound values.
Require an equality connecting the new source to a preceding source; additional
conditions may narrow the match. Initial join keys must be compatible,
unprotected scalar fields. Do not admit SQL fragments, implicit cross joins or
unsupported join kinds. Runtime validation applies even when a language's type
checker has already checked the expression.

Explicit joins return matching row combinations. They preserve duplicates and
apply sorting, pagination and aggregation to that joined row set. Joining a
parent to several children repeats the parent. There is no automatic
deduplication or assembly of child arrays.

Relation loading remains a separate operation. Move the existing TypeScript
`with` loader into the ORM so Rust can use it too. Loading related collections
must preserve the selected parent page. Use a join for a proven to-one edge and
batched child queries for to-many edges. Composite keys and non-primary unique
targets must use their actual relation metadata; never assume every reference
targets `id`. Named relation convenience derives from migration metadata;
explicit joins remain available when inference is ambiguous.

These choices follow established patterns: Diesel exposes nullable joined rows
and explicit join conditions; Django distinguishes joined to-one loading from
prefetching collections; SQLAlchemy distinguishes query joins from eager loading
and handles row multiplication explicitly. [Diesel](https://diesel.rs/guides/relations.html),
[Django](https://docs.djangoproject.com/en/6.0/ref/models/querysets/#select-related),
[SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/queryguide/relationships.html).

## Proposed application surface

The fluent methods below construct a query description. They never execute
arbitrary callbacks inside the database or accept SQL text.

```ts
import { eq } from "@zeroship/db";

const o = env.db.orders.as("o");
const c = env.db.customers.as("c");

const { data, error } = await env.db.from(o)
  .leftJoin(c, eq(o.columns.customerId, c.columns.id))
  .where(eq(o.columns.status, "paid"))
  .select({ order: o.row(), customer: c.optionalRow() })
  .orderBy(o.columns.id.asc())
  .limit(pageSize)
  .all();
```

The result is shaped as `{ order: Order, customer: Customer | null }`.
`order.customerId` retains the foreign-key value. A missing customer makes the
whole customer projection null; it does not produce a customer-shaped object
whose fields happen to be null. The TypeScript adapter keeps the existing
`Result` envelope. Transaction views use the existing throwing convention.

Rust uses generated collection and column metadata, native values and the
existing model decoders:

```rust,ignore
let o = db.entity::<schema::orders::Entity>()?.alias("o")?;
let c = db.entity::<schema::customers::Entity>()?.alias("c")?;

let rows: Vec<(OrderSummary, Option<CustomerSummary>)> = db
    .from(&o)
    .left_join(
        &c,
        o.column(schema::orders::customerId)
            .eq_column(c.column(schema::customers::id))?,
    )?
    .select((o.row::<OrderSummary>(), c.optional_row::<CustomerSummary>()))?
    .order_by(o.column(schema::orders::id).asc())
    .limit(page_size)?
    .all()
    .await?;
```

Generated names follow the descriptor. The model types above are application
projections with `FromRow` implementations. A nullable source requires an
optional projection. Arbitrary named scalar projections are also supported,
with output nullability derived from the source and expression.

## Ownership and planning

```text
Rust query builder                 TypeScript query builder
        |                                  |
        |                            zeroship-data-v8
        |                            capture native input
        +------------------+---------------+
                           |
                   zeroship-data-orm
             resolve every source and binding
             apply visibility and protection
             capture transaction and read dependencies
             prepare query and result layout
                           |
                zeroship-data-orm::sql
              typed relational SELECT plan
              PostgreSQL / SQLite rendering
                           |
                   scoped executor
                   existing driver
                   SQL + parameters
                           |
                ORM result materialization
              Rust models / V8 native values
```

Extend the existing `Select` plan with aliased sources and ordered joins. Add a
source identity to column references, separately from nested JSON paths, and
support column-to-column comparisons. Preserve outer-join order during
canonicalization. Qualify columns in projections, `ON`, filters, grouping,
having and ordering. Parameters remain native values.

The ORM prepares all source descriptors and the transaction route before
execution yields. Its result layout records output slots, source collection,
logical field, codec, protection metadata and nullable-source identity.
Internal SQL aliases must be unique even when several sources expose `id` or
`name`. They never become creator field names.

Reuse `FromRow` for each entity projection. A joined-result decoder splits the
native row according to the prepared layout and supplies each model its own
fields. Hidden non-null identity columns distinguish an unmatched source from
a matched row whose selected fields are all null. They also supply row-bound
encryption and unmask identity. Hidden fields are stripped before delivery.
Grouped results use expression decoding rather than entity decoding; injecting
entity identity columns must never change a grouping.

Route ordinary reads, joined reads and aggregates through the same relational
planner. Do not add a separate SQL-string compiler for joins. The ORM SQL
module owns syntax and plan validation; it does not acquire connections or load policy.
The driver gains no join or relation methods. No additional crate is needed.

## Visibility, protection and consistency

Apply descriptor validation, available authorization rules and soft-delete
visibility to every source. A query cannot acquire another binding's authority
through an alias. Host-generated visibility conditions on the nullable side of
a left join must preserve the outer join:

```sql
FROM orders AS o
LEFT JOIN customers AS c
  ON o.customer_id = c.id
 AND c.deleted_at IS NULL
WHERE o.deleted_at IS NULL
```

Caller predicates retain their SQL location: filtering `c.active` in `WHERE`
intentionally removes unmatched parents; placing it in `ON` narrows matches
while preserving those parents.

Every projected protected field retains its original collection, logical field
and row identity through decoding. Aliases cannot select reserved raw storage,
change AAD identity or bypass unmask authorization and audit. Join predicates
reject masked and encrypted operands. Existing protected-field restrictions
also apply to filters, sorting and grouping; the initial joined aggregate
surface rejects protected operands. Explicit unmask uses the original source
identity and keeps the independent audit-write contract.

All SQL runs through the captured transaction route. Relation-loading batches
reuse that route and run sequentially when a transaction owns the session.
A joined SELECT has statement-level consistency. Batched relation loading
does not promise a shared snapshot outside a transaction with suitable
isolation; it must not silently open a stronger transaction.

Record every participating collection as a read dependency, including sources
that produced no rows. Join subscriptions initially use collection-level
invalidation: a changed row can enter or leave the result through another table,
so independent row predicates are insufficient. Re-reads use normal protection.

## Aggregation, bounds and delivery

Support grouped joins with `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, distinct counts,
`HAVING`, ordering and limits. `COUNT(*)` counts joined rows; counting the
nullable side's identity counts matches. Parent counts require explicit
distinct parent identity. Aggregation across several to-many joins retains SQL
row multiplication; the ORM must not silently correct it.

Backend lowering must cover every accepted expression. The current `$first`
compiler emits PostgreSQL-specific SQL; it needs defined ordered semantics and
SQLite lowering before it can be advertised as portable. Unknown stages and
unsupported expressions must fail during preparation.

Bound sources, predicate depth, parameters, output rows and decoded result size.
Row limits do not bound database join work, so retain statement deadlines and
cancellation. Relation loading must also bound total child rows and batch work;
exceeding a budget returns an error rather than silently truncating a collection.
Pagination requires an explicit deterministic ordering; keyset cursors identify
the joined row combination, including nullable sources, rather than only the
root row. Parent cursors remain appropriate for parent-preserving relation loads.

Deliver the shared source/expression plan and renderers first, then the ORM
result layout and typed Rust API, then the V8/TypeScript adapter. Relation
loading now uses shared ORM planning. Update
the existing read and aggregate callers during the compiler change; do not
maintain competing production implementations or compatibility aliases.

Acceptance belongs to ordinary Rust tests with owned PostgreSQL containers and
temporary file-backed SQLite databases, plus TypeScript adapter tests:

- Inner/left, self/chained and composite joins; duplicate column names and nulls.
- Unmatched sources versus matched rows with nullable projections.
- Parent paging for relation loading versus tuple paging for explicit joins.
- Grouped left joins, distinct counts and backend-equivalent results.
- Descriptor, type, alias and binding refusals; protected-field provenance.
- Transaction visibility, scope expiry, cancellation and connection reuse.
- Invalidation when a participating collection changes an initially empty result.
- Query/batch budgets and eager loading without per-parent query loops.
