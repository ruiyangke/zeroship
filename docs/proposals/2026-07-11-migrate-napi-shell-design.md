# The standalone Node/Bun napi shell for `zeroship-migrate` — design

> **Historical design snapshot.** Package paths and package boundaries below
> describe the 2026-07-11 tree. The live DSL is the single
> `@zeroship/migrate` package at `packages/zero-migrate/`.

**Status:** proposed 2026-07-11. New end product: `@zeroship/migrate` as an npm package = a napi (`.node`) addon over the V8-free `zeroship-migrate` core + the existing TS authoring DSL + host-provided DB drivers. Branch `design/migrate-napi-shell`. Design-only; commit-only; no code shipped by this doc.

**Goal.** Ship `zeroship-migrate` as a **standalone, Node-embeddable migration engine (Bun best-effort, gated — §E.2)** — one npm package a creator installs and calls, with no Rust toolchain, no V8-in-Rust, and no io_uring dependency. Node is the primary, fully-supported target; Bun ships only if its Phase-D full-`apply` journal-identity gate passes, and drops to unsupported (Node-only) if it reds. The Rust core stays V8-free and runs its own async runtime on worker threads via napi (N-API); the JS **host** supplies the JS half — `schema.js` authoring (the TS DSL already in `sdks/migrate/`) and the DB drivers (`pg` / `mysql2` / `bun:sqlite`|`better-sqlite3`) as host-callback `PgSession` impls over napi threadsafe-functions. **No second V8 is embedded in Rust.** The blueprint is Temporal's TS SDK worker: a V8-free Rust core + state machines, N-API as the channel boundary only, the JS event loop as a peer.

**The platform's embedded Rust path is UNAFFECTED.** The in-repo control/worker embed of `zeroship-migrate` with `zsv8` + `native-pg` (compio/io_uring, in-Rust V8 recorder, live compio `Client`) continues to exist and stays green throughout. The napi shell is a *third* build shape of the same core rlib, not a replacement — the two are independent feature axes (§4).

This design builds on two landed milestones on this branch's base:
- **Phase 1 — V8 decoupling** (`docs/proposals/2026-07-10-migrate-runtime-decoupling-design.md`): a V8-free core behind `zsv8`; `src/frontend/` (JS authoring recorder) and `src/apply/backend/mysql/` (mysql2 isolate) are the only V8 users; `--no-default-features` compiles V8-free.
- **Phase 2 — Postgres driver seam** (`docs/proposals/2026-07-10-migrate-pg-driver-seam-design.md`): `trait PgSession` + generic `PostgresBackend<'a, D: PgSession = Client>`, compio behind a default-on `native-pg`. It made the **write path** run-proven-generic and explicitly flagged the **read path** (`query`/`query_one` returning the concrete `compio_postgres::Row`) as a hard prerequisite for any second driver.

Two sibling phase-maps on this branch feed this doc and are referenced, not re-specified:
- `docs/proposals/2026-07-11-migrate-napi-host-boundary.md` — the JS-host boundary (authoring host-side, host-callback drivers, npm API).
- `docs/proposals/2026-07-11-migrate-napi-node-addon-build-shape.md` — the crate/feature/platform shape (cdylib crate, executor decision, Bun caveats).

This document is the **consolidated top-level design**: it sequences the whole arc (SeamRow widening → host-pg impl → napi crate → JS package), fixes the crate/feature shape, and carries the unified phased plan + risk register.

## 1. Objective + non-goals

**Objective.** Produce a standalone `@zeroship/migrate` npm package whose engine is the `zeroship-migrate` Rust core compiled to a napi `.node` addon, driven entirely from JS: the JS host authors migrations with the existing TS DSL (producing `.ir.json`), the Rust core validates/plans/applies, and every DB verb bottoms out in a host-supplied JS driver (`pg`/`mysql2`/`sqlite`) over a napi threadsafe-function callback. The addon carries **no V8** (Node/Bun *is* the V8), **no compio/io_uring** (cross-platform), and native `rusqlite` for the SQLite leg.

**The end state, concretely:**

```ts
import { apply, plan, dryRun, generate } from "@zeroship/migrate/host";

// PG via the host's own `pg` driver — no compio, cross-platform:
await apply({ dir: "./migrations", driver: { kind: "postgres", url: process.env.DATABASE_URL } });
```

`apply` = host authors the IR envelopes (pure JS, via the TS DSL) → the addon deserializes, stamps `owner_app`, folds the authoritative checksum, runs the differ/planner/guard/executor, and drives all DB I/O through the registered host `SeamSession` threadsafe-function against the host `pg`/`mysql2`/`sqlite` wrapper.

**Non-goals (explicitly out of scope):**

- **No change to the platform's embedded RUNTIME BEHAVIOR.** The control/worker embed (`zsv8` + `native-pg`, compio `Client`, in-Rust V8 recorder) keeps **byte-identical runtime behavior and SQL** — same statements, txn boundaries, lock/journal ordering, decoded domain values. What *does* change is its **Rust type surface**: the `PgSession` trait's bind param type, its read-verb return type, its error type, seven `From` impls, and ~26 decode-site bodies are mechanically rewritten to route through `SeamBind`/`SeamRow`/`SeamError` (§A.8 blast-radius table). This is a real, review-worthy source change to security-audited code, not a no-op — but it is behavior-preserving by construction and gated by re-running the full native suite including the journal-immutability/guard/rollback tests (§7). The napi shell adds a build shape; it deletes nothing from the embedded axis.
- **No second V8 in Rust.** The napi addon has `zsv8` **off**. Authoring runs in the *host's* JS engine using the existing TS DSL; the MySQL driver runs in the *host's* `mysql2`, not an in-Rust isolate. This is the whole point of the V8-decoupling: Node/Bun already is the JS engine.
- **No compio/io_uring in the addon.** io_uring is Linux-only; the addon must be cross-platform. PG+MySQL are host-provided (no compio, no compio-mysql); SQLite is native `rusqlite` (cross-platform, no compio). The addon's engine runs on a minimal `futures::executor`, not compio, not tokio (§C.4).
- **No back-compat / no dual-source authoring.** The TS DSL (`sdks/migrate/`) is the *sole* authoring surface both for the embedded recorder and the host — they already compile to one byte-identical recorder artifact. The host does not get a second, JS-only DSL fork.
- **No hosted multi-tenant sandbox in the addon.** Pure-JS host authoring drops the in-Rust V8 sandbox (resource budget + wall watchdog + no-fs/no-net that the recorder isolate gave untrusted `up()`). That is fine for the **trusted local/self-host posture** (today's `SandboxPosture::Local`); a multi-tenant hosted recorder must re-establish sandboxing host-side (worker + `vm` + timeout) or keep the in-Rust V8 recorder service for that one posture. Scoped as a deliberate posture decision (§5.1), not delivered here.
- **~~No shadow dry-run on the host/addon path (v1).~~ SUPERSEDED — host-side shadow dry-run is now IN scope for v1 (§F).** <!-- Revised: addressing USER DECISION — host-side shadow dry-run is folded INTO v1 so the addon matches the platform's pre-apply safety. The earlier "scoped OUT" stance is retired; the structural facts below are retained as the STARTING POINT §F builds on. --> The engine's headline pre-apply safety check — the **shadow dry-run** (`MigrationEngine::dry_run`/`dry_run_declarative`, `engine.rs:1929,1958`), which provisions a real throwaway schema copy and validates the destructive/declarative plan before touching the live DB — was structurally unavailable on the addon path as of the driver-seam base, and **v1 now reconstructs it host-side (§F)** so the addon carries the **same shadow-verification semantics as the embedded `PgShadow`** — same destructive/declarative verdict — **but with a deliberate credential-topology change: the host path splits `CREATEDB`/`CREATEROLE` off the migrator connection into a distinct admin DSN** (native fuses them onto one privileged migrator connection; §F.1). So it is NOT "identical connection topology / host==native verb-for-verb"; it is "the same pre-apply *verdict*, with the admin privilege supplied as a separate DSN" — a least-privilege improvement (§F.1, §F.5). Both paths still inherit `seed_shadow_from_live`'s fidelity scope — no triggers/functions/sequences/DEFAULTs/row-data, `shadow.rs:709-720` — so the guarantee is "as strong as the platform's shadow", not "as strong as touching the live DB"; §F.5. The starting-point facts §F builds on, verified in code: the concrete-`Client` constructor `PostgresBackend::new(conn)` (`postgres.rs:51`) sets `shadow: Some(PgShadow::new(conn))`, while the generic constructor `PostgresBackend::new_generic(conn)` (`postgres.rs:69`) sets `shadow: None` (`shadow()` at `postgres.rs:306` returns `self.shadow.as_ref()…`). The `DryRunError::ShadowUnsupported` arm is preserved as the honest failure mode for backends that still have no shadow (host SQLite Option B; any driver that cannot supply a second admin connection) — mirroring the SQLite backend's own `ShadowUnsupported` at `sqlite/mod.rs:763`. §F specifies the host shadow harness concretely as **three** host connections (vs native's **two** — the split above): a **distinct admin** `SeamSession` (`shadow.adminUrl`, `CREATEDB`+`CREATEROLE`) for `CREATE DATABASE`/`DROP DATABASE` + cluster-global `DROP ROLE` **and the read-only live `snapshot_schema` seed** (declarative/incremental arm only — kept on the admin endpoint so seed-source and shadow-target share a cluster, §F.1 cluster-sameness invariant); a **shadow-target** `SeamSession` (opened by the injected shadow-open callback) that runs `CREATE SCHEMA` + `provision_migrator` + the seeded shadow apply; and the least-privileged **migrator** `SeamSession` (`driver.url`) which issues **NOTHING in the shadow pre-flight** — it is only the live-apply connection a subsequent `apply` would use. (Two arms: **plain `dry_run` does NOT seed at all** — `shadow.rs:317` runs `executor::apply` on an EMPTY shadow; only `dry_run_declarative`/`dry_run_incremental` take the seed snapshot, `shadow.rs:390,462`; §F.1.) Native fuses migrator+admin+seed onto one `admin_conn` `&Client` (`shadow.rs:318`); the host split moves `CREATEDB` off the migrator to the admin credential — the deliberate least-privilege behavior change (§F.1). Plus host-callable role provisioning (`role::{provision_migrator, deprovision_migrator, exec_retry}` — un-gated from `#[cfg(feature="native-pg")]` and generalized off `admin: &Client` to `admin: &D: PgSession`; `exec_retry` runs on the **shadow-target** connection for `provision_migrator` at `shadow.rs:680` **AND on the admin connection for `deprovision_migrator` at teardown, `shadow.rs:1141`** — two call sites, §F.2/§F.3), the tokio-free re-home of `role.rs:163`'s `compio::time::sleep` (≤280ms cumulative worst case) + the `role.rs:158` transient-error match re-established **message-only over `SeamError.message`** (mirroring native's message-only match, no SQLSTATE fork, §F.2), and a **per-verb watchdog** so a hung host driver cannot leak the shadow DB + role (§F.4). (The manifest-verifying `apply_declarative_verified` remains a *different* thing — it never touched `backend.shadow()` and was always generic-safe.)

**What this doc delivers as design:** the two-sided seam widening (§A — `SeamBind` param side + `SeamRow`/`SeamError` read side, the prerequisite), the host-callback `PgSession` bridge (§B), the napi cdylib crate + feature matrix + executor decision (§C), the JS half (§D — authoring, drivers, npm API), the cross-platform/Bun build story (§E), the **host-side shadow dry-run harness (§F — a second pinned host connection to a throwaway shadow DB, host-callable role provisioning, and the tokio-free re-homed retry)**, and a phased plan + risk register (§7–§8).

## §A. Seam widening — BOTH sides of the trait (the PREREQUISITE)

**This is the gate on everything else, and it is TWO symmetric widenings, not one.** Phase 2's seam made the write verbs *dispatch* generically, but the `PgSession` trait is still typed in `compio_postgres` types on **both** the call side and the return side:

- **Return side (READ widening, §A.2–A.8).** `query`/`query_one` return the concrete `compio_postgres::Row`; every verb returns `compio_postgres::Error`. Both have **private constructors** → a host (napi) driver *cannot build a return value*. Until this widens, the Node driver cannot RETURN rows.
- **Call side (PARAM widening, §A.1).** `query`/`execute`/`query_one` still take `params: &[&(dyn ToSql + Sync)]` (verified in `session.rs:39,51,54`). `ToSql` is a `compio_postgres` trait whose `to_sql` serializes each value to PG **binary wire format** (bytes + type OID) — *not* to a JS-marshalable value. A host `PgSession::query` handed `&[&dyn ToSql]` has **no way to extract cells** to send over the threadsafe-function boundary without re-implementing PG binary encoding. Until this widens, the Node driver cannot be CALLED.

These are two independent blockers of equal blast radius, and both must land in Phase A so the native suite proves them together. The read side is the larger design surface (a whole value union); the param side is a small, mechanical enum-swap at ~29 construction sites — but it is the true gate on a host driver being *invokable at all*, so it is specified **first** (§A.1) before the read union (§A.2+).

§A lands **compio-first** — the compio impl is the first `SeamBind`→`ToSql` mapper and the first `Row`→`SeamRow` producer, so the platform's native path proves both widenings before any host driver exists.

### A.1 The PARAM side — `SeamBind`, and the ~29 bind-slice rewrite

<!-- Added: addressing BLOCKER — the param-side ToSql widening was entirely unaddressed. -->

**The census of what actually gets bound.** A grep of every `&[&…]` bind-slice literal on a `query`/`execute`/`query_one` call across the PG apply path (`journal.rs`, `drift.rs`, `executor.rs`, `baseline.rs`, `precondition.rs`, `backend/postgres/{backfill,shadow}.rs`) shows the bound-value union is **only two Rust shapes**:

| Bound Rust type | Sites | Example |
|---|---|---|
| `&str` / `&String` (schema names, versions, checksums, actors, table/column idents, `deploy_id`, cursor `lc`) | ~26 of the ~29 slices | `journal.rs:1013` `&[&version, &name, &checksum, &applied_by]`; `drift.rs:626` `&[&project_schema]`; `backfill.rs:833` `&[&lc]` |
| `&i64` (`exec_ms` only) | `journal.rs:983` (`record_rolled_back`, `exec_ms: i64`), `journal.rs` `record_applied` | `&[&version, &name, &checksum, &rolled_back_by, &exec_ms]` |

No bool bind, no NULL bind, no decimal bind, no array bind reaches `execute`/`query` today (verified — every bind ident is a `&str`/`&String` except `exec_ms`). But to future-proof against the IR bind domain and to mirror the already-proven `render::step::BindValue` fold exactly, `SeamBind` covers the full `BindValue` shape (this is the enum the MySQL `JsDriverBackend` already marshals to JSON via `bind_to_json`, `transport.rs:596-601`):

```rust
// mirrors render::step::BindValue exactly, so the IR-fold path and the
// PgSession bind path share ONE neutral shape.
pub enum SeamBind {
    Null,
    Bool(bool),
    Int(i64),        // exec_ms; the only integer domain the IR admits
    Decimal(String), // canonical decimal string (no f64 in the IR identity)
    Text(String),    // schema/version/checksum/actor/ident/cursor
}
```

**The trait is re-typed to take `&[SeamBind]`:**

```rust
// error type widens on ALL FIVE verbs (§A.8); the SeamBind param widening is 3-of-5.
async fn batch_execute(&self, sql: &str) -> Result<(), SeamError>;                        // error only
async fn execute(&self, sql: &str, params: &[SeamBind]) -> Result<u64, SeamError>;        // param + error
async fn execute_text_params(&self, sql: &str, params: &[Option<String>]) -> Result<u64, SeamError>; // param UNCHANGED, error widens
async fn query(&self, sql: &str, params: &[SeamBind]) -> Result<Vec<SeamRow>, SeamError>; // param + error
async fn query_one(&self, sql: &str, params: &[SeamBind]) -> Result<SeamRow, SeamError>;  // param + error
```

**`execute_text_params`'s PARAM side is unchanged, but its ERROR side widens like all five verbs.** <!-- Revised: addressing MAJOR — §A.1 previously claimed the whole verb "unchanged/already neutral"; that is false on the error side. The trait returns `Result<u64, compio_postgres::Error>` (session.rs:44-48), and a host impl CANNOT construct compio_postgres::Error (private ctor), so its error type MUST widen to SeamError. --> Its *bind* side is genuinely neutral — it already takes `&[Option<String>]` (no `ToSql`), so **the param side needs no `SeamBind` widening** and it stays a distinct verb (PG refuses concrete-OID binary for `text→timestamptz`; text-format binds are required, §B.2). So **its error type widens to `SeamError` uniformly with the other four verbs (§A.8)** — `execute_text_params` is *not* fully neutral, only its bind side is. Net: the **error widening is uniform across all 5 verbs**; the **param (`SeamBind`) widening is 3-of-5** (`execute`/`query`/`query_one`), with `execute_text_params` keeping its distinct `&[Option<String>]` shape and `batch_execute` taking no params.

**The mechanical call-site rewrite.** Each `&[&x, &y]` becomes `&[x.into(), y.into()]` via `impl From<&str>/From<String>/From<i64> for SeamBind`:

```rust

// journal.rs:983 (exec_ms is i64) — before / after
```

Full census of the ~29 slice sites to rewrite (grep `&\[&` over `src/apply/` filtered to `query`/`execute`/`query_one` receivers): `journal.rs:983,1013,1078,1232,1356,1443,1741,1752,1773`; `precondition.rs:292,313`; `baseline.rs:156,163`; `drift.rs:626,650,683,713,736,779,891,954,1009,1052`; `backfill.rs:282,366,425,753,784,833`; `shadow.rs:1183`; plus the `executor.rs` role/project binds (`475,488`). ### A.2 The value-shape union (verified exhaustively, narrow, text-biased)

<!-- Revised: addressing MAJOR — the census was incomplete (Option<i32> at drift.rs:801 omitted). Re-run exhaustively with cited grep counts. -->

**The raw grep, so the closed-set claim is auditable rather than asserted.** Across `crates/zeroship-migrate/src`: `.query(` = 64 hits, `.query_one(` = 10, `.get`/`.try_get` = 477 total. Those 477 span PG *and* SQLite *and* MySQL (`Map<String,Value>`) paths; the PgSession-seam subset is the PG apply path only (`baseline.rs`, `precondition.rs`, `drift.rs`, `journal.rs`, `backend/postgres/{shadow,backfill}.rs`, `executor.rs`). Within that subset the decoded value union is **seven shapes** (corrected from "six" — the census had missed one integer width), because the SQL layer was written text-first: **every timestamp column is `to_char(...)`-cast to text**, most arrays are `array_agg(...)`, every count/`event_seq`/`exec_ms` is `bigint`. No `bytea`, no `f64`/`NUMERIC`/`Decimal`, no `Uuid`, no `serde_json::Value` (JSON columns are `TEXT`, decoded `String`, parsed in Rust), no native `timestamptz`. No consumer inspects column-type metadata or SQLSTATE through the seam (grep: zero `.columns()`/`.type_()` hits). This is what makes a stringified host driver sufficient.

The `Option<i32>` row is the census-completeness fix: `character_maximum_length` is a genuine `int4` read that is neither bigint-cast nor text-cast, so the old "no integer other than i64/bigint; only six shapes" claim was **false**. `SeamValue::Int(i64)` holds the value, but the `FromSeam` closed set must include `Option<i32>`/`i32` (narrowing from `SeamValue::Int` with an `i32::try_from` range check), else a mechanical port misses `drift.rs:801` and fails to compile. (Alternative considered and rejected: SQL-cast `character_maximum_length::bigint` and decode `Option<i64>` — a one-line SQL change, but it hides the width mismatch behind a cast rather than making the seam honestly carry `i32`; we widen `FromSeam` instead.)

Row-level metadata used through the seam: only `row.len()` (`precondition.rs:543`) and positional index `0` (`precondition.rs:539`, `backfill.rs:955`). NULL handling has two idioms — `try_get(...).ok().flatten()` (nullable → `Option<T>`) and `try_get(...).unwrap_or_default()` (NULL array → empty `Vec`) — so `SeamRow` must distinguish SQL-NULL from a present value, per cell.

### A.3 `SeamValue` — the neutral cell

A closed enum covering exactly the union, text-biased to match the SQL that already exists:

```rust
pub enum SeamValue {
    Null,
    Text(String),                    // text, name, varchar, "char"-as-1-char, to_char timestamps
    Int(i64),                        // int2/int4/int8 all widened to i64
    Bool(bool),
    TextArray(Vec<Option<String>>),  // text[]; element NULLs preserved
}
```

`i8` ("char") gets no dedicated variant: the four consumers immediately do `u8::try_from(x).map(char::from)`. The neutral getter reads a 1-char `Text` (a host `pg` driver returns `"r"`/`"v"`/`"m"` naturally; the compio adapter converts its `i8` to a 1-char string). `i32` (`character_maximum_length`) also gets no dedicated variant — it widens into `Int(i64)` and `FromSeam for Option<i32>` narrows back with a range check (§A.4). This keeps the enum minimal and matches how a JS driver naturally returns cells.

### A.4 `SeamRow` — the driver-neutral row

```rust
pub struct SeamRow {
    columns: Vec<String>,            // for name→pos
    values:  Vec<SeamValue>,
}

impl SeamRow {
    pub fn len(&self) -> usize;                                       // → precondition.rs:543
    pub fn get<T: FromSeam>(&self, col: impl SeamIndex) -> T;         // panicking, mirrors Row::get
    pub fn try_get<T: FromSeam>(&self, col: impl SeamIndex) -> Result<T, SeamError>; // mirrors Row::try_get
}
```

`SeamIndex` is implemented for `&str` (name) and `usize` (position) — both access patterns in the census. `FromSeam` is the neutral analogue of `FromSql`, implemented for exactly the closed set: `String`, `Option<String>`, `bool`, `i64`, **`i32`, `Option<i32>`** (narrow from `SeamValue::Int` via `i32::try_from`, erroring on overflow — covers `drift.rs:801`), `i8`/`char`-via-`Text`, `Vec<String>`, `Option<Vec<String>>` — a **small, closed** trait (~10 impls), not the open `FromSql` ecosystem. The host driver only produces `SeamValue`; the domain decode stays generic over `SeamRow`. Because `SeamRow::get`/`try_get` are name/position + `FromSeam`-shaped **identically** to `Row::get`/`try_get`, the ~29 consumer bodies are largely unchanged — `r.get("relkind")` still reads, resolving through `FromSeam` instead of `FromSql`.

### A.5 `SeamError` — the driver-neutral error

The consumer census shows the error is treated **opaquely everywhere through the seam**: every `From<compio_postgres::Error>` impl (`drift.rs:103`, `journal.rs:364`, `executor.rs:164,446,2987`, `baseline.rs:55`, `precondition.rs:107`, `capability.rs:37`) just wraps it as `#[source]`/`Display`. The **only** structured inspection — `.as_db_error().message().contains("tuple concurrently updated")` at `role.rs:158` (inside `exec_retry`, `role.rs:149`) — was on the concrete admin `Client` in the base; **§F now moves it through the seam**, re-established **message-only over `SeamError.message`** (§F.2 — mirroring native's message-only match exactly; it does *not* read `SeamError.code`, so classification does not fork across drivers), because §F brings role provisioning onto the host path. So this is the one error-introspection site that graduates from "compio-only, opaque" to "read over the neutral `SeamError.message`" — the reason `SeamError` carries a `message` all consumers already read; `code` stays carried-but-unread (§A.5 below).

### A.6 Where decode-to-domain moves

**It does not move.** The domain decode (`RoleSnapshot{…}`, `IndexSnapshot{…}`, `PendingContract{…}`, `BackfillProgress{…}`, the `char::from` kind-matching, the `serde_json` parse of `contract_versions`, the `SafeI64::new` clamps, the `"YES"/"NO"→bool`, the `String→Phase`/`EventKind` parses) stays exactly where it is — in the core consumer functions — but reads `SeamRow` instead of `compio_postgres::Row`. The seam is a **transport** boundary, not a decode boundary.

### A.7 The two impls

- **compio (`native-pg`, default) — the FIRST producer.** `PgSession::query` maps each `compio_postgres::Row` → `SeamRow` by iterating columns and, per cell, decoding the concrete PG value into a `SeamValue` (`String`→`Text`; `i2`/`i4`/`i8`/`"char"`→`Int` or 1-char `Text` for `"char"`; `bool`→`Bool`; `text[]`→`TextArray`; NULL→`Null`). This is the **only** place still touching `compio_postgres::types::FromSql`, and it is a fixed ~6-arm match. The native path keeps working byte-for-byte — SQL and domain decode unchanged, only the intermediate row representation is remapped. Landing this compio-first is the §A verification (§7 Phase A) — the platform suite is the proof before any host driver exists.
- **host/napi.** Builds `SeamRow` directly from JS-returned values (pg/mysql2/bun:sqlite return JS strings/numbers/bools/arrays over the threadsafe-function boundary), never constructing a `compio_postgres::Row`. This closes the `unreachable!("read verbs…")` gap in the Phase-2 mock (`backend/postgres.rs:449-459`).

   - **Element-NULL policy — PARITY, not divergence (interchangeability wins).** <!-- Revised: addressing MINOR — an earlier draft forked native (→[]) vs host (→SeamError) on reloptions, a security-relevant catalog read; that fork breaks the "drop-in identical" / journal-identity promise on exactly this cell.      - **If loud-fail is ever wanted, it must be SYMMETRIC.** Failing loudly on a surprising `reloptions` element-NULL is a defensible *future* hardening — but it would then be applied to **both** adapters as one deliberate, symmetric behavior change (native and host both `SeamError`), not forked between them. v1 keeps both on the legacy `[]` coercion so the drivers stay interchangeable.

3. **Positional + `row.len()`** (`precondition.rs:539,543`; `backfill.rs:955`). `SeamRow` must support `usize` indexing and `len()`. Trivial but must not be forgotten — name-only would miss these 3.

**Verdict: mechanical, not a typed-decode rewrite — but not a no-op either.** The domain decode is untouched (it reads `SeamRow`); the genuine design work is (a) the `SeamValue`/`SeamBind` enums + `FromSeam` impls (~10) + `SeamBind` mappers, (b) the compio `Row → SeamValue` / `SeamBind → ToSql` adapters (~6-arm matches each), (c) the three normalisation decisions. No *ordinary apply-path* consumer needs SQLSTATE, type-OID metadata, bytea, numeric, or native timestamps — the SQL layer's pre-existing casts did the hard part. The **one** structured-error consumer, `role.rs:158`'s `"tuple concurrently updated"` string-match, rides with the shadow harness, which §F now reconstructs host-side — so that match is re-established **message-only over `SeamError.message`** (§A.5, §F.2 — mirroring native's message-only match; it does *not* read `SeamError.code`, so it does not fork across drivers) rather than `compio_postgres::Error::as_db_error()`, and `role.rs:163`'s `compio::time::sleep` is **re-homed off compio** (§F.2). This means only `SeamError.message` (already read by every consumer) is read by §F role provisioning; `SeamError.code` stays carried-but-unread. The "no compio timers on the *native-pg main* apply future" invariant is preserved by keeping role provisioning on the distinct *shadow* future only (§C.4, §F.3) — one coherent decision cross-linked to §F, not a loose assertion.

**Cross-platform note.** Because the read union is fully text-representable and metadata-free, the host PG driver can be pure-JS `pg` with **zero compio** — satisfying the cross-platform-npm goal. SQLite can independently stay native (`rusqlite`) or go host-provided; the `SeamRow`/`FromSeam` contract is identical for both, so the choice is orthogonal to this widening.

## §B. The host-callback `PgSession` — the napi threadsafe-function bridge

Once §A lands, a host driver can be *called* (`&[SeamBind]`, §A.1) and can *return* rows (`SeamRow`, §A.2). §B specifies how the Rust core *invokes* the host driver: the Rust engine runs on its own worker thread (Temporal-style) and each `PgSession` verb calls into JS via an N-API **`ThreadsafeFunction`** whose completion is signalled by a Rust-supplied callback (NOT an awaited Promise — the tokio-free bridge, §B.3).

### B.1 The precedent — the MySQL `JsDriverBackend` proves the PROTOCOL (not the async transport)

This is **not** a new *protocol*. `crates/zeroship-migrate/src/apply/backend/mysql/transport.rs` already marshals `Vec<Map<String,Value>>` rows, folds binds via `bind_to_json` (`BindValue::{Int→number, Decimal|Text→string, Bool→bool, Null→null}`), maps `remoteError → {code, sqlstate, message} → JsDriverError::Remote`, and enforces **one pinned, non-reentrant, one-in-flight connection** via an explicit `in_flight: bool` re-entry check (`transport.rs:252,386-393`) over a JS `mysql2/promise` loop. The napi `PgSession` reuses that **same protocol shape** — `#[napi(object)]` `SeamBind`/`SeamRow`/`SeamError` in place of the Rust-embedded V8 + serde channel.

<!-- Revised: addressing MINOR — do not let the MySQL precedent absorb the async-bridge risk it does not cover. -->
**What the MySQL precedent proves — and what it does NOT.** It runs inside an **in-Rust Trusted V8 isolate** with serde-JSON marshaling over an *embedded* engine on the *same* thread; there is no cross-OS-thread hand-off and no host event loop. So it proves only the **protocol / marshaling shape**: `{sql,binds}→rows|err`, one pinned connection, SQLSTATE-carrying errors, the bind/decode value union. It proves **nothing** about the three actually-novel risks of the napi transport: (a) the N-API cross-thread boundary (`ThreadsafeFunction` fired from the engine worker thread, `done` fired back from the JS thread), (b) the **tokio-free** cross-thread wakeup of a reactor-less `block_on` (§B.3/§B.5), and (c) Bun's N-API `ThreadsafeFunction` behavior (§E.2). Those three are de-risked **separately** by the Phase-B.5 spike (§B.5) and the Phase-D Bun gate (§7) — the MySQL precedent is cited for the *protocol* only and must not be read as evidence that the async bridge works.

### B.2 What crosses the boundary

Per verb: `{ kind, sql, binds }` → `{ rows: [{col: cell}], rowCount } | { error: { sqlstate, message } }`.

- **Params (Rust → JS).** The trait now carries `&[SeamBind]` (§A.1), and `SeamBind` is a field-for-field mirror of `render::step::BindValue` — so the napi layer marshals `SeamBind → JS` with the **same fold the MySQL `bind_to_json` already proves** (`transport.rs:596-601`): `Int→number`, `Text→string`, `Bool→bool`, `Null→null`, `Decimal→string`. (Today only `Text` and `Int` binds actually reach the wire, §A.1; the other arms are enum-complete but dormant.)
- **`execute_text_params` (Rust → JS) — a DISTINCT, LIVE, correctness-sensitive marshaling path, not a neutral no-op.** <!-- Revised: addressing MAJOR — §A.1 called this verb "already neutral" but never specified the host-side marshaling; it is on the live apply path (executor.rs:2305) and must bind PG *text-format* params. --> `execute_text_params(&self, sql, params: &[Option<String>])` stays a distinct verb because a concrete-OID binary bind makes PG refuse `text → timestamptz`; the op.* text-param assembler (`executor.rs:2305` `conn.execute_text_params(template, &params)`) is on the **live apply path**, so the host `pg` wrapper must marshal it explicitly, not treat it as solved:
  - **Rust→JS value mapping:** each `Option<String>` element crosses as JS `string | null` — `None → null`, `Some(s) → s` verbatim, **no type coercion** (never `Number(s)`, never a Date). The napi glue marshals the `&[Option<String>]` to a JS `(string | null)[]` and the `pg` wrapper passes it straight to `client.query({ text, values })`.
  - **The bind must be text-format with NO explicit type OID.** `driver-pg.js` issues these as an **unadorned** parameterized query (`client.query(sql, values)` with no `types`/OID array on the params) so node-postgres sends every non-null param in **text format** and lets PG infer the target type from context — reproducing exactly what compio's `execute_text_params` does (server-side text→target coercion, e.g. `text→timestamptz`).   This verb is added to the **Phase-D differential oracle** (§7): a migration that exercises the op.* text-param assembler at `executor.rs:2305` (e.g. an op-DML insert with a timestamptz/text-coerced param) runs through `driver-pg.js` and its journal/target rows are asserted byte-identical to the `native-pg` path — proving the host text-param path, not assuming it neutral.
- **Rows (JS → Rust → `SeamRow`).** The host driver returns JS cells; the napi layer marshals them into `SeamValue`-shaped cells (§A). **int8/numeric cross as strings** → `SeamValue::Text`, preserving the IR's exact-integer domain — but this is a **contract the `pg` wrapper must enforce with its own type parsers** (§D.2), not a default to be trusted. `character_maximum_length` (int4) crosses as a JS number → `SeamValue::Int`, narrowed by `FromSeam for Option<i32>` (§A.2). `text[]` cells cross as JS arrays → `SeamValue::TextArray`; an element-NULL (JS `null` inside the array) is carried as `None` and coerced to the legacy `[]` outcome by `FromSeam for Vec<String>` + the caller's `.unwrap_or_default()` — **the same result the native adapter produces** (§A.8 chooses parity, not a fork, so native and host stay interchangeable on this raw nullable-array cell). **SQLSTATE rides on node-pg's `err.code`** → `SeamError.code`.
- **Txn control / advisory locks / `SET`s are NOT new callbacks.** They are SQL strings on the existing verbs (`batch_execute("BEGIN")`, `execute("SELECT pg_advisory_xact_lock(...)")`, `batch_execute("SET LOCAL …")`). But they require the host to **pin ONE connection** (not a pool) for the whole session — a session-scoped `BEGIN … advisory-lock … SET LOCAL … COMMIT` must land on the same socket.

**The connection-cardinality contract — stated explicitly (v1).** <!-- Revised: addressing USER DECISION — the ordinary apply path is one-connection, but §F's host shadow dry-run introduces the SECOND and THIRD host connections; the "future add" forward-note is now the realized §F design. --> The host driver contract for the **ordinary `apply`/`plan` path** is **exactly ONE pinned connection per `SeamSession`, one engine future per worker thread, one verb in flight at a time** (§B.6 `in_flight: AtomicBool`). The embedded engine's real deploys carry both a migrator and an admin connection in `ExecutorConfig`; the addon's *apply* path uses only the migrator connection because the deploy future does no shadow/role work — role provisioning and shadow live on a **separate, opt-in pre-flight future** (§F), not the deploy future. **Concurrency across sessions:** two concurrent `apply()` calls (e.g. two engine worker threads in one Node process) get **independent `SeamSession`s, each with its own pinned host connection and its own `in_flight` guard** — there is no shared connection and no cross-session advisory-lock coordination in-process (PG's advisory locks arbitrate between them server-side, exactly as with two separate embedded deploys). **The second and third host connections (now realized by §F, not deferred).** The host-side shadow dry-run harness (§F) introduces exactly the additional connections the earlier forward-note anticipated — and §F.1 **resolves** them as three *distinct* connections (a deliberate CREATEDB split off native's fused two): a **distinct admin** `SeamSession` (`shadow.adminUrl`, `CREATEDB`+`CREATEROLE`) used for `CREATE DATABASE`/`DROP DATABASE` + cluster-global `DROP ROLE` **and the read-only live seed snapshot** (declarative/incremental arm — on the admin endpoint, §F.1 cluster-sameness); a **second** pinned shadow-target `SeamSession` to the throwaway *shadow DB* (its own host `PgSession` + its own `in_flight` guard) that runs `CREATE SCHEMA` + `provision_migrator` + the seeded shadow apply; and the **migrator** `SeamSession` (`driver.url`) which issues **nothing during the shadow pre-flight** (it is the live-apply connection a subsequent `apply` uses). §F.1 keeps the migrator connection least-privileged — the split moves `CREATEDB` and the seed read onto the admin credential (the point: least privilege + seed↔shadow cluster-sameness). Each carries its **own** `in_flight` discipline; advisory-lock contention across the shadow and migrator connections is **not** coordinated by any single `in_flight` bool — §F.3 specifies the serialization (the shadow pre-flight completes and tears down *before* the live apply acquires the project lock, so the two never race on the live DB). The `dryRun` facade verb (§D.3) drives §F; ordinary `apply`/`plan` without a preceding `dryRun` stay genuinely single-connection.

### B.3 The async / Promise model — the tokio-free Promise→oneshot bridge

<!-- Revised: addressing MAJOR — the ergonomic napi async path is tokio-backed; specify the exact tokio-free completion-callback bridge instead of hand-waving "oneshot resolved by TSFN". -->

**Why the ergonomic napi path is forbidden here.** napi-rs's ergonomic async — `#[napi] async fn` returning `Promise<T>`, and `p.await?` to resolve a *returned* JS Promise from Rust — is **gated behind the `async`/`tokio_rt` feature** (napi-rs docs, `concepts/promise`: *"Use `await` … within a Rust async function. Requires `tokio_rt` and `napi4` features"*; `concepts/async-fn`: *"you must enable the `async` or `tokio_rt` feature"*). That feature bundles a **tokio** runtime to drive the future and bridge promise-await. Zeroship's zero-tokio invariant forbids it. So the design must **never call `Promise::await`** and must **never use `#[napi] async fn`** in a way that pulls `tokio_rt`.

**The tokio-free bridge, concretely — a completion callback, not a returned Promise.** The host driver callback does **not** return a Promise for Rust to await. Instead each verb is a `ThreadsafeFunction` whose JS side receives `(request, done)` where `done` is a **napi `Function`** supplied by Rust. The flow per verb:

1. Rust (on its worker thread) allocates a `futures::channel::oneshot` pair and stashes the `Sender` (keyed by a call-id) so a later `done(...)` can find it.
2. Rust calls `tsfn.call(SeamRequest { kind, sql, binds, call_id }, ThreadsafeFunctionCallMode::Blocking)`.
3. The JS wrapper does its real async work (`const rows = await client.query(sql, binds)`), then invokes the Rust-supplied completion — `done(null, { rows, rowCount })` on success, `done({ sqlstate, message }, null)` on failure.
4. `done` is a napi callback whose Rust body deserializes the payload into `SeamRow`s/`SeamError` and **fires the `oneshot::Sender`**.
5. The engine's `block_on` (§C.4), parked on the `oneshot::Receiver`, wakes and the verb returns.

This keeps the entire path on **raw napi4 threadsafe-function primitives + one extra napi `Function`** — no `async` feature, no `tokio_rt`, no `Promise::await`. (If a value-*returning* TSFN is preferred over a separate `done` Function, napi-rs's `call_with_return_value(payload, mode, |ret, _| { … })` closure — `concepts/threadsafe-function` — is the sync-return equivalent: its closure runs on the JS thread with the callback's *resolved* value and can fire the oneshot; but because the DB work is genuinely async, the explicit `done`-callback shape is cleaner and is the specified design.) `PgSession` verbs stay `async fn` in the *trait* (`!Send`, single-thread), but their bodies `.await` a **`oneshot::Receiver`**, never a JS `Promise` — so the future graph the engine's `block_on` drives contains only oneshots and never touches napi-rs's tokio-coupled `Promise`.

<!-- Revised: addressing MAJOR — the Send/thread-affinity + reactor-less-wakeup contract N-API forces was asserted, not stated. Specify exactly what crosses the boundary, and prove the parker/waker guarantee. -->
**The Send + `'static` boundary — stated exactly (this is what N-API forces).** napi-rs requires the JS-side callback body of a `ThreadsafeFunction` (and any napi `Function` invoked from a foreign thread) to be `Send + 'static`, because napi-rs copies the payload onto a libuv/Bun task-queue and runs the JS call on the JS/main thread. The engine, however, is `!Send` by design (`session.rs:32` — `!Send` on the single-thread compio-shaped runtime), and **none of that `!Send` engine state may cross the boundary.** Concretely, exactly two values cross into the napi call, and both are `Send + 'static`:
  - the **`call_id`** (a `u64`), and
  - the **`futures::channel::oneshot::Sender<Result<SeamReply, SeamError>>`** for that call.

  `oneshot::Sender<T>` is `Send` whenever `T: Send` (futures-channel), and `SeamReply`/`SeamError` are plain owned data (`String`/`i64`/`Vec` — no borrows, no V8 handles), so the `Sender` is `Send + 'static`. The `SeamRequest { kind, sql, binds, call_id }` payload is likewise all-owned. **The call-id→Sender map itself does NOT cross** — it stays on the engine worker thread; only the *individual* `Sender` for the in-flight call is moved out (into the closure the `done` Function fires), so no shared, `!Send` map, no `!Send` engine handle, and no `PostgresBackend<&D>` borrow is ever captured into a napi callback. The one-in-flight discipline (§8, §B.5) guarantees there is exactly one such `Sender` outstanding at a time, so "move the Sender out" is unambiguous.

**The reactor-less wakeup guarantee — with citation, not assertion.** `futures::executor::block_on` drives its single future by parking the calling (engine worker) thread on a `std::thread`-parking `Waker` (futures' `ThreadNotify`), and its `Waker::wake`/`wake_by_ref` calls `Thread::unpark`, which is defined to be safe and effective **cross-thread** (`std::thread::Thread::unpark` — "atomically make the token available if it was not already … a subsequent call to `park` will return immediately"). So when the `done` callback (on the JS thread) fires `oneshot::Sender::send(...)`, futures-channel wakes the registered `Waker`, whose `wake` unparks the engine worker thread; the engine's `block_on` re-polls and the awaited `oneshot::Receiver` resolves. This is the *entire* feasibility hinge, and it holds because (i) the parker/unparker pair is explicitly cross-thread-safe in `std`, and (ii) `oneshot`'s waker registration is atomic (the `send` either observes the registered waker and wakes it, or the receiver re-polls and finds the value — no lost-wakeup window). No I/O reactor is needed because the *only* wakeups the engine future ever sees come from these out-of-thread `Sender::send`s (§C.4 audits that no other suspension source exists).

**Build assertion:** the addon's `napi` dependency is declared with `default-features = false` and **without** `async`/`tokio_rt` (only `napi4` + the TSFN/Function features), and a `cargo tree -p zeroship-migrate-node` gate asserts **zero `tokio`** in the leaf's closure (§8 risk row, §C.4).

Marshalling notes carried forward: the pinned-connection requirement is enforced host-side (the driver wrapper holds exactly one `pg.Client`/`mysql2` connection per session, never a pool); reentrancy is prevented by one-in-flight (the MySQL backend's proven discipline — §8 risk row, §B.6).

### B.5 Phase-B.5 — the runnable async-bridge spike (gates Phase C)

<!-- Added: addressing MAJOR — the tokio-free oneshot bridge is asserted, not demonstrated. De-risk it with a minimal runnable spike BEFORE the full napi crate is trusted. -->

The §B.3 bridge is the feasibility hinge of the whole design, so it is **proven by a minimal runnable spike before Phase C invests in the full crate** — not inferred from the MySQL precedent (which does not cover the cross-thread wakeup, §B.1). The spike is a throwaway napi cdylib (~60 lines) that isolates *only* the async boundary, with no engine, no DB, no SeamRow:

1. Rust `#[napi]` `run_spike(session: ThreadsafeFunction, done_maker: …)` spawns **one worker thread** that runs `futures::executor::block_on(async { rx.await })` on a `oneshot::Receiver<u64>`.
2. Before parking, it moves the matching `oneshot::Sender<u64>` (the only value crossing) into a Rust closure exposed to JS as the `done` napi `Function`, and fires the `ThreadsafeFunction` with a `call_id`.
3. The JS test harness receives `(request, done)`, does `await Promise.resolve()` (a real event-loop turn to force the wakeup to be genuinely cross-thread and deferred), then calls `done(42)`.
4. `done`'s Rust body fires `Sender::send(42)`; the assertion is that the **worker thread unparks and `run_spike` returns `42`** — i.e. a `Waker::wake` fired from the JS/main thread demonstrably unparks a `futures::executor::block_on` on a different OS thread.

**Explicit spike assertions (the contract §B.3 states, mechanically checked):** (a) the worker thread wakes and returns — proving the parker/unparker cross-thread guarantee empirically, not just by `std` citation; (b) `cargo tree` on the spike shows **zero tokio** (built with `napi = { default-features = false, features = ["napi4"] }`, no `async`/`tokio_rt`); (c) only `call_id: u64` + `oneshot::Sender` cross into the napi callback (the closure captures nothing else — enforced by the closure's type: it is `move` over exactly those two, and the spike deliberately has no other state to capture); (d) a variant that fires `done` from a **`setTimeout(…, 0)`** (deferred to a later loop tick, JS thread genuinely idle in the meantime) still wakes the parked worker — closing the "does the wake reach the parker if the worker parked first" ordering question. **Phase C does not start until this spike is green on Node** (and its Bun variant is folded into the §E.2 / Phase-D Bun gate).

### B.6 The one-in-flight invariant — mechanically enforced in the driver, not asserted by analogy

<!-- Revised: addressing MAJOR — the one-verb-at-a-time claim was "by analogy" to MySQL; enforce it with a driver-side runtime guard and make it a Phase-C gate. -->

§B.1/§8 argued reentrancy-safety *by analogy* to the MySQL backend's discipline. That analogy is necessary but not sufficient here, because the apply path threads a borrow `&'a D` through `PostgresBackend` (`postgres.rs:69` `new_generic(conn: &'a D)`): the borrow checker permits a strictly-sequential source that nonetheless holds a verb's `Future` alive across a suspension point (e.g. a future refactor that lazily streams a `Vec<SeamRow>`, or a helper awaiting two introspection calls). On one pinned host connection, a second verb issued while the first's future is still alive **deadlocks** — the second `tsfn.call` blocks on a connection the first hasn't released. So the invariant must be **enforced by the driver**, not trusted:

- The host `PgSession` impl carries an `in_flight: AtomicBool` (the exact shape the MySQL backend already uses — `transport.rs:252,386-393`, `bool` there, `AtomicBool` here because the seam is `&self`, not `&mut self`). Each verb does `compare_exchange(false, true)` on entry and **panics on re-entry** ("PgSession verb issued while another is in flight — the engine must be strictly one-verb-at-a-time"), clearing to `false` in the verb's completion arm (guard/RAII so an error path also clears).
- **Phase-C gate (converts by-analogy → mechanically-proven):** run the **full apply** against the in-crate host mock (Phase B's recording `PgSession`) with the `in_flight` guard **armed**, and assert it **never trips** across the whole DDL+journal+drift+rollback surface exercised by the suite. This turns "the engine issues one verb at a time" from a claim into a checked invariant; if any code path ever holds a verb across a suspension point, the gate fails loudly rather than deadlocking in production.

## §C. The napi crate + feature matrix + executor

### C.1 A new leaf `cdylib` crate — `crates/zeroship-migrate-node`

Add `crates/zeroship-migrate-node`: a napi-rs `cdylib` (`[lib] crate-type = ["cdylib"]`, deps `napi`/`napi-derive` 3, build-dep `napi-build` 1, `build.rs = napi_build::setup()`), depending on `zeroship-migrate` with `default-features = false, features = ["host-pg"]`. `@napi-rs/cli` compiles it and emits `index.node` + `index.d.ts`.

**Why a new crate, not a feature/target on the core:**
- A `cdylib` is **terminal** (no Rust crate can depend on it) → it is necessarily a leaf → the graph stays acyclic (`zeroship-migrate-node → zeroship-migrate` is the only edge).
- The core must still build as a **pure rlib** (`--no-default-features`) for control/worker to embed; putting `napi`/`cdylib` on the core would drag N-API into every embedder's dependency closure.
- One core rlib, three shells: **platform** (`native-pg` + `zsv8`), **lean embedder** (`--no-default-features`), **addon** (`host-pg`). This mirrors the existing feature split.
- **Add the leaf to the root workspace `exclude`** (like `refs`/`ntex-bench`) so the platform's `cargo build` doesn't pull the napi toolchain; it releases independently as npm. `crates/*` is a glob member with `resolver = "3"`, which keeps the addon's feature profile from unifying onto platform binaries.

### C.3 The SQLite decision — keep it NATIVE (`rusqlite` bundled)

The addon keeps SQLite **native** (`rusqlite` + `bundled`) and host-provides only PG+MySQL. Rationale:
- `rusqlite`+`bundled` is **already cross-platform** (Linux/macOS/Windows) — it is *not* what makes anything Linux-locked; **compio is**. Keeping SQLite native costs nothing on the cross-platform axis.
- The engine's **journal-immutability + confinement guarantees are in-process `rusqlite`-authorizer-shaped** (`load_extension_disable()`, `Arc<AtomicU8>` mode-flip, SQLite 3.51.x floor). A host `bun:sqlite`/`better-sqlite3` **cannot install that authorizer** → host-SQLite would trade the engine's core security property for a smaller binary. Wrong trade.
- Host-SQLite (Option B) stays a documented, re-proof-gated future option for a "no-native-deps" build, not the default.

The existing `apply/backend/sqlite/` actor keeps working unchanged; SQLite is synchronous in-process, so it needs **no host callback at all** on the addon path.

### C.4 The executor — `futures::executor`, not compio, not tokio

The engine is a real state machine (plan → guard → lock → apply+confinement → journal → rollback/backfill → shadow-verify), not a request wrapper, and its steps `.await` on driver I/O. Following Temporal's core (Rust `sdk-core` keeps its own runtime + state machines; N-API is only the channel boundary), **the engine keeps its own runtime** — but that runtime does **no io_uring**. Its I/O leaves are `oneshot` channels resolved by the TSFN completion callback (§B.3). So:

- **Use a minimal single-threaded `futures::executor::block_on`** (already a workspace dep) on one Rust worker thread — **not compio** (io_uring, Linux-only), **not tokio** (violates zero-tokio; napi-rs's bundled `tokio_rt` runtime is therefore rejected — and, per §B.3, the design never calls `Promise::await`/`#[napi] async fn`, the two things that would pull `tokio_rt`).

Audit result (grep over `src/apply/`, non-test): **zero** `join!`/`select!`/`try_join!`/futures-`::spawn` in the apply path — the engine issues exactly one verb at a time and awaits it before the next. The audit therefore splits cleanly: the main apply future has **zero** timers (native and host alike); the shadow pre-flight future has exactly the re-homed, non-compio retry (§F.2), still driven by the same out-of-thread-woken `block_on` (the SeamSession round-trips + the re-homed sleep's timer are cross-thread wakeups, not an io_uring reactor poll — §F.3). ## §D. The JS half — authoring, drivers, npm API

### D.1 Authoring host-side — Node produces the same `.ir.json`, purely in JS

**How it works today (the in-Rust V8 recorder).** `src/frontend/op_recorder.js` imports the bundled creator migration + `{ __begin, __drain }` from `@zeroship/migrate` and, per phase, does `__begin("up"); up(); const ops = __drain()`. `up()`'s `table(...).column(...).add(...)` calls record ops into an ambient buffer (the `defineOp → push` chokepoint in `ops.ts`); it emits `globalThis.__zsOpIR = JSON.stringify({ ok, ir: { ir_version: 6, name, ops } })`. Rust reads it back, **stamps `owner_app`** (untrusted `up()` must NOT set this — it is a provenance field), and folds the **single authoritative** `Checksum::of_ir`. The JS side deliberately never computes the checksum.

**The TS DSL already produces this byte-identically.** `sdks/migrate/src/embedded-recorder.ts` is tsup-bundled into the exact `dist/embedded-recorder.js` the crate `include_str!`s — the SDK recorder and the engine-embedded recorder are **already one compiled artifact** (Phase-1 S0.5). It already exports the full recorder seam: `__begin`/`__drain`, all op producers, value factories, `lintDeterminism`, and structured errors (`OP_OUTSIDE_RECORDER`, `SELECTOR_NOT_TERMINATED`).

**Node can produce the SAME `.ir.json` purely in JS.** The recorder is ordinary ESM; the in-Rust V8 isolate was only ever a *sandbox* for untrusted `up()`, never an authoring requirement. Host flow: esbuild-bundle the `.ts` → import + `@zeroship/migrate` → `__begin`/`up()`/`__drain` → build the `{ir_version, name, ops}` envelope → hand to the Rust core, which stamps `owner_app` and folds `Checksum::of_ir`. **The checksum invariant is preserved for free** — it is value-equality over the canonical op list regardless of which JS engine drained it (`op_round_trip.rs` already asserts this).

**What is missing from `sdks/migrate` to author host-side (small, mechanical):**
1. A thin **host recorder entry** — the JS equivalent of `op_recorder.js`'s try/`__begin`/`up()`/`__drain`/catch wrapper + `resolveMigration`/`resolveName`, which today live only in the Rust-side `.js` glue, not exported from the SDK.
2. **`CURRENT_IR_VERSION` as one source of truth** across the boundary (today `6` is hardcoded in both `op_recorder.js` and `model/ir.rs`).
3. **Sandbox becomes the host's problem** (§5.1) — the one real capability the pure-JS authoring path drops. Fine for the trusted local/self-host posture; a multi-tenant hosted recorder re-establishes sandboxing host-side (worker + `vm` + timeout) or keeps the in-Rust V8 recorder for that posture only. A scoping decision, not a blocker.

### D.2 Drivers host-side

- **PG** — a thin `pg` wrapper: one pinned `pg.Client` per session, `{kind, sql, binds} → {rows, rowCount} | {error}`, int8/numeric returned as strings.
  - **`execute_text_params` is a first-class, distinct code path in the wrapper** (§B.2), not folded into the ordinary `execute`: it receives a `(string | null)[]` and calls `client.query(sql, values)` with **no explicit param type OIDs**, so `pg` sends them text-format and PG infers the target type (matching compio's `text → timestamptz` coercion). `null` maps to a PG NULL bind; every non-null crosses as its exact string with no coercion. Wired into the Phase-D differential oracle against `executor.rs:2305`.
  - **The int8/numeric-as-string contract must be ENFORCED, not assumed.** <!-- Revised: addressing MINOR — global pg.types.setTypeParser overrides can silently break the exact-integer invariant. --> node-postgres's default parsers return int8 (oid 20) and numeric (oid 1700) as **strings**, which is what preserves the IR's exact-integer domain (`event_seq`, `version`, seq bounds cross as `SeamValue::Text` and never lose precision). But `pg.types.setTypeParser` is **global and mutable** — a host app that has overridden the int8 parser to return a JS `number` (a common footgun) would silently truncate large bigints below the seam, corrupting journal `event_seq`/`version` comparisons **with no error**. So `driver-pg.js` MUST install its **own** deterministic parsers scoped to the pinned `Client`, independent of any global override: construct the `pg.Client` with a private `types` object (`new pg.Client({ types: customTypes })`, where `customTypes.getTypeParser(oid, format)` forces oid 20/1700/1016 → `String` and int4/oid 23 → the default int parser) — or, equivalently, register the parsers on a per-connection `pg.types` instance. This makes int8/numeric/int8[] parsing deterministic regardless of the host's global `setTypeParser` state. **Verification:** a differential-oracle test (§7 Phase D) that first calls `pg.types.setTypeParser(20, x => Number(x))` globally to poison the default, then runs an apply through `driver-pg.js` and asserts the journal `event_seq`/`version` values are still exact — proving the wrapper's own parsers win.
- **MySQL** — the existing `JsDriverBackend` protocol minus the in-Rust V8: TLS-pin + net-allowlist + timeout logic move host-side (the host now owns sockets). Uses the host's `mysql2/promise`.
- **SQLite** — **native `rusqlite`** by default (no host callback); Option B host `bun:sqlite`/`better-sqlite3` deferred (§C.3).

### D.3 The npm package + the creator-facing API

`@zeroship/migrate` = `dist/` (TS DSL `index.js` unchanged + NEW `host-recorder.js` + NEW `driver-{pg,mysql2,sqlite}.js` wrappers) + `native/migrate.<platform>.node` (V8-free Rust core + bundled rusqlite) + `optionalDependencies: pg/mysql2`, prebuilt `.node` per platform (napi-rs prebuild).

The creator calls a thin async facade — never sees N-API, `SeamRow`, or the addon:

```ts
// WITHOUT touching the live DB. Needs an admin DSN for CREATE/DROP DATABASE.
```

**The facade surfaces a real `dryRun` verb — host-side shadow dry-run, matching the platform's pre-apply safety (§F).** <!-- Revised: addressing USER DECISION — host-side shadow dry-run is IN v1; the facade exposes it. So the addon's `dryRun` carries the **same shadow-verification semantics — same `DryRunReport` verdict — as the platform's embedded `PgShadow`**, verified by the §F.5 differential oracle; **it is NOT identical connection topology** — the host path deliberately splits `CREATEDB`/`CREATEROLE` off the migrator into a separate admin DSN (native fuses them; §F.1), a least-privilege improvement. ### E.2 Bun N-API caveats

- Bun implements N-API → the `.node` loads unmodified. **Use `napi_get_uv_event_loop`, never `uv_default_loop`** (Bun is not on libuv on Linux/macOS; `uv_default_loop`-based `uv_async` callbacks silently don't fire). napi-rs's `ThreadsafeFunction` routes through N-API TSFN primitives, which is *necessary* for Bun-compat but **not by itself sufficient evidence** — Bun's N-API TSFN has historically had gaps (Blocking-mode call semantics, non-libuv loop). <!-- Revised: addressing MINOR — "Bun-safe by construction" overstated the evidence; gate it with a real Bun run, not inference. --> So Bun is **proven by test, not by construction**: the Phase-B.5 spike has a Bun variant, and Phase-D gate 6 runs the full `apply` under `bun run` and asserts journal-identity with Node (§7). Until those pass, `bun run` is "supported pending the Bun gate", not assumed-equivalent.
- **`bun build --compile`** embeds the `.node` via the `process.dlopen`/`Bun__resolveEmbeddedNodeFile` path (distinct from the `bun:ffi type:"file"` path that regressed — bun#30717): it copies the addon to a temp dir and `dlopen`s it. **Broken on Windows** (segfault at addon load under a compiled binary; works under `bun run` — bun#23771). ABI-mismatch errors occur when mixing node/bun prebuilds (qmd#319).
- **Posture:** Node = primary; Bun `bun run` = supported (ship napi prebuilds); `bun build --compile` = **Linux/macOS supported, Windows fragile — gate behind a per-platform compiled-binary smoke test**; Deno/edge = out of scope (a separate WASM track that would force host-SQLite + no threads — deferred).
- **Bun-failure contingency (what if the Phase-D Bun gate reds).** <!-- Revised: addressing MINOR — the doc gated Bun but never said what happens if the gate fails; state the fallback + a version floor + re-verify cadence. --> Bun is **best-effort, not load-bearing**. If the Phase-D full-`apply`-under-`bun run` journal-identity gate (§7 gate 6) or the B.5 Bun spike variant reds — e.g. Bun's TSFN Blocking-mode call ordering or `done`-callback delivery diverges from Node, or the reactor-less cross-thread wakeup does not reach the parked worker under Bun's non-libuv loop — then **Bun drops to "unsupported" and the addon ships Node-only.** The title/objective are qualified accordingly: **Node-primary; Bun best-effort, gated.** No mitigation (libuv-loop shim, custom parker) is committed in v1 — a Bun red is a scope reduction, not a re-architecture, because every Bun-specific risk is isolated to the N-API boundary (the Rust core, `SeamRow` seam, and `futures::executor` runtime are Bun-agnostic). **Bun version floor + cadence:** the gate is run against a **named minimum Bun version** (pinned in the addon's CI matrix and the packaging metadata — pick the current stable at Phase-D time, since Bun's N-API TSFN behavior moves fast) and **re-run on every Bun bump**; a Bun release that regresses the gate reverts the Node-only posture for that version rather than shipping a silently-broken addon. What is settled (and independently confirmed): Bun does **not** run on libuv on Linux/macOS, so `napi_get_uv_event_loop` (never `uv_default_loop`) is mandatory, and TSFN Blocking-mode / libuv-loop semantics are exactly the area of Bun's N-API still reaching behavioral parity — which is *why* the gate exists.

(The still-hung JS `Promise` is abandoned; because the connection is pinned and single-in-flight, the abandoned verb's later resolution — if it ever comes — finds a fired/closed channel and is a no-op. The pinned `pg.Client` is closed by the shadow-open handle teardown, mode-independent.) **§F.4-watchdog-timeout: the watchdog is a HANG detector, NOT a slow-DDL wall-clock cap — it MUST NOT spuriously fire on a legitimately-slow seed/apply verb.** <!-- Added: addressing MAJOR — a uniform 60s per-verb wall-clock cap would spuriously fire teardown on a legitimately-slow-but-not-hung seed apply: the declarative/incremental seed replays the ENTIRE live structure (all tables/indexes/constraints) via executor::apply on the shadow-target (shadow.rs:846), each DDL statement a separate verb, and a single CREATE INDEX on a large seeded table can legitimately exceed a fixed 60s — converting a slow-but-valid dry-run into a false ShadowUnsupported/timeout. On the declarative/incremental arm, `seed_shadow_from_live` (`shadow.rs:731`) drives `executor::apply` over the shadow-target (`shadow.rs:846`) to reconstruct the **entire live structure** — every table, index, and constraint — as a batch of DDL statements, each a separate host verb. A single `CREATE INDEX` (or a constraint validation) on a large seeded table is a legitimately-long *single statement* that can exceed tens of seconds while the DB is genuinely making progress; a fixed 60s cap would fire teardown mid-index and surface a false timeout. So the watchdog is specified as a **liveness/heartbeat check, not a raw wall-clock cap**:
- **Heartbeat form (preferred).** `driver-pg.js` (§D.2) posts a periodic **heartbeat** to the Rust bridge for a verb that is *genuinely still executing* (node-postgres exposes query lifecycle; the wrapper pings, e.g., every few seconds, while `client.query(...)` is pending and un-rejected). The watchdog fires **only if no heartbeat arrives within the heartbeat interval** — distinguishing "the JS event loop is still servicing this query" (alive, keep waiting arbitrarily long) from "the JS side is wedged / the completion callback was lost" (dead → fire teardown). A legitimately-slow `CREATE INDEX` keeps heartbeating and never trips; a hung socket / lost TSFN completion stops heartbeating and trips within one interval.
- **Wall-clock fallback (if a driver cannot heartbeat).** For a driver that cannot post liveness, `ZEROSHIP_MIGRATE_VERB_TIMEOUT` is a **configurable per-verb wall-clock bound whose default is set high enough to accommodate the LONGEST legitimate single statement, not tuned as a hang heuristic** — documented as "this bounds the longest legitimate single DDL statement on your largest seeded table; raise it for very large schemas", with a conservative default (e.g. several minutes, not 60s) and explicit guidance that it is a leak-prevention backstop, not a responsiveness SLA. A slow-but-progressing statement under this bound completes normally; only a statement exceeding the (generous) bound is treated as hung.
- **Seed-apply per-statement cost, noted.** The seed's cost is dominated by the largest single DDL on the largest reconstructed object (typically a `CREATE INDEX`), not by the *count* of statements (each other DDL is fast). So the heartbeat form is strictly better than any single wall-clock number: it tolerates an arbitrarily long *but live* index build while still catching a true hang within one interval. The §F.5 oracle's hung-driver test (a mock whose `done` never fires **and** never heartbeats) exercises the heartbeat-absence trip; a companion test with a slow-but-heartbeating mock verb asserts the watchdog does **not** fire — proving slow-DDL and hang-detection do not conflate.

So the **teardown invariant holds for every host-only failure mode**: shadow-open error and `done({error})`/dropped-`Sender` failures are `Err`s on the engine thread (mode 3's `oneshot::Canceled` mechanism converts even a silently-dropped completion into an `Err`); the `in_flight` re-entry panic is a panic *on the engine thread* caught by the existing `catch_unwind`; a JS-thread panic is marshaled back as a `SeamError` (an `Err` on the engine thread) and can never cross the boundary as an unwind; and the **genuine driver hang (mode 4) is converted to an engine-thread `Err` by the per-verb watchdog**, so `catch_unwind → finish_dry_run → teardown_shadow` is reached even when the JS side never completes. The §F.5 teardown/no-leak oracle exercises **each** of these paths explicitly — **including a simulated hung driver (a `SeamSession` mock whose `done` is deliberately never called) to prove the watchdog fires teardown and the shadow DB + role do not leak** (below).

`driver-pg.js` (§D.2) gains a **shadow-open callback**: given a `shadow_db`, it opens a fresh pinned `pg.Client` to the swapped DSN (`shadow_dsn(adminUrl, shadow_db)`), installs the same connection-scoped int8/numeric parsers (§D.2 — the exact-integer contract must hold on the shadow connection too), and returns the handle. |---|---|---|
| **§A read widening regresses row decode** — the ~26 `.get`/`.try_get` sites break (incl. the newly-found `Option<i32>` at `drift.rs:801`) | Med | Land **compio-first** (§A.7): the platform suite on :5440 (Phase A gate, incl. journal/guard/rollback) is the regression bar; the compio adapter forwards decode byte-for-byte. `FromSeam` now includes `i32`/`Option<i32>`. The 3 flagged decisions (§A.8) are made once in the adapter, not per site. |
| **§A param widening — a bind site is missed** — a `&[&x]` slice not rewritten to `&[x.into()]` fails to compile, or a bind type has no `From` impl | Med | The ~29 sites are census'd explicitly (§A.1); `SeamBind` mirrors `BindValue` so `From<&str>/From<String>/From<i64>` cover every live bind (`&str`/`&String`/`exec_ms:i64`), and the compiler is the backstop (a missed site won't build). The compio `SeamBind→ToSql` mapper is the only remaining `ToSql` touch. |
| **`"char"`/`text[]` marshal differently host vs compio** — `SeamValue` shape diverges across drivers | Med | The two format-coupling spots (§A.8 flags 1–2) are resolved in the **adapter**: `"char"`→1-char `Text`, `text[]` NULL-vs-empty + element-NULL semantics fixed once. A differential oracle (Phase D) catches any host/compio delta. |
| **Awaiting the host callback without pulling tokio** — the ergonomic napi async path (`#[napi] async fn` / `Promise::await`) is gated behind the tokio-backed `async`/`tokio_rt` feature, which zero-tokio forbids; AND the cross-thread wakeup of a reactor-less `block_on` is the feasibility hinge | **Med** | Do **not** return a JS Promise for Rust to await. Use the **completion-callback bridge** (§B.3): `tsfn.call((request, done))` where `done` is a Rust-supplied napi `Function`; the JS wrapper `await`s its own driver then calls `done(err, rows)`, whose Rust body fires a `futures::channel::oneshot`; the engine's `block_on` parks on the `Receiver` and is unparked cross-thread by the `Sender::send`'s `Waker::wake` (`std::thread::Thread::unpark` is defined cross-thread-safe — §B.3). Only `call_id: u64` + the `Send + 'static` `oneshot::Sender` cross the napi boundary; no `!Send` engine state does (§B.3 Send-boundary). **Demonstrated, not asserted, by the Phase-B.5 runnable spike (§B.5) which gates Phase C.** Build with `napi = { default-features = false }` (no `async`/`tokio_rt`); a `cargo tree` gate asserts zero tokio. | **Threadsafe-function reentrancy / deadlock** — the engine holds a verb's future across a suspension point (the `&'a D` borrow permits a strictly-sequential source to do so) and issues a second verb on the one pinned connection | Med | **Mechanically enforced, not by analogy (§B.6):** the host `PgSession` carries an `in_flight: AtomicBool` (the shape the MySQL backend already runs — `transport.rs:252,386-393`) that `compare_exchange`es on entry and **panics on re-entry**. The **Phase-C gate runs the full apply with the guard armed and asserts it never trips** — converting "one verb at a time" from a claim into a checked invariant. Txn/lock/`SET` are SQL on existing verbs, so no nested callback exists; the host wrapper holds one `pg.Client`, never a pool. |
| **Marshaling correctness for typed catalog rows** — int8-as-string, int4 `character_maximum_length`, `"char"`, ordered `text[]` with NULL-vs-empty-vs-element-NULL | Med | The read union is 7 text/number-representable shapes (§A.2); int8/numeric cross as strings→`Text` **only if the `pg` wrapper installs its own parsers** (§D.2 — global `setTypeParser` override is a footgun, defended by connection-scoped parsers + a poisoned-global oracle); int4 crosses as number→`Int`, narrowed by `FromSeam for Option<i32>`; `text[]` order is load-bearing but JS arrays preserve order; NULL-array→`[]` vs present-array split fixed in `FromSeam`, and an **element-NULL coerces to `[]` on BOTH adapters (parity, not a fork)** so native and host stay interchangeable (§A.8). Checksum-identity + journal-identity oracles (Phase D) are the backstop. |
| **Bun N-API gaps** — `uv_default_loop` silently no-ops; Bun's TSFN Blocking-mode ordering / `done`-callback delivery may diverge from Node; `bun build --compile` Windows segfault | Med | Use `napi_get_uv_event_loop` (§E.2). **Do not infer Bun-correctness from "implements N-API":** the Phase-B.5 spike runs a Bun variant, and the **Phase-D gate runs the FULL host `apply` under `bun run` against real Postgres and asserts journal-identity with Node** (§7 gate 6) — proving Bun's TSFN ordering + `done` delivery match, not assuming it. `bun build --compile` gated per-platform (load-only), Windows flagged fragile; Deno/edge out of scope. Node is primary. **Contingency: if the Bun gate reds, Bun drops to unsupported (Node-only ship) — a scope reduction, not a re-architecture (§E.2); a named Bun version floor is pinned in CI and re-run per Bun bump; the cited Bun issue statuses are re-verified at Phase-D time, not trusted from a snapshot.** |
| **Platform native path regresses under the refactor** — the widening touches security-audited apply/journal/guard SOURCE (its type surface changes even though runtime behavior does not) | Med | The change is behavior-preserving by construction but **is** a real source rewrite (§A.8 table): the Phase A gate re-runs the **journal-immutability, guard/confinement, and rollback-ordering** suites specifically, plus the full PG suite on :5440, asserting identical outcomes. `SeamBind`/`SeamRow`/`SeamError` are unconditional; `native-pg` provides `SeamBind→ToSql` + `From<compio Row/Error>` adapters that forward SQL + binds + domain decode byte-for-byte. The addon is an *excluded leaf* crate — root `cargo build` never pulls napi. |
| **Sandbox capability dropped host-side** — pure-JS authoring loses the in-Rust V8 resource/wall/no-fs sandbox | Low (trusted posture) | Scoped as a posture decision (§1 non-goal, §D.1): fine for local/self-host (`SandboxPosture::Local`); multi-tenant hosted re-establishes sandboxing host-side (worker + `vm` + timeout) or keeps the in-Rust recorder for that posture only. Not a blocker for the primary local-deploy flow. |
| **SQLite security guarantee lost if host-provided** — `bun:sqlite`/`better-sqlite3` can't install the rusqlite authorizer | Low | Keep SQLite **native `rusqlite`** (§C.3) — the journal-immutability/confinement authorizer is in-process and cross-platform already; host-SQLite is a deferred, re-proof-gated option, never the default. |
| **Cargo feature unification pulls napi/compio onto platform binaries** | Low | `resolver = "3"` + the addon as an **excluded** leaf crate (§C.1) isolate its feature profile; `compio` becomes `native-pg`-scoped optional; verify `cargo tree` on the addon shows no compio and on the platform shows no napi. |
| **§F blast radius UNDER-SIZED** — sizing §F as "a constructor + role sig-generalization" hides that the entire ~700-line free-fn shadow harness (`shadow.rs`) + the `PostgresBackend.shadow` FIELD TYPE are a generic rewrite of the crate's most security-sensitive code | Med | **Sized honestly with the §F blast-radius table** (mirroring §A.8): every free fn (`dry_run`/`dry_run_declarative`/`dry_run_incremental`/`_body`s/`open_and_provision_shadow`/`seed_shadow_from_live`/`finish_dry_run`/`teardown_shadow`/`close_shadow_session`) goes `<D: PgSession>`; the compio-specific `connect_with_handle`/`JoinHandle` move behind an injected opener; the struct field `Option<PgShadow>` → `Option<ShadowKind/Box<dyn ShadowDryRun>>` with a rewritten `shadow()` accessor + `postgres.rs:33-42` doc comment. The shadow pre-flight fully completes+tears-down *before* the live apply acquires the project lock (§F.3), so the shadow and migrator connections are never in flight against overlapping state; the shadow DB has its own lock namespace, PG arbitrates cross-process. **Concurrent `apply()`+`dryRun()` in one process** get independent `SeamSession`s on independent worker threads, arbitrated server-side; the shadow migrator role is derived over the nanosecond-unique `shadow_db` (`shadow.rs:285,324`), and `migrator_role_name` is injective (`role.rs:184,407`), so the shadow role name **can never collide** with the live migrator role (§F.3). | **Host shadow dry-run — provision_migrator/exec_retry are `#[cfg(native-pg)]`, so ABSENT from the addon build** — a bare sig-generalization would call a symbol not compiled under `host-pg` | Med | §F.2 **removes the `#[cfg(feature="native-pg")]` gate** from `provision_migrator`/`deprovision_migrator`/`exec_retry` (`role.rs:148,228,380`) so they compile under `host-pg`; gate-removal forces the transitive de-compio work (the `compio::time::sleep` re-home + the `as_db_error()`→`SeamError.message` accessor — the only compio touches in the reachable bodies, confirmed by grep). **Build-gate:** `cargo build --no-default-features --features host-pg` compiles `provision_migrator` over the in-crate host `PgSession` with no compio in `cargo tree`, and Phase B runs it generically (§F.2/§7). |

Exact retry semantics (transient-only, 8-attempt bound, `attempt*10ms` backoff ⇒ ≤280ms cumulative) preserved; accessor changes `as_db_error().message()`→`SeamError.message`. Unit-tested (§F.2/§7 Phase B). |
| **`role.rs:158` transient-error match over `SeamError.message` instead of `as_db_error().message()`** — the host `pg` driver must surface the message so the transient-race retry still fires; and the predicate must NOT fork across drivers | Low | The match is **message-only** (`SeamError.message.contains("tuple concurrently updated")`), mirroring native `role.rs:158` **exactly** — it does *not* add a `SeamError.code`/SQLSTATE branch, so a host error with the message-but-a-surprising-code (or vice versa) classifies **identically** to native (§F.2). `SeamError.message` is mapped from node-pg's `err.message` (§B.2); the compio `&Client: PgSession` adapter carries the same message it read from `as_db_error().message()`, so the **native** retry is byte-identical. **Parity unit test:** the *same* synthetic `SeamError { message: … }` fed to both the native-adapted and host classifier fires the retry on both; a non-matching message fires on neither. |
| **napi-rs bundled `tokio_rt` sneaks tokio into the addon** — violates zero-tokio | Low | Explicitly **rejected** (§C.4, §B.3): `napi` declared `default-features = false` (no `async`/`tokio_rt`); the design never uses `#[napi] async fn` or `Promise::await` (the only two tokio-pulling napi features) — verbs bottom out in the completion-callback→oneshot bridge on `futures::executor::block_on`. A `cargo tree -p zeroship-migrate-node` gate on the leaf asserts zero `tokio` in its closure — wired to this specific design, not a promise. |
