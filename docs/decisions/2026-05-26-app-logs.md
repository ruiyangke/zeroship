# 2026-05-26 App Logs Source

## Decision

App logs originate from the runtime's existing `console.*` capture. The V8 console callback appends each line to `RuntimeState.per_request_logs`; `Runtime::call_fetch_handler` drains those lines into `FetchOutcome` / `SettledFetch`.

The worker now retains those returned request logs in a process-wide per-app ring buffer and exposes them at `GET /logs/{app_id}`. The control plane's `GET /api/apps/{id}/logs` admin route fan-outs to configured workers and returns the collected `string[]` unchanged to the builder.

Retention is intentionally small and in-memory: the last 1000 log lines per app per worker process. Runtime-side line truncation remains the existing 4096-byte cap.

## Rejected Options

- Control-plane generated sample logs: rejected because the builder and SRE views need actual app output, not a placeholder.
- Reading control-plane audit rows or usage reports: rejected because those record platform events and usage counters, not creator app `console.*` output.
- Reading tracing/stdout from process logs: rejected because the existing runtime mirror is gated for operator visibility and is not structured as per-app queryable state.
- Adding a durable logs database now: rejected as too broad for B2. The worker already receives real per-request console lines, and a bounded in-memory ring is enough to unblock pre-launch builder visibility without inventing a storage contract.
