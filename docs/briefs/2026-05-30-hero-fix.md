# Fix brief: Hero section — dual-review merge (codex + claude)

Hero (`sdks/ui/src/sections/Hero/`) is uncommitted. Two independent reviews
(codex xhigh + claude) converged on a cluster of real correctness bugs in the
**dual-surface normalization** and the **heading-label (`aria-labelledby`)
contract**. Token purity, Slot/asChild routing, forced-colors, and the happy-path
visuals are all sound — the bugs are in the edge interactions between the prop
surface and the compound surface.

WORKTREE: `/home/ruiyang/Projects/appbase/.claude/worktrees/ui-layouts-blocks`.
> **DO NOT commit, push, or merge.** Implement + self-verify + report.

The root cause across R1–R4 is the same: `Children.forEach` (Hero.tsx:242) is a
flat, single-pass, first-match walk, and the heading id is shared via context so
every `HeroTitle` claims it. The fix is one **recursive child-normalization pass**
in `HeroRoot` that flattens Fragments, lifts *all* media, identifies the *single*
primary headline, and assigns the section's labelling id to exactly that heading.

---

## R1 🔴 — `media` prop + `<Hero.Media>` child silently drops the child
Hero.tsx:242-257, 273-274. The walk lifts the first `<Hero.Media>` out of
`restChildren` (the `return` skips the push), then `mediaNode = media != null ?
<HeroMedia>{media}</HeroMedia> : mediaChild` prefers the prop and the lifted child
renders **nowhere**. Violates the file's own "ADDITIVE — there is no suppression"
contract (Hero.tsx:34-36), which holds for title/eyebrow/description/actions but
not media.

**Fix (additive, matches the title precedent): collect ALL media sources into the
media column.** Build `mediaNodes: ReactNode[]`:
- if `media != null` → push `<HeroMedia>{media}</HeroMedia>` (give it a stable key);
- push **every** lifted `<Hero.Media>` child (see R2), in document order, preserving keys.
`hasMedia = mediaNodes.length > 0`. The media column renders all of them. No
silent drop; nothing left stranded in the text flow. This also resolves the
multiple-`<Hero.Media>` 🟡 below (all collected, not just the first).

## R2 🔴 — Fragment-wrapped parts are invisible to the walk
Hero.tsx:242-257. `Children.forEach` does not descend Fragments. A plausible
pattern — `<><Hero.Media/></>` or grouping parts in a `<>…</>` — leaves the
`<Hero.Media>` inside the text Stack, `hasMedia` stays false, the split never
engages. Same blind spot makes the `hasTitleChild` no-headline guard misfire.

**Fix: replace the flat walk with a recursive flatten that descends Fragments**
(one level is the common case, but recurse fully to be safe), preserving keys and
document order. Match `child.type === HeroMedia` / `=== HeroTitle` against the
flattened nodes. A small local helper, e.g.:
```ts
function flattenChildren(children: ReactNode): ReactNode[] {
  const out: ReactNode[] = [];
  Children.forEach(children, (child) => {
    if (isValidElement(child) && child.type === Fragment) {
      out.push(...flattenChildren((child.props as { children?: ReactNode }).children));
    } else {
      out.push(child);
    }
  });
  return out;
}
```
(`import { Fragment } from "react"`.) Then iterate the flattened array to lift all
media, detect titles, and collect the rest. Keep keys stable so React doesn't warn
on the reordered media/text columns.

## R3 🔴 — duplicate heading `id` when both `title` prop AND `<Hero.Title>` render
Hero.tsx:296 + 369-374. Both the prop-driven `HeroTitle` and a compound
`<Hero.Title>` read the same `titleId` from context → two elements with
`id={titleId}` → invalid DOM + ambiguous `aria-labelledby`. The context JSDoc
(lines 96-100) *claims* "the first Title claims the id; a SECOND Title does NOT" —
but that guard is **not implemented**.

**Fix: the root owns the labelling id; exactly one headline carries it.** Stop
sharing `titleId` through context for the id. Instead:
- `HeroTitle` resolves its own id as `id ?? useId()` (its own fallback) — it NO
  LONGER reads `titleId` from context. (Context keeps carrying `align` only, used
  by Actions; Title doesn't need align. Drop `titleId` from context value, or keep
  the field unused — prefer dropping it so the contract is clear.)
- The **root** designates the single primary headline by precedence: the `title`
  **prop** if present; otherwise the **first** `<Hero.Title>` child (in flatten
  order). The root assigns `id={titleId}` to that one:
  - prop-driven: render `<HeroTitle id={titleId}>{title}</HeroTitle>`.
  - first compound child (only when `title == null`): `cloneElement(firstTitle,
    { id: titleId })`. Non-primary `<Hero.Title>` children render unchanged (own
    `useId` → unique, never `titleId`).
- Result: never two elements with the same id; the section is always labelled by
  the real primary headline.

## R4 🔴 — custom `id` on `<Hero.Title>` desyncs the section label
Hero.tsx:374 + 324. `resolvedId = id ?? titleId`, but the section unconditionally
emits `aria-labelledby={titleId}`. A consumer `<Hero.Title id="custom">` gives the
heading `id="custom"` while the section still points at `titleId` → dangling label.
The JSDoc punts this to the consumer, but the consumer can't reach the internal
section attr.

**Fix (folded into R3): Hero manages the labelling id; a custom `id` on the PRIMARY
title is overridden with `titleId` + a dev-warn.** Since the root injects
`id={titleId}` onto the primary headline (R3), a consumer-supplied `id` on the
primary is overwritten by the clone/explicit-prop — add a dev-warn when the primary
title carries a conflicting `id` ("Hero manages the heading id for the section
label; the custom id was ignored"). A custom `id` on a NON-primary `<Hero.Title>`
is honored (it isn't the label anchor). After R3+R4, `heading.id ===
root.aria-labelledby` always holds for the primary.

## R5 🟡 — multiple `<Hero.Media>` parts
Resolved by R1's "collect all media sources" (every `<Hero.Media>` lands in the
media column; none stranded in the text flow). No separate work — verify the R1
test covers two `<Hero.Media>` children.

## R6 🟡 — production ships a dangling `aria-labelledby` when no headline
Hero.tsx:324. The dev-warn DCEs in prod; the section still emits
`aria-labelledby={titleId}` pointing at nothing.
**Fix:** gate it — `aria-labelledby={hasHeadline ? titleId : undefined}` where
`hasHeadline = title != null || <at least one Hero.Title in flattened children>`
(both known before the return).

## R7 🟡 — `Hero.Title asChild` accepts a Fragment child
Hero.tsx:377-388. `isValidElement(<></>)` is `true`, so a Fragment passes the
guard; `Slot` then clones the Fragment with `id`/`className` that never reach a
real heading → the label dangles.
**Fix:** in the `asChild` branch, also reject a Fragment child
(`children.type === Fragment`) — dev-warn ("Hero.Title asChild expects a single
concrete element, not a Fragment; rendering nothing") and return null, same shape
as the existing non-element guard.

## R8 🟡 — missing `prefers-reduced-motion` parity block
Hero.css has `@media (forced-colors: active)` but no
`@media (prefers-reduced-motion: reduce)`. House rule requires both; Hero has no
motion, so add the no-op parity block matching the AuthForm.css:179-187 convention
(comment that there's nothing to disable, present for surface parity).

## R9 🟡 — breakpoint value drift
Hero.css:87 uses `@media (max-width: 47.99rem)`; the sibling split-collapse
implementations (`layouts/Split/Split.css`, `blocks/FormSection/FormSection.css`)
use `47.999rem` for `--zs-bp-md` (48rem). Align Hero to **`47.999rem`** so the
collapse breakpoint matches the rest of the package exactly.

## R10 🟢 — `useHeroContext` fallback returns `titleId: ""`
After R3, Title no longer reads `titleId` from context, so drop `titleId` from the
context value/fallback entirely (the fallback becomes `{ align: "center" }`).
Tidies the nit out.
